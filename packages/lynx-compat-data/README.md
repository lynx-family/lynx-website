# `@lynx-js/lynx-compat-data`

The Lynx Compatibility Data ("LCD") project contains machine-readable compatibility data for Lynx technologies, such as Lynx APIs, elements, components, and features across different platforms and versions. Our goal is to document accurate compatibility information for Lynx technologies, enabling developers to create cross-platform compatible applications more easily within the Lynx ecosystem.

## Package contents

There are two types of data in this package:

1. **Platform data**: Data for Lynx platforms e.g. iOS, Android, Web, etc.
2. **Compatibility data**: Platform and version support for Lynx APIs, elements, CSS, and features.

### Platform data

Platform data are defined against [`platform.schema.json`](./schemas/platform.schema.json). See [`platform-schema.md`](./schemas/platform-schema.md) for more details.

#### [`platforms`](./platforms)

Data for Lynx platforms e.g. iOS, Android, Web, etc.

`platforms.json` contains the ids of all platforms. This shall be generated by the build script in the future.

### Compatibility data

Compatibility data are defined against [`compat-data.schema.json`](./schemas/compat-data.schema.json). See [`compat-data-schema.md`](./schemas/compat-data-schema.md) for more details.

Compatibility data are organized into category directories such as `elements`, `css`, and `features`. A category may contain subcategory directories, such as `css/properties`, when the subcategory is not directly referenceable. Referenceable technologies are defined in `*.json` files under the corresponding category.

Each `*.json` file describes a referenceable Lynx technology and its compatibility statements. API module files may also define nested identifiers such as functions, classes, and properties.

#### [`elements`](./elements)

Data for Lynx elements e.g. `<view>`, `<text>`, `<image>`, etc.

#### [`css`](./css)

Data for CSS e.g. properties like `background`, `color`, etc.

> **Note**: CSS property compatibility data (`css/properties/*`) is generated at build time and is **not** tracked in git. The generator (`pnpm run gen-css`) uses these inputs:
>
> 1. **`@lynx-js/css-defines`** — the primary source of truth. To update a property, change the upstream definition and bump the dependency, then regenerate.
> 2. **`css/properties-manual/`** — hand-maintained files for properties not yet covered by `css-defines` (e.g. `css-variable`, `custom-property`, `filter-properties`). The directory listing itself is the allowlist; no name is hardcoded in the generator. A filename collision between the two sources fails the build, so once `css-defines` adds coverage, remove the corresponding file from `properties-manual/`.
> 3. **`web-css-support.json`** — Web support corrections for properties from `css-defines`, checked against `lynx-stack/main`. Each entry identifies a feature by its key path and replaces only `support.web_lynx`. Other platforms and feature definitions remain owned by `css-defines`. Missing upstream properties or feature paths fail generation, so dependency updates cannot silently discard these corrections.
>
> Every generated `__compat` block includes source metadata so contributors can
> find the authoritative input instead of editing generated output:
>
> - `source_url` points to the upstream `css-defines` JSON file.
> - `source_file` identifies a hand-maintained file relative to this package.
>   Web overrides retain the upstream `source_url` and add `source_file: "web-css-support.json"`.
>
> Nested features receive the same metadata as their parent property.
>
> The package `prepack` lifecycle runs the CSS generator and validation before
> packing or publishing, so generated `css/properties/*.json` files are included
> in the package tarball without being committed to git.

#### [`lynx-api`](./lynx-api)

Data for Lynx APIs, e.g. `setTimeout`.

#### [`lynx-native-api`](./lynx-native-api)

Data for Lynx Native APIs, e.g. `LynxView`.

#### [`react`](./react)

Data for ReactLynx framework.

#### [`features`](./features)

Data for cross-platform Lynx features that are not APIs, elements, or CSS.

## Usages

### Usages of JSON files

This package contains all the data in its raw JSON format without packaging them into a giant aggregated JSON file, so you can just reference them individually by path:

```ts
// Static import
import testData from '@lynx-js/lynx-compat-data/test/api.json';

// Dynamic import
const testData = await import('@lynx-js/lynx-compat-data/test/api.json');

// If you server them somewhere...
fetch('/path/to/data.json')
  .then((res) => res.json())
  .then((data) => {
    // use the data here
  });
```

### Usages of TypeScript types

Additionally, types are also exported. Types are particularly useful when you want to declare functions to consume data in a type-safe manner:

```ts
// Import specific types
import type { PlatformName } from '@lynx-js/lynx-compat-data';

function mapPlatformNameToName(platform: PlatformName) {
  switch (platform) {
    case 'android':
      return 'Android';
    case 'ios':
      return 'iOS';
    // if you miss some cases, TypeScript will help you out.
  }
}
```

### Type-safety

The json files will be validated using [Avj JSON schema validator](https://ajv.js.org/) against [JSON Schemas](./schemas) prior to release, so you can usually trust their types:

```ts
// Platform data
import type { PlatformStatement } from '@lynx-js/lynx-compat-data';
import iosJson from '@lynx-js/lynx-compat-data/platforms/ios.json';
const ios = iosJson.platforms.ios as PlatformStatement;

// API data
import type { Identifier } from '@lynx-js/lynx-compat-data';
import sTOJson from '@lynx-js/lynx-compat-data/lynx-api/global/setTimeout.json';
const sTO = sTO['lynx-api'].global.setTimeout as Identifier;
```

But to make it more robust, we have also exported utility functions to help you work with the data in a type-safe manner at runtime.

For example, use the platform-name helper without accessing the platform JSON
structure in the caller:

```ts
import { getFullPlatformName } from '@lynx-js/lynx-compat-data';

getFullPlatformName('android'); // "Android"
```

```ts
import { isPlatformStatement } from '@lynx-js/lynx-compat-data';
import iosJson from '@lynx-js/lynx-compat-data/platforms/ios.json';

if (isPlatformStatement(iosJson.platforms.ios)) {
  // ios: PlatformStatement
  ios.type; // safe to access
}
```

A more realistic example of fetching data remotely:

```ts
fetch('https://api.example.com/lynx-compat-data/platforms/ios.json')
  .then((response) => response.json())
  .then((data) => {
    if (isPlatformStatement(data.platforms.ios)) {
      console.log(`iOS platform type: ${data.platforms.ios.type}`);
      console.log(
        `Latest iOS version: ${Object.keys(data.platforms.ios.releases).pop()}`,
      );
    } else {
      console.error('Invalid iOS platform data');
    }
  })
  .catch((error) => console.error('Error fetching iOS data:', error));
```

## Development

Follow [Compatibility Data](../../CONTRIBUTING.md#compatibility-data) for
authoring and review principles.

### Update Web support

The Web statements were reviewed against
[`lynx-stack/main` at `5041e00c0`](https://github.com/lynx-family/lynx-stack/tree/5041e00c0ff501cda3ec08f6ea7a402910898aa7).
Check the implementations and tests in `packages/web-platform/web-core`,
`packages/web-platform/web-elements`, and `packages/react/runtime` before changing
support. Tag aliases, event payloads, and method signatures can differ from native
Lynx even when a browser API with a similar name exists.

Use `version_added: true` for implemented Web features when the first Web package
release is unknown, `false` for unsupported features, and `null` for unknown
support. Use `partial_implementation` only when a missing core capability or a
limitation affects common usage, and explain that limitation. Unsupported edge
cases alone do not warrant a partial flag or a compatibility note. Do not mark
an entire feature as partial solely because an optional subfeature is unsupported.
Use `alternative_name` when callers need a different tag or method name. Native
Lynx SDK versions do not identify Web package releases.

Edit the corresponding compatibility JSON for hand-maintained features. For
generated CSS properties, edit `web-css-support.json` and record the reviewed
source revision there. After an upstream `css-defines` release incorporates a
correction, remove the redundant override. Run `pnpm run gen-css`, `pnpm run lint`,
and `pnpm test` from this package to verify the result.

### Lint/Validate JSON Data

Run the linting process to validate all JSON data files against their schemas:

```bash
pnpm run lint
```

### Lint Key Names

Run the key name linter to check for improperly named keys in compat data JSON files. This ensures keys use meaningful API names instead of placeholder names like `nested_value_N`:

```bash
pnpm run lint:keys         # Check for issues
pnpm run lint:keys --fix   # Auto-fix issues by extracting names from description fields
```

The linter checks for:

1. Keys like `nested_value_N` or `unsupported_value_N` that should use actual API names
2. Keys with `<code>name</code>` patterns in their description that should use the name as the key

### Build

The build process consists of the following steps:

1. **Generate CSS property data** from `@lynx-js/css-defines`:
   ```bash
   pnpm run gen-css
   ```
2. **Generate platforms data**.
3. **Generate TypeScript declarations** for all JSON data files.
4. **Compile runtime helpers and their declarations**.

Run all build steps at once:

```bash
pnpm run build
```

The build also compiles `index.ts` into the helper runtime and declarations in
`dist/`. To refresh only those entry points after editing helpers or data types:

```bash
pnpm run build:runtime
```

The package root exports data types and runtime helpers such as
`getFullPlatformName` and `isPlatformStatement`. JSON subpaths remain available.
The website's `prepare` lifecycle runs `build:package` for local consumers.
Generated `dist/` files are not committed.

### Prepare package artifacts

From the OSS repository root, prepare the package for a workspace or submodule
consumer with one command:

```bash
pnpm --filter @lynx-js/lynx-compat-data run build:package
```

This generates CSS property data, fixes key names, validates compatibility data,
and compiles the helper runtime and declarations. It uses the committed platform
metadata and schema types; `build` additionally regenerates those maintained
files.

Published packages already include generated CSS and `dist/`. Consumers can
reuse complete artifacts from an installed package or a prepared OSS checkout.
If either output is missing, install the OSS checkout's dependencies and run
`build:package` there before copying the package into the consuming site.

### Site-specific Statistics

Generate statistics after applying any data overlays. From the OSS repository
root, use `pnpm gen:compat-stats`; it supplies this site's EN documentation
root.

Consumers running `gen-stats` themselves should supply their own docs root via
`--docs-root <dir>` or `LYNX_COMPAT_DOCS_ROOT`. Relative paths resolve from the
caller's working directory. With a docs root, the generator emits `doc_url`
only for destinations that resolve to a route in that tree.

Without a docs root, it emits URLs unchecked. A supplied root that does not
exist is an error, not a silent skip. Neither `build:package` nor the package's
installation location chooses a site's routes. Route existence does not prove
that a destination is canonical; see
[Compatibility Data](../../CONTRIBUTING.md#compatibility-data).

### Package

Before packing or publishing, the `prepack` lifecycle runs `build:package`,
using the same artifact preparation as workspace and submodule consumers.

To verify the packed package contract locally:

```bash
pnpm run pack:check
```

This check creates a package tarball, verifies that generated
`css/properties/*.json` files are included, installs the tarball into a clean
temporary consumer with scripts disabled, and reads
`css/properties/custom-property.json`. It also imports runtime helpers from the
package root and type-checks a consumer using both helpers and data types.

### Test

Run the test process to validate the generated TypeScript declarations:

```bash
pnpm run test
```
