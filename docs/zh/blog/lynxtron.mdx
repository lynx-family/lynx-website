Electron 让前端开发者可以用 JavaScript 高效地开发桌面应用：界面用 Web 技术编写，系统能力通过 Node.js 调用。这份效率建立在 Chromium 之上，代价也同样来自它：每个应用都要随包分发一份浏览器内核，基础包体因此偏大，运行时内存占用也偏高。为了在保留这份效率的同时减轻这些代价，我们开发了 **[Lynxtron](/zh/lynxtron/)**。

它以 Node.js 为宿主，由 Lynx 渲染界面，基础运行时不内置浏览器内核。开发者可以继续使用 Electron 风格的主进程 API 管理窗口和应用生命周期，并以开发 Web 应用的方式编写 Lynx 组件和样式。同一套界面代码也能[在浏览器里运行](/zh/lynxtron/learn/running-on-web)，不必为 Web 另写一份。

<span id="light-weight-and-fast" />

- **下载体积。** Lynxtron 0.0.28 的运行时压缩包在 macOS arm64 上为 **24 MB**，在 Windows x64 上为 **35 MB**。相同平台上，Electron 44.3.0 分别为 **130 MB** 和 **158 MB**。[Lynxtron 发布包](https://github.com/lynx-family/lynxtron/releases/tag/v0.0.28) · [Electron 发布包](https://github.com/electron/electron/releases/tag/v44.3.0)
- **空闲内存。** 在 700×520 的 hello-world 空闲基准中，Lynxtron 0.0.28 的占用低于 Electron 44.3.0：macOS 上（Apple M5 Max MacBook Pro）单进程为 **52 MB** 内存 Footprint，Electron 四个进程合计 **86 MB**，约低 **40%**；Windows 上（Windows 11 25H2、Core Ultra 7 155H）单进程为 **68.3 MB** Working Set - Private，Electron 四个进程合计 **158.7 MB**，约低 **57%**。
- **启动速度。** 抖音 PC Windows 版已上线 Lynxtron 启动入口，与原有的 Electron 启动入口并存。线上真实用户数据显示，首屏展现耗时 P50 缩短 **27%**；冷启动场景下，首刷耗时 P90 从 Electron 的 **19.0 秒**降至 **10.8 秒**，降幅 **43%**。

## Electron 风格的 API 与架构 \{#multiplatform}

### Node.js 宿主与 Lynx 渲染架构

迁移 Electron 应用时，Agent 可以直接从现有的 Node.js 主进程脚本入手。Lynxtron 沿用 Electron 的主进程 API：应用生命周期、菜单、托盘、对话框等保持同样的用法。最直接的差异在窗口这一层：`BrowserWindow` 换成 `LynxWindow`，窗口的创建、尺寸、显隐和全屏等管理方法沿用 `BaseWindow` 的命名与语义，但加载的是 Lynx bundle 而非 HTML，`webContents` 也不再提供。渲染架构随之改变：Electron 在独立的 Chromium 进程里渲染页面，Lynxtron 在同一进程的主线程上渲染界面，在后台线程执行业务逻辑。[了解 Lynxtron 架构](/zh/lynxtron/learn/what-is-lynxtron)。

![在 Lynxtron 中，Node.js 宿主和 Lynx 渲染共用主线程，UI 业务逻辑运行在后台线程。](https://lf-lynx.tiktok-cdns.com/obj/lynx-artifacts-oss-sg/lynx-website/assets/lynxtron/lynxtron-architecture.png)

### 用 Agent 熟悉的 API 管理窗口

例如，Electron 应用通常在 `app.whenReady()` 之后打开第一个窗口。在 Lynxtron 中也一样，创建 [`LynxWindow`](/zh/lynxtron/api/@lynx-js/lynxtron/Class.LynxWindow.mdx)，然后加载编译好的 Lynx bundle 即可。

```ts
import { app, LynxWindow } from '@lynx-js/lynxtron';

app.whenReady().then(() => {
  const win = new LynxWindow({ width: 800, height: 600 });
  win.show();
  win.loadFile('main.lynx.bundle');
});
```

### 在 Lynx 中直接调用 Node.js 对象

Lynxtron 的 [preload script](/zh/lynxtron/learn/Communication-Between-Node-And-Lynx) 与 [Electron 的做法](https://www.electronjs.org/docs/latest/tutorial/tutorial-preload) 一致：在隔离的上下文中获得 Node.js 能力，再暴露给界面。区别在于系统环境与 UI 环境之间能传递什么。Electron 的 [`contextBridge`](https://www.electronjs.org/docs/latest/api/context-bridge) 会按自己的规则序列化、代理或拷贝跨上下文的值，页面拿不到 preload 上下文里的原始对象。Lynxtron 的 [`contextBridge.exposeInLynxBTS()`](/zh/lynxtron/api/@lynx-js/lynxtron/context-bridge/Interface.ContextBridge.mdx#exposeinlynxbts) 则把 JS 对象直接暴露给 Lynx BTS：对象上可以带函数，函数可以使用 preload 上下文中的闭包、接收其他函数作为参数，也可以返回 Promise。

Electron 也提供 `nodeIntegration`，让页面直接使用 Node.js 能力，但开启后隔离性变差，通常不被推荐。Lynxtron 不需要这个取舍：preload script 在隔离的上下文中使用 Node.js，暴露出来的对象依然可以直接调用。

### 把原生视图嵌入 Lynxtron

### 在 UI 侧直接加载 Node-API 模块

Electron 的渲染进程跑在 Chromium 里，用不了 [Node-API](/zh/guide/use-native-modules.html?platform=node-api)，原生模块只能加载在主进程，UI 通过 IPC 调用。Lynxtron 的 preload script 运行在 Node.js 环境中，可以直接 `require` 原生模块，再把对象交给 Lynx UI。模块本身与 Electron 通用，都是 npm 上的 Node-API 模块，重建工具换成 [`@lynx-js/lynxtron-rebuild`](/zh/lynxtron/api/@lynx-js/lynxtron-rebuild/) 即可。我们也在为所有 Lynx 原生平台[引入 Node-API](https://github.com/lynx-family/lynx/discussions/845)。
