Lynx 4.0 已经正式发布！

这个版本继续改善从编写界面到定位问题的开发体验：让 AI 更准确地使用 Lynx API、生成可渲染的界面，让 ReactLynx 支持更灵活的动态元素构建，并把线上错误与运行时 UI 节点映射回源码。在折叠屏适配上，Lynx 通过客户端同步尺寸变化，让 Lynx 页面沿用熟悉的 Flex 布局和相对单位，随窗口大小自然调整。此外，4.0 还更新了桌面端 CSS 与元件能力，开源了 `<webview>` 和 `<blur-view>`，并新增了全局内存查询。下面我们一起来看看这些变化。

## 自适应设计

### 折叠屏

苹果在秋季发布会上推出了首款折叠屏 [**iPhone Duo**](https://www.apple.com.cn/newsroom/2026/09/apple-unveils-iphone-duo/)，也对应用适配动态变化的屏幕形态提出了新的要求。基于与 TikTok 的合作实践，Lynx 4.0 现已具备基础的折叠屏适配能力。窗口尺寸变化时，宿主会为 [LynxView](/api/lynx-native-api/lynx-view) 一并更新[屏幕尺寸](https://github.com/lynx-family/lynx/blob/4.0.3/platform/darwin/ios/lynx/public/LynxView.h#L244)、[视口](/api/lynx-native-api/lynx-view/update-viewport)和 [GlobalProps](/api/lynx-api/lynx/lynx-global-props)。这些更新会触发页面重新布局；在默认的 reactive 模式下，GlobalProps 更新还会触发 ReactLynx [重新渲染](/api/rspeedy/react-rsbuild-plugin.pluginreactlynxoptions.globalpropsmode)。对于已经采用[弹性布局](/guide/ui/layout/flexible-box-layout)和[相对单位](/api/css/data-type/length)的页面，通常无需修改前端代码，即可适应折叠、展开带来的尺寸变化。更多信息请参阅[**折叠屏适配指南**](/guide/inclusion/foldable-devices)。

## 原生背景模糊与 Liquid Glass

Lynx 直接渲染为平台原生 UI，因此从第一天起就能承载 Liquid Glass 等原生视觉效果。在 TikTok 等线上应用中持续打磨数月后，我们终于有信心将这项能力交付给社区。

我们选择通过一个一体化的 `<blur-view>` 元素，统一封装 Web、HarmonyOS 和 iOS 的原生背景模糊、iOS Liquid Glass，以及 Lynx 的 Android 模糊实现，让开发者可以跨平台复用相同的结构，并通过平台专属配置实现渐进增强与优雅降级。

在 iOS 上，为 `<blur-view>` 配置 [`blur-effect="glass"`](/api/elements/built-in/blur-view#blur-effect) 即可渲染 Liquid Glass。Lynx 通过 [`glass-style`](/api/elements/built-in/blur-view#glass-style)、[`glass-tint-color`](/api/elements/built-in/blur-view#glass-tint-color) 和 [`glass-interactive`](/api/elements/built-in/blur-view#glass-interactive) 开放了 [`UIGlassEffect`](https://developer.apple.com/documentation/uikit/uiglasseffect) 的关键配置。对于基于 [`UIGlassContainerEffect`](https://developer.apple.com/documentation/uikit/uiglasscontainereffect) 的组合效果，可以使用 [`blur-effect="glass-container"`](/api/elements/built-in/blur-view#blur-effect)，并通过 [`spacing`](/api/elements/built-in/blur-view#spacing) 控制玻璃元素开始融合的间距。

## 桌面端渲染

Lynx 4.0 进一步扩展桌面端的 CSS 表现力，为采用 Clay 渲染的 macOS 和 Windows 应用带来自定义文本插入光标与多层遮罩合成。

### 自定义文本插入光标

四个新的 `-x-caret-*` 属性让你可以为 `<input>` 和 `<textarea>` 设置光标的[渐变](/api/css/properties/-x-caret-gradient)、[宽度](/api/css/properties/-x-caret-width)、[高度](/api/css/properties/-x-caret-height)与[圆角](/api/css/properties/-x-caret-radius)：

```css
input {
  -x-caret-gradient: linear-gradient(to bottom, #00a6a6, #1479ff);
  -x-caret-width: 2px;
  -x-caret-height: 20px;
  -x-caret-radius: 1px;
}
```

### 多层遮罩合成

通过 [`mask-composite`](/api/css/properties/mask-composite)，你可以使用 `add`、`subtract`、`intersect` 和 `exclude` 组合多个遮罩层，直接通过 CSS 实现镂空、交叠等视觉效果：

```css
.masked-view {
  mask-image: linear-gradient(#000, #000), linear-gradient(#000, transparent);
  mask-composite: exclude;
}
```

## ReactLynx

### `createElement` 与 `cloneElement`

ReactLynx 现已支持 [`createElement`](/api/react/Function.createElement) 和 [`cloneElement`](/api/react/Function.cloneElement)。当元件类型要到运行时才能确定，或需要基于已有元素调整属性时，可以直接使用这两个熟悉的 React API：

```tsx
import { cloneElement, createElement } from '@lynx-js/react';

export function StatusLabel({ selected }: { selected: boolean }) {
  const label = createElement('text', { className: 'label' }, 'Lynx 4.0');

  return selected
    ? cloneElement(label, { className: 'label label-selected' })
    : label;
}
```

这让配置驱动的界面和通用组件封装有了更多选择。如果元件结构在开发时已经确定，仍然推荐直接编写 JSX，让编译器分析静态结构并优化渲染。两种写法的取舍见[编译协同渲染](/react/compiler-informed-rendering)。

### 统一调试信息

线上报错通常指向压缩后的 JavaScript，主线程报错给出的则是字节码位置，无法直接对应源码的行列号。为此，Rspeedy 现在会为每次构建生成一份 `debug-metadata.json`，统一汇集 JavaScript 与 CSS Source Map、字节码调试信息和 UI Source Map。借助它可以完成两类反解：

- **线上错误反解**：将打包后的错误堆栈还原为源码文件、行和列，主线程抛出的错误同样适用。
- **UI 节点树反解**：从客户端导出运行时 UI 树，找到创建每个节点的 JSX，帮助定位界面问题。

UI Source Map 默认关闭，需要在 `pluginReactLynx` 中显式开启：

```ts title="lynx.config.ts"
import { defineConfig } from '@lynx-js/rspeedy';
import { pluginReactLynx } from '@lynx-js/react-rsbuild-plugin';

export default defineConfig({
  plugins: [
    pluginReactLynx({
      enableUiSourceMap: true,
    }),
  ],
});
```

生产构建默认会在生成后删除 `debug-metadata.json`。进行线上错误反解时，需要保存并托管每次构建对应的调试信息；进行 UI 节点树反解时，还需要让运行时能够获取对应的 `debugMetadataUrl`。具体接入方式见[线上错误反解](/rspeedy/map-errors-to-source)和[反解 UI 节点树](/rspeedy/ui-source-map)。

## 生成式 UI

### A2UI

除了帮助开发者写代码，[Lynx A2UI](/react/genui/a2ui) 也让 Agent 能在运行时生成界面：模型输出结构化的协议消息，由 Lynx 渲染器转换为原生 UI，并随着消息到达逐步更新。

在此前发布 A2UI 渲染器的基础上，我们新增了 [`lynx-a2ui`](/ai/skills/lynx-a2ui) Skill，并通过 `lynx-community/skills` 统一维护和分发：

```bash
npx skills add lynx-community/skills -s lynx-a2ui
```

这个 Skill 会先读取应用的能力目录（Catalog），再根据其中的组件、函数和参数约束生成 A2UI 消息。开发者可以使用默认目录，也可以提供业务自己的目录，让 Agent 生成的界面使用应用已支持的能力。完整介绍见 [A2UI 驱动的 Lynx 生成式界面](/blog/lynx-a2ui)。

### OpenUI

Lynx 也提供了 [`lynx-openui`](/ai/skills/lynx-openui) Skill，将自然语言界面需求转换为 OpenUI Lang v0.5 声明式程序。生成的内容可以传给 `@lynx-js/genui/openui` 的 `<OpenUiRenderer>` 渲染，适合需要流式生成、响应式状态和工具调用的界面。

```bash
npx skills add lynx-community/skills -s lynx-openui
```

这个 Skill 会引导 Agent 先读取内置 Catalog 或应用提供的自定义组件签名，再检查组件名称、位置参数和引用关系，生成符合当前 Renderer 能力的程序。默认输出完整程序；显式启用 edit mode 或 `mergeStatements` 后，也可以只输出发生变化的语句，实现增量更新。

对于可交互界面，可以通过 `$state` 表达响应式状态，通过 `Query()` 读取宿主数据，并用 `Action()` 编排交互步骤。查询和写入只使用宿主实际提供的工具，其中 `Mutation()` 必须由显式 Action 触发，例如用户点击提交按钮。这样，生成的界面既能展示内容，也能接入应用已有的业务流程。

接入方式见 [ReactLynx 中的 OpenUI](/react/genui/openui)，也可以在 [Lynx GenUI OpenUI Playground](https://lynx-stack.dev/genui/#/openui) 中体验。

## API 文档 Skill

让 AI 编写 Lynx 页面时，一个常见问题是它会沿用 Web 开发经验，生成 Lynx 尚不支持的属性或布局写法。[`lynx-api-docs`](/ai/skills/lynx-api-docs) Agent Skill 为 coding agent 提供项目本地的 Lynx API、CSS、布局和元件参考资料，帮助它在实现前确认能力边界。

这些资料来自公开的 `@lynx-js/lynx-api-docs` 软件包，可以通过社区维护的 [Lynx Agent Skills](https://github.com/lynx-community/skills) 安装：

```bash
npx skills add lynx-community/skills -s lynx-api-docs
```

安装后，兼容的 agent 可以按任务加载相关资料。比如在实现一个滚动列表前，先确认 `<scroll-view>` 的属性、事件和布局约束，再生成代码。更多项目配置方式见[面向 AI 的 Lynx](/ai/)。

## 全局 Lynx 内存查询

当应用同时承载多个 Lynx 页面时，定位内存问题往往需要先回答：哪些实例还存活、内存主要花在哪里？Lynx 4.0 在 iOS 和 Android 提供了[全局 Lynx 内存查询](/guide/performance/monitor-performance/global-memory-usage-query)，可以异步采集当前进程内存活实例的 Lynx 归因内存，并按 Element、UI/View、主线程 runtime 和后台线程 runtime 等分类返回结果。

这项能力适合在内存压力或问题排查时主动获取快照。若需要进一步追踪 JavaScript 对象的引用关系，可以根据查询结果选择目标实例，再分析 heap snapshot。
