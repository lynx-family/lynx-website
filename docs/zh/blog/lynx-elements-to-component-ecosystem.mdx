Lynx 开源之初，我们曾提到，许多经过生产验证的能力——包括更丰富的 UI 组件——[还在路上](/blog/lynx-unlock-native-for-more#这不是终点而是新的起点)。从 Lynx 3.6 到当前开发版本，我们一直在推进这项工作：让更多原生元件进入开放环境，也通过 [lynx-ui](/blog/lynx-ui) 将这些底层能力组合成前端开发者可以直接使用的组件。

这些进展正在补上能力开放的第一块拼图，也让社区的关注点从“有哪些 Element 可以使用”，进一步转向这些能力承诺怎样的跨平台语义、如何被组合成产品级体验、能否被不同 DSL 复用，以及如何在长期演进中保持稳定。

因此，下一阶段要补上的不只是更多 Element 或更多组件，而是一条能够持续运转的能力链路：原生能力可以进入，跨平台语义可以讨论，组件模型可以验证，社区反馈也可以重新推动实现演进。

> **范围说明：**本文讨论的是 Lynx 跨端 UI 生态的建设方向，而不是一份带有固定日期的交付清单；其中一些能力已经在推进，另一些仍需要通过 RFC、实现和社区讨论形成具体设计。本文也不试图为所有社区组件定义统一的治理或准入规则。

## 能力正在开放，关注点也随之改变

在 Lynx 中，[元件（Element）](/guide/ui/elements-components)是界面的基础构建单元。`<view>`、`<text>` 和 `<image>` 负责最基本的结构与表达；滚动、输入、媒体播放和浮层等能力，则需要与各平台的原生 UI 系统深入协作。

Lynx 3.6 时，开源体系中的扩展原生元件主要包括 `<input>`、`<textarea>` 与 `<overlay>`。此后，我们逐步将更多已经在真实应用中运行的能力带入开放环境：

- Lynx 3.7 引入了跨平台原生矢量渲染元件 [`<svg>`](/api/elements/built-in/svg)；
- Lynx 3.8 继续补充 [`<refresh>`](/api/elements/built-in/refresh) 等交互容器，并开始开放 Markdown 渲染能力；
- 在当前开发版本中，`blur-view`、`markdown`、`scroll-coordinator`、`video`、`viewpager` 与 `webview` 等能力也在 Android、iOS 和 HarmonyOS 上陆续进入开放体系。

这些能力覆盖输入与键盘、独立浮层、矢量与模糊效果、刷新与复杂滚动、富文本与媒体，以及嵌入式内容。它们中的许多并不是新的实验，而是经历过真实产品检验的实现。

但代码进入仓库并不等于能力已经进入生态。平台支持、稳定性等级、已知差异、变更记录、迁移路径和自动化测试，都会决定开发者能否真正依赖一项能力。**从代码开放到能力可依赖，中间仍然需要一套公开的语义与维护承诺。**

## XElement × lynx-ui：从线性分层到反馈系统

把组件生态理解为“Element 外面再包一层组件”，隐含了一个线性模型：原生层先定义完整能力，前端层再负责消费。但真实的跨端 UI 并不沿着这条单向链路演进。

如果每一种产品交互都被固化为新的原生属性，Element API 会不断膨胀，底层实现也很难跟上产品需求；如果平台差异、性能开关和兼容策略全部交给前端，每个 DSL 和产品团队又会重新支付同一份工程成本。原生负责性能，不意味着原生应该定义所有产品行为；前端负责组合，也不意味着前端应该重新处理所有平台差异。

因此，XElement、Element 与 lynx-ui 的关系也不能只靠一组静态分层来描述。Element API 会受到原生平台能力的约束，也会被上层组件的真实需求重新塑造；lynx-ui 消费底层能力，也会通过组件模型、测试和产品场景参与定义什么才是可依赖的跨平台行为。

更准确的观察方式，是看同一个系统中两种相反方向的流动：

> **Capability Flow：平台能力 → XElement 实现 → Element 契约 → lynx-ui 组合 → 产品体验**
>
> **Feedback Flow：产品需求与测试 → 组件模型 → Element 语义 → XElement 实现**

在 Capability Flow 中，[XElement](/guide/ui/elements-components#xelement) 扩展 Lynx 可以原生表达的能力，并消化平台 API、线程模型、性能与兼容性差异；Element 以开发者可见的 API、事件和状态承载这些能力；[lynx-ui](https://github.com/lynx-family/lynx-ui) 则把它们组织成 ReactLynx 开发者可以直接使用的无样式组件。

在 Feedback Flow 中，方向反了过来。真实组件会暴露容器、生命周期、事件、动画与无障碍上的缺口；这些问题先推动组件模型和 Element 语义收敛，再进入各平台的 XElement 实现与测试。Element 是两者共同使用的语言：它把原生能力变成可以讨论和依赖的契约，也让上层组件的反馈有明确的落点。

### 让能力在实现与组合之间往返

Overlay 展示了这两种流动如何发生在同一项能力上。

作为 XElement 的一部分，原生 `<overlay>` 解决的是独立渲染层问题：它让内容脱离普通视图树的裁剪与层级限制，并在正确的原生容器中显示。但 `<overlay>` 本身并不知道什么是对话框，也不负责管理打开与关闭、进出场动画、锚点定位或拖拽吸附。

lynx-ui 首先通过 `OverlayView` 统一不同容器和平台上的 Overlay 使用方式。在此之上：

- `Popover` 组合锚点追踪、定位、开关状态与 Presence；
- `Dialog` 组合 Trigger、Backdrop、Content、关闭行为与进出场状态；
- `Sheet` 进一步组合 Overlay、Presence、主线程手势与 Motion，支持拖拽、阻尼和吸附点。

这个例子说明，XElement 与组件之间不是一一对应关系。一个稳定的 XElement 可以支撑多个上层组件；这些组件又会对容器选择、事件穿透、生命周期和动画协同提出更具体的要求，帮助 `<overlay>` 收敛出更清晰的跨平台语义。

这条链路不再只是“原生能力 → 前端封装”，而开始形成循环：

> **原生能力 → 组件组合 → 产品场景 → 语义反馈 → 原生能力**

没有 XElement，组件需要反复处理平台差异；没有 lynx-ui，原生能力也缺少进入真实产品场景的验证过程。两者不是上下游的一次性交付关系，而是在实现与组合之间共同收敛能力。

### 让反馈系统进入开放生态

如果 Overlay 说明了能力如何在实现与组合之间往返，`video` 则呈现了这套反馈系统进入开放生态后的初步形态。

`video` 的 API、跨平台语义和兼容性预期将由 Lynx 团队与社区共同讨论、共同定义；Lynx 团队负责把这些共识落实为 Android、iOS 与 HarmonyOS 上的具体实现，并承担测试、发布和长期维护。

这并不意味着协作模式已经定型。`video` 仍然只是一个开始，但它让能力进入开放生态的过程发生了变化：不再只是在实现完成后开放代码，而开始把需求、标准、实现和验证放进同一个公共循环。

> **社区共同定义标准，Lynx 团队负责实现与长期维护。**

Overlay 让反馈发生在技术栈之间，`video` 则尝试让反馈进一步发生在官方与社区之间。如果你正在构建媒体、输入、浮层、复杂滚动或其他跨平台组件，欢迎更早把真实需求、平台差异和测试用例带到社区讨论中，而不是等实现完成后再讨论 API 是否合适。

这套协作也不应该止步于 ReactLynx。lynx-ui 目前是这套能力链路中的官方组件实现与验证场，但 Lynx Engine 和 XElement 并不绑定某一种前端框架。随着更多 DSL 在 Lynx 上发展，复用的目标不是复制一份 lynx-ui 代码，而是避免每个生态都从平台差异开始重新解决同样的问题。

不同 DSL 可以共享三类基础：

- **可复用的底层实现**：手势竞争、动画驱动、浮层、焦点与键盘等依赖原生或主线程的机制；
- **共同的行为契约与测试**：即使状态管理和组合代码不同，也遵循相同语义并通过同一组跨平台断言；
- **符合各自习惯的轻量封装**：组件组合、上下文和受控状态等 API，由不同 DSL 以最自然的方式表达。

因此，多 DSL 复用的目标不是共享同一份组件代码，而是共享已经被 XElement 实现、被 Element 表达并被测试验证的能力基础；在此之上，每个 DSL 仍然可以拥有符合自身习惯的组件 API 与组合模型。

共同语义也不意味着相同实现，更不意味着应该抹平平台已经形成的交互预期。

当一个能力可以完整遵循 Web 语义时，我们会优先使用 Web 开发者熟悉的 API；当 Web 无法准确表达原生行为时，我们会从各平台的原生交互与用户预期出发，定义一致的 **Semantic Target**。对于无法完全统一的部分，我们倾向于通过渐进增强保留平台能力，并清晰标注兼容性状态和降级行为。

真正需要一致的不是实现细节，而是开发者和用户可以依赖的核心行为：状态如何变化、事件何时发生、能力在哪些平台可用，以及不支持时如何降级。这些承诺需要在 XElement 的多平台实现中得到验证，也需要在 lynx-ui 和其他 DSL 的真实组件组合中接受检验。

Overlay 证明了能力可以在实现与组合之间持续往返，`video` 则让需求、标准、实现与验证开始进入同一个公共循环。当反馈系统从技术栈内部走向开放社区，问题也就从“如何开放更多能力”，转向“如何共同建设一个生态”。

## 从能力开放到生态共建

接下来的 Roadmap 不以组件数量为目标，也不是一份按日期排列的功能清单。它只回答两个问题：已经开放的能力，怎样才能让开发者放心使用？由官方维护的能力，又怎样才能变成整个生态都能复用的基础？

### 让开放能力真正可依赖

代码开放回答了“能不能看到”，生态建设还要回答“能不能长期依赖”。

代码进入仓库只是开始。一个 XElement 要成为真正可依赖的能力，还需要清晰的 Element API、稳定的多平台行为、明确的兼容和降级策略，以及与版本一起维护的文档、示例、测试和迁移路径。对应的 lynx-ui 组件也不能只覆盖最顺利的使用方式；键盘、焦点、手势、无障碍、性能和边界状态，都应该成为完整实现的一部分。

我们会把 XElement 与 lynx-ui 作为同一套能力体系持续维护：前者把经过生产验证的原生能力带入开放环境，后者把这些能力变成前端开发者可以直接使用和组合的入口。真实组件继续检验默认行为，发现的问题再回到 Element 语义和各平台实现中。

衡量这一步是否完成，不是看开源了多少代码，而是看开发者能否回答三个问题：这项能力在哪些平台可用？不支持时会怎样？升级时需要付出什么成本？只有这些答案足够稳定，开放能力才真正变成了可信能力。

### 让一套能力服务整个生态

一项能力进入仓库，不是协作的结束，而是公共讨论的开始。

需求、API 和跨平台行为不应该等实现完成后才被看见。社区可以更早通过 RFC 和 Discussions 参与讨论，共同定义 Element 应该承诺什么、组件应该如何组合、测试应该验证什么；Lynx 团队负责把这些共识变成 Android、iOS 与 HarmonyOS 上的实现，并承担发布和长期维护。

当语义和测试成为公共标准，复用也不再局限于 ReactLynx。不同 DSL 不必共享同一份 lynx-ui 代码，却可以共享 XElement、Element 行为规范和跨平台测试；原生扩展、行业组件和设计系统也可以建立在同一套能力基础上。未来的发现、分发和依赖机制，则让这些成果能够真正流动起来，而不是散落在不同仓库和产品中。

我们希望最终形成的，不只是一个由官方不断增加组件的目录。Lynx 团队维护高质量的核心能力，社区共同定义新的需求、标准和测试，每一次真实使用再继续推动底层实现和上层组件向前演进。

## 从公共基础到 Agent-ready UI

Web 生态的活力从来不只来自浏览器内置了多少控件，更来自稳定的原语、共同的标准、开放的工具，以及任何人都可以在其上继续创造的空间。Lynx 的组件生态也需要这样的基础，同时保留原生渲染、跨平台交付和低延迟交互带来的独特价值。

当这条循环逐渐闭合，一个原生能力或组件就不再只是某个平台、某个框架或某个团队内部的一次性实现。它可以被不同 DSL 表达，被不同设计系统组合，并在多个平台上保持一致的用户语义。跨端原生 UI 也可以从每个团队反复支付的工程成本，转化为整个生态能够共同积累的公共资产。

这套基础首先服务开发者和不同 DSL，也会服务新的界面生产方式。AI 不会消除组件实现，却会降低生成代码的成本，同时放大稳定语义、组合规则和验证体系的价值。方向不是让 Agent 多写几段 TSX，而是让它在一套经过验证的 UI 词汇中表达意图，再把这种表达变成可信的跨端体验。

> **Agent-ready UI = Constrained Expression × Trusted Semantics × Executable Evaluation**

这不是另一套架构，而是同一套公共基础多了一个消费者。Lynx Engine 负责执行，XElement 吸收平台、线程和版本差异，Element 提供稳定的 API 与行为，lynx-ui 和其他 DSL 组件库提供可组合的交互词汇，LUNA 则作为视觉语义的参考实现。这样，Agent 面对的就不再是平台私有参数和无限开放的代码空间，而是一套有明确边界、可以被验证的 UI 语言。

> **XElement 让原生能力稳定可用，lynx-ui 让这些能力可以被组合，最终的产品形态仍然由开发者决定。**

[OpenUI](https://lynxjs.org/next/react/genui/openui.html) 已经展示了一种可能：Agent 不直接面对无限开放的代码空间，而是在受控组件词汇中生成表达式，再由可信 Renderer 映射为真实界面。[lynx-ui Skills](https://lynxjs.org/4.0/ui/introduction.html) 是另一个起点。下一步，Component Manifest 可以让组件实现、类型、文档、组合约束、兼容信息和测试来自同一个事实源，并进一步驱动 Skills、OpenUI Catalog 和生成结果的评测。

对 Agent 来说，一个组件的价值不再只是源码，还包括可理解的契约、明确的使用边界和可以执行的测试。我们也会用一次编译通过率、跨端运行结果、视觉与交互通过率，以及需要多少人工修改，来判断这套基础是否真的可信。

如果你正在维护跨端组件、设计系统或新的 DSL，或者正在探索生成式 UI，请告诉我们：哪些平台差异正在重复消耗工程成本，哪些行为应该成为公共标准，哪些测试可以让所有实现共同受益。

我们尤其希望与社区一起回答三个问题：

1. Element 应该承诺怎样的跨平台语义，XElement 又应该如何验证这些语义？
2. 组件 API 与组合模型应该如何反映和推动底层能力？
3. 测试、工具和贡献基础设施应该如何开放，才能让能力被更多 DSL、社区组件和新的 UI 工具复用？

欢迎前往 [Lynx GitHub Discussions](https://github.com/lynx-family/lynx/discussions) 发起或参与讨论，也可以在 [Discord](https://discord.com/invite/mXk7jqdDXk) 与我们交流，并通过 [X](https://x.com/lynxjs_org) 关注最新进展。GitHub Discussions 将作为提案、标准讨论与后续决策记录的主要入口。

Lynx 下一阶段要开放的，不只是一批经过验证的实现，而是能力从需求、标准、原生实现到组件组合的完整过程。我们希望与社区一起建立的，也不只是更多组件，而是一套任何 DSL、产品和工具都可以继续使用、验证和扩展的跨端 UI 公共基础。
