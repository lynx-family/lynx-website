# Snapshot 编译优化

Snapshot 首先是一项**编译优化**。ReactLynx 编译器会提前分析 JSX，把能够确定的元件结构转换为直接创建 Lynx 元件的代码，并为动态属性和子节点生成专门的更新逻辑。运行时只需要实例化编译结果并传入动态值，不必重新解释完整的 JSX 结构。

:::info

这里的 Snapshot 不是测试框架中的“快照测试”，也不是 React 类组件的 `getSnapshotBeforeUpdate()`。它是 ReactLynx 的内部实现，应用代码只需照常编写 JSX，不需要直接创建或操作 Snapshot。

:::

## 为什么需要 Snapshot

### 常规 JSX 的运行时开销

常规 JSX 产物会把元件结构、静态值和动态表达式保留在运行时。每次创建或更新 UI 时，运行时需要生成元素描述、逐层调和宿主元件，并将属性和子节点的变化落实到 UI。

以下组件同时包含静态结构和动态内容：

```tsx
export function Greeting({ name, highlighted }) {
  return (
    <view className={highlighted ? 'card active' : 'card'}>
      <text>Hello, {name}</text>
    </view>
  );
}
```

如果只进行常规 JSX 转换、不提取 Snapshot，上述组件的编译结果在语义上类似：

```js
export function Greeting({ name, highlighted }) {
  return _jsx('view', {
    className: highlighted ? 'card active' : 'card',
    children: _jsx('text', {
      children: ['Hello, ', name],
    }),
  });
}
```

这段产物仍然保留完整的 `view` 和 `text` 元件层级。每次渲染都会重新生成这棵元素描述，运行时需要依据完整层级进行调和。当页面规模较大时，逐层调和的耗时会更加明显，元素描述和节点状态占用的内存也会随之增加。

ReactLynx 编译器可以提前完成其中不依赖运行时数据的工作：

- 确定内置元件的类型、层级和插入顺序。
- 提取固定文本、静态属性和 CSS 作用域等信息。
- 找出动态属性、展开属性和动态子节点的位置。
- 为每个动态部分生成有针对性的更新函数。

这些编译结果共同组成 Snapshot 定义。

### JSX 编译为 Snapshot

对于上述 `Greeting`，ReactLynx 编译器则会在构建时将它拆分为：

- **静态结构**：`view`、`text` 和固定文本 `Hello, `。
- **动态属性**：由 `highlighted` 决定的 `className`。
- **动态子节点**：由 `name` 生成的文本。

最后，编译器会把静态创建逻辑、动态更新函数和插槽位置组合成一个可复用的 Snapshot 定义，并为它生成 Snapshot ID。运行时通过这份定义创建 Snapshot 实例，只需传入每个实例自己的动态值和子节点。

具体来说，一个 Snapshot 定义包含以下四部分：

| 编译结果       | 作用                                                             |
| -------------- | ---------------------------------------------------------------- |
| 静态创建函数   | 直接创建确定的 Lynx 元件，并建立父子关系。                       |
| 动态更新函数   | 按索引更新某个属性、事件或展开属性，不需要重新遍历整段静态结构。 |
| 动态子节点插槽 | 标记组件、条件分支、文本表达式和列表等动态子树应该插入的位置。   |
| Snapshot ID    | 标识这份编译后的结构，让多个组件实例复用同一个 Snapshot 定义。   |

使用当前版本的 ReactLynx 编译器转换上述组件，会得到类似下面的代码：

```js
const __snapshot_a721c_e4779_1 = '__snapshot_a721c_e4779_1';

ReactLynx.snapshotCreatorMap[__snapshot_a721c_e4779_1] = (
  __snapshot_a721c_e4779_1,
) =>
  ReactLynx.createSnapshot(
    __snapshot_a721c_e4779_1,
    () => {
      const pageId = ReactLynx.__pageId;
      const view = __CreateView(pageId);
      const text = __CreateText(pageId);
      const rawText = __CreateRawText('Hello, ');
      const slot = __CreateWrapperElement(pageId);

      __AppendElement(view, text);
      __AppendElement(text, rawText);
      __AppendElement(text, slot);

      return [view, text, rawText, slot];
    },
    [
      function (ctx) {
        if (ctx.__elements) {
          __SetClasses(ctx.__elements[0], ctx.__values[0] || '');
        }
      },
    ],
    [[ReactLynx.__DynamicPartSlotV2, 3]],
  );

export function Greeting({ name, highlighted }) {
  return _jsx(__snapshot_a721c_e4779_1, {
    values: [highlighted ? 'card active' : 'card'],
    $0: name,
  });
}
```

:::warning

`createSnapshot`、`snapshotCreatorMap`、全局元件操作函数和生成的 Snapshot ID 都是内部实现。具体名称和参数可能随源码、编译配置及 ReactLynx 版本变化，请勿在应用代码中依赖或复制这些产物。

:::

基于这样的编译优化，原本需要逐层参与调和的多层宿主结构会被压缩为一层 Snapshot 单元。页面越复杂、可静态确定的结构越多，这种压缩带来的调和规模缩减越明显。这里压缩的是运行时调和层级，Snapshot 仍会在主线程创建完整的 Lynx 元件树。

### Snapshot 如何驱动渲染

Snapshot 定义是编译器生成的可复用描述，SnapshotInstance 则是这份定义在运行时的一次实例化。在 ReactLynx 的双线程架构中，同一个逻辑 Snapshot 在两条线程上有各自的运行时对象：

| 所在线程 | 运行时对象                   | 职责                                                                                                                                   |
| -------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 后台线程 | `BackgroundSnapshotInstance` | 作为 Preact 调和到宿主层时的节点，保存 Snapshot ID、动态值和子节点关系；比较动态值，并记录创建、插入、删除和属性更新等可序列化 Patch。 |
| 主线程   | `SnapshotInstance`           | 在首屏渲染或接收后续 Patch 时，根据 Snapshot 定义创建并持有真实的 Lynx FiberElement；执行定向更新函数，并把动态子节点插入对应的插槽。  |

后台线程提交更新时，会将实例 ID、操作类型和必要的动态数据发送到主线程。主线程根据实例 ID 找到对应的 `SnapshotInstance` 并应用操作。因此，两侧对象代表同一个逻辑 UI 单元，但它们不是同一个 JavaScript 对象，也不通过共享内存直接访问彼此。

这种双线程分工让调和与元件操作都以 Snapshot 为单位。编译后的 `_jsx(snapshotId, props)` 不再向运行时展开完整的宿主元件层级。后台线程进行 React 调和时，整段已编译结构对应一个 `BackgroundSnapshotInstance`；主线程中与之对应的 `SnapshotInstance` 再执行静态创建函数，将它展开为真实的 FiberElement。

以上面的 `Greeting` 为例，主线程的 `SnapshotInstance` 内部包含 `view`、`text`、固定文本和插槽对应的 FiberElement。但是在后台线程的调和树中，可静态确定的 `view → text → Hello, ` 不再需要逐个作为宿主节点处理，而是由一个 `BackgroundSnapshotInstance` 代表；只有 `$0` 对应的 `name` 继续作为动态子节点参与调和。

| 场景                   | 逐个处理宿主元件时                               | 编译成 Snapshot 后                                                                                   |
| ---------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 创建 UI                | 逐层调和 `view`、`text`、文本及其父子关系。      | 后台线程调和一个 `BackgroundSnapshotInstance`，主线程由对应的 `SnapshotInstance` 创建 FiberElement。 |
| `highlighted` 发生变化 | 再次确定动态值对应哪个元件和属性。               | 后台线程比较 `values[0]` 并生成 Patch，主线程直接更新根 FiberElement 的 `className`。                |
| `name` 发生变化        | 固定文本和动态文本组成的宿主子树都在处理范围内。 | 固定文本保留在主线程实例内部，只有 `$0` 对应的动态插槽继续参与调和并生成子节点 Patch。               |
| 渲染多个相同组件       | 每个实例都需要携带并处理相同的宿主元件结构。     | 每个逻辑实例只对应一对轻量实例对象，多个实例共享同一个 Snapshot 定义。                               |

最直接的变化是：运行时不再需要理解这段 JSX 应该如何创建和更新，而是围绕 Snapshot 实例执行编译器已经准备好的操作。原本由多个静态宿主节点形成的调和层级，在后台线程中被折叠为一个 `BackgroundSnapshotInstance`；主线程对应的 `SnapshotInstance` 只负责将编译结果落实为 FiberElement。调和范围因此缩小到 Snapshot 实例及其动态插槽。

:::note

这里缩小的是宿主元件层面的调和规模，并不是绕过 React 调和。组件、条件分支、列表和动态子节点仍然正常参与调和；Snapshot 只折叠编译器能够静态确定的宿主元件结构。

:::

## 如何编写编译友好的 JSX

Snapshot 优化由编译器自动完成，不需要手动开启。编写 JSX 时，关键是让宿主元件的类型、层级和插入顺序在源码中清晰可见，并把运行时数据集中在属性和子节点表达式中。编译器就能将前者提取为静态骨架，将后者转换为定向更新函数或动态插槽。

### 动态值不会阻止静态结构提取

以下组件的 `view → text` 层级始终不变，变化的只有 `className` 和文本内容：

```tsx
function UserCard({ name, selected }) {
  return (
    <view className={selected ? 'user-card selected' : 'user-card'}>
      <text className="user-name">{name}</text>
    </view>
  );
}
```

编译器可以将这段 JSX 拆分为：

- **静态结构**：`view`、`text` 及二者的父子关系。
- **静态属性**：`text` 上的 `user-name`。
- **动态位置**：卡片的 `className` 和由 `name` 生成的文本子节点。

因此，不必为不同的 `name` 或 `selected` 组合编写不同组件。保留稳定的宿主结构，让数据通过表达式进入即可。

### 将共享结构放在条件分支外

下面的写法在两个分支中重复了整个卡片结构：

```tsx
function ProductCard({ name, price, showPrice }) {
  if (showPrice) {
    return (
      <view className="product-card">
        <text className="product-name">{name}</text>
        <text className="product-price">{price}</text>
      </view>
    );
  }

  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
    </view>
  );
}
```

可以只保留一份稳定外壳，将价格区域作为动态插槽：

```tsx
function ProductCard({ name, price, showPrice }) {
  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
      {showPrice && <text className="product-price">{price}</text>}
    </view>
  );
}
```

`showPrice` 变化时，React 只需要调和价格对应的动态区域，卡片外壳可以继续复用。如果两个分支的界面本来就完全不同，则无需强行合并，保持分支清晰更重要。

### 显式声明宿主类型

Snapshot 编译器分析的是 JSX 结构。通过字符串和 `createElement()` 在运行时决定宿主类型时，编译器无法提前确定这部分结构：

```tsx
import { createElement } from '@lynx-js/react';

function DynamicNode({ type, value }) {
  return createElement(type, { className: 'content' }, value);
}
```

如果候选结构在开发时已经确定，直接写出 JSX 分支：

```tsx
function Content({ variant, value }) {
  if (variant === 'label') {
    return <text className="content-label">{value}</text>;
  }

  return (
    <view className="content-panel">
      <text>{value}</text>
    </view>
  );
}
```

两个分支仍然由运行时数据选择，但每个分支的宿主结构都对编译器可见，可以分别生成 Snapshot。只有宿主类型确实来自运行时配置时，才需要使用动态创建方式。

### 属性集合固定时优先显式声明

spread 属性受 Snapshot 支持，但编译器会将整个展开对象记录为一个动态属性集合。更新时，运行时需要比较集合中的属性，再将变化应用到对应元件：

```tsx
function UserCard({ id, name, selected }) {
  const cardProps = {
    id,
    className: selected ? 'user-card selected' : 'user-card',
  };

  return (
    <view {...cardProps}>
      <text>{name}</text>
    </view>
  );
}
```

当属性集合在开发时已经确定，显式声明属性更优：

```tsx
function UserCard({ id, name, selected }) {
  return (
    <view id={id} className={selected ? 'user-card selected' : 'user-card'}>
      <text>{name}</text>
    </view>
  );
}
```

显式写法让编译器直接知道 `id` 和 `className` 分别对应哪个动态位置，可以为每个属性生成定向更新逻辑；它也避免了每次渲染都创建 `cardProps` 对象。组件需要透传调用方提供的未知属性时，spread 仍然是合适的写法，不必为了 Snapshot 强行逐项展开。
