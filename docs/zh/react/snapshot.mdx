# Snapshot 编译优化

一个 UI 组件里，大部分结构在源码中就已经固定，每次渲染真正会变的往往只是少数属性和文本。ReactLynx 的 **Snapshot 编译优化**利用了这一点：编译器在构建时提取 JSX 中能够静态确定的元件结构，并为动态部分生成专门的表示。这样，可静态确定的宿主元件不必在每次渲染时逐层进入协调过程，运行时只需实例化编译结果并处理动态位置。

:::info

这里的 Snapshot 不是测试框架中的“快照测试”，也不是 React 类组件的 `getSnapshotBeforeUpdate()`。它是 ReactLynx 的内部实现，应用代码只需照常编写 JSX，不需要直接创建或操作 Snapshot。

:::

## 为什么需要 Snapshot

常规 JSX 产物会把元件结构、静态值和动态表达式都保留在运行时代码中。每次渲染时，`_jsx()` 会创建描述 UI 结构的虚拟节点（VNode），ReactLynx 的协调器再沿着这些节点逐层比较，决定复用、创建或更新哪些宿主元件。这个过程通常称为协调（Reconciliation）。

以下组件同时包含静态结构和动态内容：

```tsx
export function Greeting({ name, highlighted }) {
  return (
    <view className={highlighted ? 'card active' : 'card'}>
      <text>Hello, {name}</text>
    </view>
  );
}
```

如果只进行常规 JSX 转换、不提取 Snapshot，上述组件的编译结果在语义上类似：

```js
export function Greeting({ name, highlighted }) {
  // view 和 text 仍然分别对应一个宿主 VNode。
  return _jsx('view', {
    className: highlighted ? 'card active' : 'card',
    children: _jsx('text', {
      children: ['Hello, ', name],
    }),
  });
}
```

这段产物仍以 `view` 和 `text` VNode 表达完整的宿主层级。即使协调器最终复用了对应的宿主元件，每次渲染仍会重新创建这些 VNode，并让完整的 `view → text` 层级参与协调。这里真正会变化的只有 `className` 和 `name`，元件类型、层级和父子关系始终不变。

这些稳定不变的结构，正是编译器可以提前提取的部分。

### JSX 如何编译为 Snapshot

启用 Snapshot 提取后，同一组件的调用部分在语义上则类似：

```js
const __snapshot_xxx = '__snapshot_xxx';

export function Greeting({ name, highlighted }) {
  // 静态宿主层级被折叠为一个 Snapshot 类型。
  return _jsx(__snapshot_xxx, {
    values: [highlighted ? 'card active' : 'card'], // 动态属性位置 0
    $0: name, // 动态子节点插槽 0
  });
}
```

两份产物的差别在于：常规产物直接展开完整的宿主 VNode 层级；Snapshot 产物只引用一个 Snapshot ID，并将 `className` 和 `name` 分别传入预先确定的动态位置。

编译器由此可以提前确定内置元件的类型、层级和插入顺序，提取固定文本、静态属性和 CSS 作用域，并找出动态属性、展开属性和动态子节点的位置。对于上述 `Greeting`，具体可以拆分为：

- **静态结构**：`view`、`text` 和固定文本 `Hello, `。
- **动态属性**：由 `highlighted` 决定的 `className`。
- **动态子节点**：由 `name` 生成的文本。

最后，编译器把静态创建逻辑、动态更新函数、插槽位置和一个 Snapshot ID 组合成可复用的 Snapshot 定义。运行时通过这份定义创建 Snapshot 实例，只需传入每个实例自己的动态值和子节点。

### Snapshot 定义包含什么

从编译模型来看，一个 Snapshot 定义可以归纳为以下四个核心部分：

| 编译结果       | 作用                                                             |
| -------------- | ---------------------------------------------------------------- |
| 静态创建函数   | 直接创建确定的 Lynx 元件，并建立父子关系。                       |
| 动态更新函数   | 按索引更新某个属性、事件或展开属性，不需要重新遍历整段静态结构。 |
| 动态子节点插槽 | 标记组件、条件分支、文本表达式和列表等动态子树应该插入的位置。   |
| Snapshot ID    | 标识这份编译后的结构，让多个组件实例复用同一个 Snapshot 定义。   |

上面的 Snapshot ID 对应一份构建时生成的 Snapshot 定义。为突出其编译结构，下面给出一份简化示意，其中保留了静态创建函数、动态更新函数和插槽，省略了 CSS、entry 和兼容性等编译元数据：

```js
ReactLynx.snapshotCreatorMap[__snapshot_xxx] = (__snapshot_xxx) =>
  ReactLynx.createSnapshot(
    __snapshot_xxx,
    () => {
      // 这部分只依赖 JSX 中可以静态确定的结构。
      const pageId = ReactLynx.__pageId;
      const view = __CreateView(pageId);
      const text = __CreateText(pageId);
      const rawText = __CreateRawText('Hello, ');
      const slot = __CreateWrapperElement(pageId); // 为 $0 预留插入位置

      __AppendElement(view, text);
      __AppendElement(text, rawText);
      __AppendElement(text, slot);

      // 更新函数和插槽描述通过这些数组索引定位元件。
      return [view, text, rawText, slot];
    },
    [
      function (ctx) {
        if (ctx.__elements) {
          // values[0] 只更新 elements[0]，也就是根 view。
          __SetClasses(ctx.__elements[0], ctx.__values[0] || '');
        }
      },
    ],
    [[ReactLynx.__DynamicPartSlotV2, 3]], // $0 对应 elements[3]
  );
```

:::warning

`createSnapshot`、`snapshotCreatorMap`、全局元件操作函数和生成的 Snapshot ID 都是内部实现。具体名称和参数可能随源码、编译配置及 ReactLynx 版本变化，请勿在应用代码中依赖或复制这些产物。

:::

### 编译产物如何进入运行时

编译生成的 Snapshot 定义可以被多个 `Greeting` 复用，而每次实际渲染都会产生一组彼此对应的运行时实例：主线程实例持有创建出的 Lynx 元件，后台实例保存参与协调的逻辑树和动态数据。运行时消费编译产物的过程可以分为首屏创建和后续更新两个阶段。

#### 首屏：根据定义创建实例

首屏的 UI 元件由主线程直接创建。运行时先根据 VNode 的类型找到 Snapshot 定义，再为这次 `Greeting` 创建主线程实例。静态创建函数返回的 Lynx 元件由这个实例持有；初始动态值随后交给对应的更新函数，动态子节点则插入定义中的插槽。

下面是这一过程的概念伪代码：

```js
function renderFirstScreen(vnode) {
  const definition = getSnapshotDefinition(vnode.type);
  const instance = createMainThreadSnapshotInstance(vnode.type);

  instance.elements = definition.create(instance);
  instance.values = vnode.props.values;
  definition.update[0](instance); // 将 values[0] 写入 className
  insertDynamicChild(instance, 0, vnode.props.$0);

  return instance;
}
```

对于当前例子，`definition.create()` 创建 `view`、`text` 和固定文本；`definition.update[0]()` 将 `values[0]` 写入 `className`；`insertDynamicChild()` 则把 `$0` 对应的 `name` 放进预留插槽。这里仍会创建完整的 Lynx 元件树；差别在于静态层级由 `definition.create()` 直接展开，不再通过每个宿主 VNode 逐层协调。

后台首轮协调也会生成与主线程实例树对应的逻辑实例树。首屏同步通过 hydration 建立两侧实例的对应关系，使后续更新可以用 `instanceId` 定位首屏时创建的主线程实例。

#### 更新：根据实例对应关系应用变化

对应关系建立后，后台线程比较新旧动态值并生成更新，主线程再找到实际实例并应用它。

下面的伪代码继续使用 `Greeting`。`highlighted` 对应动态位置 `0`，因此它变化时会生成一条属性更新；`name` 位于动态子节点插槽中，继续由 React 协调：

```js
// 后台线程：比较动态属性，并继续协调动态子节点
function reconcileGreeting(previous, next, instanceId) {
  if (!isEqual(previous.values[0], next.values[0])) {
    emitAttributePatch({
      instanceId,
      dynamicPartIndex: 0,
      value: next.values[0],
    });
  }

  // $0 仍作为 React 子节点参与协调，结果会变成插入、移除等树操作。
  reconcileChildren(previous.$0, next.$0, {
    parentInstanceId: instanceId,
    slotIndex: 0,
  });
}

// 主线程根据实例和动态位置应用属性更新
function applyAttributePatch(patch) {
  const instance = findSnapshotInstance(patch.instanceId);
  const index = patch.dynamicPartIndex;

  instance.values[index] = patch.value;
  instance.definition.update[index](instance);
}
```

对于属性路径，`reconcileGreeting()` 只生成“哪个实例的哪个动态位置发生了变化”的描述，`applyAttributePatch()` 则找到主线程实例并调用编译器生成的更新函数。动态子节点不经过这组属性更新函数，而是由 React 协调后产生相应的树操作。实际实现会将这些操作编码进序列化的 Snapshot Patch。

## 如何编写编译友好的 JSX

使用默认 Snapshot 编译后端时，优化由编译器自动完成。编译器能提取多少静态结构，取决于宿主元件的类型、层级和插入顺序在源码中是否清晰可见。下面几种写法有助于暴露稳定的宿主结构，但它们不是硬性规则：组件语义和可读性始终优先。

### 放心让动态值进入稳定结构

前面的 `Greeting` 中，`className` 和 `name` 都来自运行时，但 `view → text` 的宿主层级仍然直接出现在源码中。编译器因此可以提取这段骨架，只把两个表达式记录为动态位置。

动态值本身不会阻止 Snapshot 提取。只要宿主类型、层级和顺序保持稳定，就可以让数据自然地通过属性或动态子节点进入，不必为了把属性或文本写成静态值而拆分组件。

### 将共享结构放在条件分支外

下面的写法在两个分支中重复了整个卡片结构：

```tsx
function ProductCard({ name, price, showPrice }) {
  if (showPrice) {
    return (
      <view className="product-card">
        <text className="product-name">{name}</text>
        <text className="product-price">{price}</text>
      </view>
    );
  }

  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
    </view>
  );
}
```

可以只保留一份稳定外壳，将价格区域作为动态插槽：

```tsx
function ProductCard({ name, price, showPrice }) {
  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
      {/* 只有价格区域会随 showPrice 改变结构。 */}
      {showPrice && <text className="product-price">{price}</text>}
    </view>
  );
}
```

当两个分支本来就表示同一种卡片结构时，后一种写法能让共享外壳直接暴露给编译器，并把价格区域保留为动态插槽。`showPrice` 变化时，运行时只需处理这个动态区域。如果移动结构会改变组件身份、状态保留或其他行为，就不应为了 Snapshot 强行合并分支。

### 显式声明宿主类型

编译器只能分析它在源码里看得见的 JSX 结构。如果你用字符串加 `createElement()` 在运行时才决定宿主类型，这部分结构就无法提前确定，也就无法提取成 Snapshot：

```tsx
import { createElement } from '@lynx-js/react';

function DynamicNode({ type, value }) {
  // type 直到运行时才有具体值，编译器看不到宿主类型。
  return createElement(type, { className: 'content' }, value);
}
```

如果候选结构在开发时已经确定，直接写出 JSX 分支：

```tsx
function Content({ variant, value }) {
  // 两种候选宿主类型都直接出现在 JSX 中。
  if (variant === 'label') {
    return <text className="content-label">{value}</text>;
  }

  return (
    <view className="content-panel">
      <text>{value}</text>
    </view>
  );
}
```

两个分支仍然由运行时数据选择，但每个分支的宿主结构都对编译器可见，可以分别生成 Snapshot。只有宿主类型确实来自运行时配置时，才需要使用动态创建方式。

### 属性集合固定时优先显式声明

spread 属性同样受 Snapshot 支持。编译器知道展开对象作用于哪个元件，但由于属性集合要到运行时才能确定，只能把整个对象记录为一个动态位置。更新时，运行时需要遍历新旧对象的属性，再把变化应用到目标元件：

```tsx
function UserCard({ id, name, selected }) {
  // spread 会让整个属性集合成为一个动态位置。
  const cardProps = {
    id,
    className: selected ? 'user-card selected' : 'user-card',
  };

  return (
    <view {...cardProps}>
      <text>{name}</text>
    </view>
  );
}
```

当属性集合在开发时已经确定，显式声明属性更优：

```tsx
function UserCard({ id, name, selected }) {
  // 每个动态属性都能获得独立的位置和更新函数。
  return (
    <view id={id} className={selected ? 'user-card selected' : 'user-card'}>
      <text>{name}</text>
    </view>
  );
}
```

显式写法让编译器直接知道 `id` 和 `className` 分别对应哪个动态位置，可以为每个属性生成独立的定向更新逻辑；它也避免了每次渲染都创建 `cardProps` 对象。组件需要透传调用方提供的未知属性时，spread 仍然是合适的写法，不必为了 Snapshot 强行逐项展开。

判断 JSX 是否适合静态提取时，可以记住一个原则：让确定的宿主类型、层级和顺序直接出现在源码中，让真正的运行时数据通过属性或动态子节点进入。对于本来就需要在运行时决定的结构，保持动态写法比迎合编译器更重要。
