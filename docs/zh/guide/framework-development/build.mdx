# 构建产物

运行时决定了主线程如何驱动 UI、后台线程分担什么。
构建阶段要做的事只有一件：把这些代码变成宿主能加载的一个文件——`.lynx.bundle`。

本文从最简单的形态讲起：**两个入口文件**。

## 从两个入口文件开始

先不谈任何 Lynx 特有的概念。假设你的框架为一个页面生成了两个文件：

```text
src/counter/
├── main-thread.ts   运行在主线程，调用 Element PAPI 画界面
├── background.ts    运行在后台线程，管状态和异步逻辑
└── style.css        样式
```

它们是两个**互不相同的文件**，各自作为一个 entry 被打包。到这一步为止，和普通的前端构建没有区别：两个 entry，编译出两份 JavaScript。

真正 Lynx 特有的问题是下一步：**这两份 JavaScript 怎么变成一个 `.lynx.bundle`？**

Bundle 不是把两份 JS 和 CSS 拼接到一个文件里，而是一种二进制模板格式，内部有若干个区段，每个区段有明确的角色。所以打包工具必须先说清楚“哪份代码是主线程的、哪份是后台线程的”，再交给编码器。

<Mermaid>{`
flowchart LR
  MT["main-thread.ts"] --> MainJs[".rspeedy/counter/main-thread.js"]
  BG["background.ts"] --> BgJs[".rspeedy/counter/background.js"]
  CSS["style.css"] --> CSSRule["CSS 规则"]
  MainJs --> Encode["编码输入<br/>（tasm.json）"]
  BgJs --> Encode
  CSSRule --> Encode
  Encode --> Bundle["counter.bundle"]
`}</Mermaid>

## 标明哪一份是主线程

构建产物里的资产默认都长得一样——都是 JavaScript 文件。打包工具通过给资产打标记来区分线程角色：

```ts
compilation.updateAsset(asset.name, asset.source, {
  ...asset.info,
  'lynx:main-thread': true,
});
```

带 `lynx:main-thread` 标记的资产会被归入主线程区段，其余 JavaScript 资产归入后台线程区段。这是默认的分组规则，[ReactLynx 的构建插件](https://github.com/lynx-family/lynx-stack/blob/main/packages/webpack/react-webpack-plugin/src/ReactWebpackPlugin.ts)就是这么做的。

如果你的入口是手工搭的、没有打这个标记，也可以在编码前的钩子里直接指定各区段的内容——下面会看到。

后台线程的 chunk 还需要经过 `RuntimeWrapperWebpackPlugin` 包装。它在代码外面套一层函数，宿主按这个约定加载后台脚本，并把 `tt`、`console`、`setTimeout`、`NativeModules`、`lynx` 等对象作为模块级变量注入进去——Lynx 不使用 CommonJS，这些绑定只能由加载方在包装层提供。主线程代码不走这条加载路径，所以不需要包装。

## 编码输入：`tasm.json`

分好组之后，打包工具把所有资产整理成一个结构化对象，这就是编码器的输入：

| 字段              | 内容                                                 |
| ----------------- | ---------------------------------------------------- |
| `lepusCode`       | **主线程**代码。`{ root, chunks, filename }`         |
| `manifest`        | **后台线程**代码。`{ 文件名: 文件内容 }`             |
| `css`             | 样式规则映射和内容                                   |
| `compilerOptions` | `targetSdkVersion`、`enableCSSSelector` 等编译开关   |
| `sourceContent`   | `{ dsl, appType, config }`，其中 `config` 是页面配置 |
| `customSections`  | 延迟加载组件、字节码等扩展数据，不需要时为空         |

:::info 字段名容易看反
`lepusCode` 放的是**主线程**代码，`manifest` 放的是**后台线程**代码。这两个字段名都是历史遗留，从字面上看不出对应关系，填错了不会报错，只会得到一个跑不起来的产物。
:::

这个对象在开发构建时会原样写到磁盘上，就是 `.rspeedy/<入口名>/tasm.json`：

```bash
# 生产构建默认不产出 tasm.json，用 DEBUG 打开
DEBUG=rspeedy:template rspeedy build
```

它不是构建的中间缓存，而是**编码器实际收到的参数本身**（`JSON.stringify` 出来的）。产物不对劲时，先看这个文件：主线程代码是不是进了 `lepusCode`、后台代码是不是进了 `manifest`、样式在不在，一目了然。

## 编码为 Bundle

最后一步由 [`@lynx-js/tasm`](https://www.npmjs.com/package/@lynx-js/tasm) 完成——它是真正的编码器，把上面的结构化数据写成 Lynx 模板二进制，同时产出调试信息和样式诊断。

在构建流程里，这两件事由 `@lynx-js/template-webpack-plugin` 的两个插件配合完成，**它们需要一起使用**：

| 插件                 | 职责                                                         |
| -------------------- | ------------------------------------------------------------ |
| `LynxTemplatePlugin` | 按入口收集资产、分组、组装出上面那个对象，并暴露编码前的钩子 |
| `LynxEncodePlugin`   | 接住编码请求，在 worker 里调用 `@lynx-js/tasm` 完成编码      |

只挂前者不会产出 Bundle——没有人执行编码；只挂后者则没有输入。

<Mermaid>{`
flowchart LR
  Assets["分好组的资产"] --> Template["LynxTemplatePlugin<br/>组装 encodeOptions"]
  Template --> Json[".rspeedy/counter/tasm.json<br/>（dev / DEBUG 时落盘）"]:::flow-label
  Template --> EncodePlugin["LynxEncodePlugin"]
  EncodePlugin --> Tasm["@lynx-js/tasm"]
  Tasm --> Bundle["counter.bundle"]
`}</Mermaid>

一个可以直接运行的完整实现，见 lynx-examples 里的 [vanilla 示例](https://github.com/lynx-family/lynx-examples/tree/main/examples/vanilla)：它的 `plugin.ts` 把上面这些步骤写成了一个 Rsbuild 插件——按入口找到 `main-thread.ts` 和兄弟 `background.ts`、挂上两个插件、并在 `beforeEncode` 钩子里把两个 chunk 分别放进 `lepusCode` 和 `manifest`。如果你的框架有自己的打包工具，也可以不用这两个插件，只要最终交给 `@lynx-js/tasm` 的数据结构是对的。

## 当两个线程共用一份源码

到这里为止，主线程和后台线程一直是**两个不同的文件**。这对于理解产物结构足够了，但大多数框架并不这么写。

以 ReactLynx 为例，开发者写的是一个组件文件，同一份源码要**同时**编译进两个线程——主线程产物里保留渲染部分、剥掉事件处理和 Effect，后台产物里则相反。这时两个 entry 指向同一个文件，仅靠文件路径已经无法区分该用哪套转换规则。

解决办法是给 entry 打上 [`layer`](https://rspack.rs/zh/config/entry#entrydescriptionlayer)：

```ts
chain.entry('counter__main-thread').add({
  import: ['./src/counter/index.tsx'],
  layer: 'framework:main-thread',
});
chain.entry('counter__background').add({
  import: ['./src/counter/index.tsx'],
  layer: 'framework:background',
});
```

`layer` 是构建期的编译上下文，不代表额外创建了运行时线程。它会沿模块图传递，loader 规则通过 [`rules[].issuerLayer`](https://rspack.rs/zh/config/module-rules#rulesissuerlayer) 匹配“是谁引入了这个模块”，从而选择对应的转换流程——于是同一个文件在两个 layer 中可以走两套完全不同的编译。这两个配置项都来自 Rspack，并非 Lynx 特有。

ReactLynx 正是这样实现的，具体可以参考 [`@lynx-js/react-rsbuild-plugin` 的入口处理](https://github.com/lynx-family/lynx-stack/blob/main/packages/rspeedy/plugin-react/src/entry.ts)。

需要注意的是，`layer` 解决的只是**编译**问题。资产分组、`tasm.json` 组装和编码这几步和前面完全一样：无论源码怎么组织，最终都要落到“哪份代码是主线程、哪份是后台线程”这一个契约上。
