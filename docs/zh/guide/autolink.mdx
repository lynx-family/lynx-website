# 原生库与 Autolink

Lynx 原生库是一个 npm 包，可以打包元件、原生模块和 Service 中的任意组合，供宿主 Lynx 应用消费。在此之前，这些能力只能在每个宿主应用里各接一次，Android、iOS 和 HarmonyOS 还要分别写一遍。Autolink 是配套的集成机制，让宿主应用自动发现 `node_modules` 中安装的库，并接入它们的原生能力，避免为每个元件、原生模块或 Service 手动写注册代码。

Autolink 在 Android 和 iOS 上提供应用级全局注册。HarmonyOS 接入方式已在下文说明，但尚未包含在正式发布的 Lynx SDK 中。Autolink 也覆盖 Lynxtron 原生库使用的包元数据和宿主加载，但不会生成单个 `LynxView` 的局部 Library 注册或 Web 接入代码。

本页分为两部分：要在应用里用上一个已有的库，从[使用库](#使用库)开始；要把自己的原生能力发布成库，从[开发库](#开发库)开始。想先建立整体印象，可以直接看 [Autolink 工作原理](#autolink-工作原理)。

:::info 开始前的准备

✅ 已完成[接入现有应用](/guide/start/integrate-with-existing-apps)

✅ 了解[原生模块](/guide/use-native-modules)和[自定义元件](/guide/custom-native-component)

:::

:::note 工具可用性

请使用与应用 Lynx SDK 同一发布渠道的 Autolink 工具。相关 package 和 plugin 名称如下：

- npm：`create-lynx-library` 和 `@lynx-js/autolink-codegen`（`lynx-autolink-codegen` binary）
- Android：Gradle plugin `org.lynxsdk.lynx.library-settings` 和 `org.lynxsdk.lynx.library-build`
- iOS：Ruby gem `cocoapods-lynx-library`
- HarmonyOS：Hvigor plugin `@lynx-js/lynx-library-plugin`
- Lynxtron：`create-lynx-library` 可以生成 shared native library 包，`@lynx-js/lynxtron-dev-plugins` 通过 `pluginLynxtron()` 提供宿主侧加载能力。

如果当前配置的 registry 还无法解析其中某个包，说明你使用的 Lynx SDK 发布版本尚未在该 registry 中包含 Native Autolink。此时请继续使用既有手动原生注册方式，等待匹配版本发布后再接入。

:::

## 什么是 Lynx 原生库

一个库就是一个 npm 包，可以包含以下能力的任意组合：

- **元件**：Lynx 渲染的自定义原生元件，例如 `<x-button>`。
- **原生模块**：可以在 Lynx 应用代码中调用的、带类型声明的 JavaScript-to-native API。
- **Service**：应用级的原生单例，可以被库内的其他能力依赖。

每个库都通过包根目录下的 `lynx.lib.json` 清单文件声明原生入口。这三类能力相互独立：一个库可以只暴露元件、只暴露原生模块、只暴露 Service，也可以暴露它们的任意组合。

原生模块有两种实现方式。如果 Android、iOS 和 HarmonyOS 需要分别实现，请选择 `native-module`；如果 API 和业务逻辑可以通过标准 Node-API C++ addon 实现一次，再编译到 Android、iOS、HarmonyOS 和 Lynxtron，请选择 `napi-native-module`。两种方式都会给 Lynx 应用代码暴露带类型的模块，但生成文件和原生注册链路不同。

应用侧像安装普通 npm 依赖一样安装库。Android Gradle 插件、iOS CocoaPods 插件和 HarmonyOS Hvigor 插件会读取 `lynx.lib.json`，把原生代码链接进宿主应用；宿主应用本身无需了解每个库具体暴露了哪些能力。Lynxtron 会从已安装包中读取同一份清单，把匹配到的包文件收集到宿主输出目录，并在宿主 bundle 前置生成代码，加载每个已收集包的 `./lynxtron` 入口。

## 使用库

本节面向把一个或多个库集成进宿主 Lynx 应用的应用团队。

### 宿主应用项目结构

接入 Autolink 前，需要先确保宿主应用有一个可以安装 npm 包的项目根目录，并暴露原生应用的构建入口。典型结构如下：

```text
lynx-app/
├── package.json
├── android/
│   ├── settings.gradle
│   └── app/
│       └── build.gradle
├── ios/
│   └── Podfile
├── harmony/
│   ├── hvigorconfig.ts
│   └── entry/
│       └── hvigorfile.ts
├── shared/
│   ├── CMakeLists.txt
│   └── ...
├── dist/
└── src/
```

- `package.json` 是必需的，用来声明 Autolink 库依赖。
- Android 接入需要 Gradle settings 文件，例如 `settings.gradle` 或 `settings.gradle.kts`，以及 Android application 的构建文件，例如 `app/build.gradle` 或 `app/build.gradle.kts`。
- iOS 接入需要 CocoaPods 入口，通常是 `Podfile`。Podfile 需要声明 [`lynx-family` Specs 仓库](https://github.com/lynx-family/Specs)作为源。如果团队通过 Bundler 管理 Ruby 依赖，可以在 `Gemfile` 中维护 `cocoapods-lynx-library` gem。
- HarmonyOS 接入需要根目录的 `hvigorconfig.ts`，以及一个依赖 `@lynx/lynx` 的 entry 或 feature HAP 模块。
- `shared/` 用于宿主应用自有的跨端原生源码和 CMake 构建入口，需要自行编译。
- Lynxtron 接入需要应用具备宿主侧 Rspack 构建，并通过 `pluginLynxtron()` 安装和加载原生库；一般消费编译后的 `dist/` 产物。

安装依赖后，Autolink 会从已安装 npm 包的包根目录扫描 `lynx.lib.json`。`package-lock.json`、`pnpm-lock.yaml` 或 `yarn.lock` 等 lockfile 有助于可复现安装，但不是 Autolink 的必需项。

### 接入 Autolink

宿主应用只需要接入一次 Autolink。接入完成后，已安装的库会从 `node_modules` 中被发现，并在 Lynx 初始化时通过生成的 registry 自动注册。

<PlatformTabs queryKey="platform">
<PlatformTabs.Tab platform="android">

在 `settings.gradle` 中启用 settings plugin，让库的 Android 工程可以通过 `lynx.lib.json` 被发现并 include 进来：

```groovy
plugins {
  id 'org.lynxsdk.lynx.library-settings' version '4.0.1'
}
```

在 Android application 工程中启用 build plugin，让生成的 registry 加入应用源码，并自动把库工程接入为依赖：

```groovy
plugins {
  id 'com.android.application'
  id 'org.lynxsdk.lynx.library-build'
}
```

Gradle sync/build 后，Autolink 会生成固定的 Android registry 入口并加入应用源码。应用初始化 `LynxEnv` 时会自动加载该入口，库提供的元件、原生模块和 Service 会按应用全局注册生效；业务侧无需额外编写原生初始化代码。

</PlatformTabs.Tab>

<PlatformTabs.Tab platform="ios">

在 iOS 构建环境中安装 `cocoapods-lynx-library` gem。然后在应用的 Podfile 中加入 pod 源和 CocoaPods plugin，并调用 `use_lynx_library!`。执行 `pod install` 时，插件会加入库的 podspec 和生成的 registry pod：

```ruby
source 'https://cdn.cocoapods.org/'
source 'https://github.com/lynx-family/Specs.git'

install! 'cocoapods', :generate_multiple_pod_projects => true
plugin 'cocoapods-lynx-library'

target 'LynxApp' do
  use_lynx_library!
end
```

接入 N-API 库时需要保留 `generate_multiple_pod_projects`。它会隔离各 pod 的 header map，避免同名的 PrimJS 和 LynxWeakNodeAPI header 发生冲突。同时还需要让 Lynx 配套 pods 与主 Lynx pod 保持同一版本；否则旧 lockfile 可能继续保留不兼容的版本。

执行 `pod install` 后，Autolink 会生成 registry pod，并把它接入 Lynx 的初始化流程。应用创建 `LynxConfig` 或初始化 `LynxEnv` 时，库提供的元件、原生模块和 Service 会自动注册生效；业务侧无需导入生成文件或编写额外初始化代码。

</PlatformTabs.Tab>

<PlatformTabs.Tab platform="harmony">

在 HarmonyOS 工程根目录的 `hvigor/hvigor-config.json5` 中添加插件依赖：

```json5
{
  modelVersion: '5.0.0',
  dependencies: {
    '@lynx-js/lynx-library-plugin': '^0.1.0',
  },
}
```

在 HarmonyOS 工程根目录创建 `hvigorconfig.ts`，并启用一次插件：

```ts
import * as hvigorApi from '@ohos/hvigor';
import { enableHarmonyLynxAutolink } from '@lynx-js/lynx-library-plugin';

enableHarmonyLynxAutolink(hvigorApi, {
  moduleName: 'entry',
});
```

当工程中只有一个依赖 `@lynx/lynx` 的 entry 或 feature HAP 时，可以省略 `moduleName`。如果有多个 Lynx HAP 模块，则必须显式指定目标模块。

在 Hvigor 创建模块节点之前，插件会扫描可见的 `node_modules`，通过 Hvigor 公开的 `parseJsonFile()` API 解析 HarmonyOS JSON5 元数据，在工程忽略的 `.hvigor/lynx-autolink/<moduleName>` 缓存目录生成 Registry HAR，并通过 `hvigorConfig.includeNode()` 把 Library HAR 和 Registry HAR 加入构建图。目标 HAP 完成求值后，插件通过 HAP model API 注入 Registry 依赖和生成的资源目录，并设置 `module.appStartup`。AppStartup 源码位于 HAP 模块的 `build/generated/lynx-autolink` 目录；生成的 Hvigor task 会在 `clean` 后、当前 target 的 `PreBuild` 前恢复这些文件。插件不会修改应用的 `src` 目录，也不会改写版本库中的 `build-profile.json5`。

生成的 AppStartup task 会在应用代码创建 Lynx runtime 之前于主线程运行，并且只调用 Registry HAR 中幂等的 `setupGlobal()`。如果 HAP 已配置 AppStartup profile，插件会保留原有 task 和 `configEntry`，并追加 Lynx task。应用无需运行 `lynx-harmony-autolink` 命令，也无需手动调用 `setupGlobal()`。

</PlatformTabs.Tab>

<PlatformTabs.Tab platform="lynxtron">

:::note Lynxtron 工具链版本

请为 `@lynx-js/create-lynxtron`、`@lynx-js/lynxtron`、`@lynx-js/lynxtron-dev-plugins` 和 `@lynx-js/lynxtron-builder` 使用相同的发布版本。`targets` 清单和原生产物自动打包从 `0.0.22` 开始提供；本流程也已使用 Lynxtron `0.0.30`、`create-lynx-library@0.6.1` 和 `@lynx-js/autolink-codegen@0.6.0` 验证。复现本教程时请保留 lockfile。

Lynxtron 为桌面端原生库提供了 Autolink 支持。并不是所有嵌入 Lynx 的桌面宿主都开箱支持 Autolink，这是 Lynxtron 自带的能力。

在 Lynxtron 宿主侧 Rspack 配置中使用 `pluginLynxtron()`。这个插件默认包含 Lynxtron Autolink：它会扫描已安装依赖中的 `lynx.lib.json`，选择匹配的 `platforms.lynxtron.targets` 记录，把对应原生库 package 收集到宿主输出目录，并注入前置代码来加载所收集 package 的 `./lynxtron` 入口。业务代码直接导入 `<package>/lynxtron` 时，也会被别名到生成的代理模块，并在运行时解析已收集的 package，但原生注册不需要这种显式导入。`./lynxtron` 入口负责加载当前宿主对应的 `.node` 产物。

```ts
import { pluginLynxtron } from '@lynx-js/lynxtron-dev-plugins/rspack';

export default {
  target: 'electron-main',
  plugins: [
    pluginLynxtron({
      isDev: process.env.NODE_ENV === 'development',
      entry: './dist/desktop',
    }),
  ],
};
```

`entry` 参数是开发 runtime 接收的 Lynxtron 应用目录。`pluginLynxtron()` 会把已收集的原生库包放到 `<output>/.lynxtron/native` 下，其中 `<output>` 对应 Rspack 的 `output.path`。electron-builder 的 `directories.app` 必须指向同一个应用输出目录。打包应用时，`lynxtron-builder` 会把这些 package 保留在 ASAR 外；macOS 会把所选 target 的 Framework 和嵌套 app bundle payload 复制到 `Contents/Frameworks`，Windows 则让 `.node`、DLL、资源包和 locales 继续相邻地保存在解包目录中。

如果宿主使用 Rsbuild，则改为从 `@lynx-js/lynxtron-dev-plugins/rsbuild` 导入 `pluginLynxtron`。这个封装会配置底层 Rspack plugin、自动判断开发模式，并默认把 `entry` 指向 Rsbuild environment 的输出目录。

Lynxtron 加载原生库后，其中的生成注册会在 Lynx runtime 中生效。平台原生模块和元件使用 Lynx 静态注册，共享 N-API 模块则使用生成的 Node-API 注册。库作者不需要 Lynxtron 专用注册宏。

</PlatformTabs.Tab>
</PlatformTabs>

### 安装库

应用接入 Autolink 后，在 Lynx 应用中安装库：

```bash
npm install @example/lynx-button
```

每个库包都会在包根目录暴露 `lynx.lib.json` 清单文件。Autolink 会扫描已安装 npm 包中的这个文件。

```json
{
  "platforms": {
    "android": {
      "packageName": "com.example.button",
      "sourceDir": "android"
    },
    "ios": {
      "sourceDir": "ios",
      "podspecPath": "ios/build.podspec"
    },
    "harmony": {
      "packageDir": "harmony"
    },
    "lynxtron": {
      "targets": [
        {
          "os": "darwin",
          "arch": "arm64",
          "files": ["dist/darwin/arm64/lynx-button.node"],
          "frameworks": ["dist/darwin/arm64/Button.framework"],
          "appBundles": ["dist/darwin/arm64/Button Helper.app"]
        },
        {
          "os": "win32",
          "arch": "x64",
          "files": ["dist/win32/x64/lynx-button.node"]
        }
      ]
    },
    "macos": {
      "sourceDir": "shared"
    },
    "windows": {
      "sourceDir": "shared"
    }
  }
}
```

Android 侧必须声明 `platforms.android.packageName`，`sourceDir` 默认是 `android`。iOS 侧 `sourceDir` 默认是 `ios`，`podspecPath` 默认使用 iOS 源码目录下找到的第一个 `.podspec` 文件。HarmonyOS 侧 `packageDir` 默认是 `harmony`；该目录必须是完整的源码 HAR，包含 `hvigorfile.ts`、`oh-package.json5`、`build-profile.json5`、`src/main/module.json5`，以及由 `main` 声明的 package 入口或 `Index.ets`。

`platforms.macos.sourceDir` 和 `platforms.windows.sourceDir` 指向以源码形式暴露的 `shared/` 目录。它是跨端原生源码结构，后续也可以被更多平台复用。

对于 Lynxtron，使用 `targets` 按宿主组织运行时产物。每个 target 都包含 `os`、`arch`，以及名为 `files`、`frameworks` 和 `appBundles` 的字符串数组中的至少一个；其中每条路径都相对于包根目录。Autolink 会选择并校验与目标宿主匹配的 target、暂存对应 package，然后加载 package 的 `./lynxtron` export。该入口读取同一份清单，并从 `files` 中加载选中的 `.node`。`files` 列出保持包内相对位置的全部 payload，包括原生 addon、动态库、可执行文件、资源包和目录。在 macOS 上，`frameworks` 列出 `.framework` bundle，`appBundles` 列出嵌套 `.app` bundle；Lynxtron 会将两者放入 `Contents/Frameworks`，并把嵌套应用纳入宿主签名流程。

`npm pack` 不会保留 package 内容中的符号链接条目。如果 Framework 或 app bundle 依赖符号链接，需要提供幂等的安装步骤，使用随包发布的目标文件恢复链接，并验证安装后的 package。Lynxtron 会在收集和打包 bundle 时保留这些已恢复的链接。

这些路径只标识 npm 包内的源产物。Lynxtron 的开发插件和 builder 会自动决定它们在开发输出及最终应用包中的位置；应用团队不需要复制这些产物，也不需要为每个库增加打包规则。Lynxtron 清单不提供不透明的 package 根目录或旧字段别名：请严格使用 `targets`、`files`、`frameworks`、`appBundles` 和 `arch` 选择器。

安装或更新库后，Android 或 HarmonyOS 侧重新构建应用，iOS 侧重新执行 `pod install`，让生成的 registry 和原生依赖刷新。Lynxtron 应用只需执行自身标准的构建和打包命令，`pluginLynxtron()` 与 `lynxtron-builder` 会自动处理所选 target。应用不需要导入库的 `./lynxtron` 入口、复制原生文件，也不需要为每个库编写注册或打包配置。

## 开发库

本节面向开发可复用原生库供其他 Lynx 应用安装的库作者。

### 库包结构

一个典型的库结构如下；`shared/` 用于跨端原生实现，如果同一个包也发布 Lynxtron 原生产物，同一个结构中也可以包含 Lynxtron 加载入口和按宿主区分的输出：

```text
lynx-button/
├── package.json
├── lynx.lib.json
├── types/
│   ├── index.d.ts
│   ├── platform-native-module.d.ts
│   └── napi-native-module.d.ts
├── src/
│   └── index.ts
├── generated/
│   ├── ButtonModule.ts
│   └── ButtonModuleNapi.ts
├── android/
│   └── src/main/java/com/example/button/
│       ├── ButtonElement.java
│       ├── ButtonModule.java
│       ├── ButtonService.java
│       └── generated/ButtonModuleSpec.java
├── ios/
│   ├── build.podspec
│   └── src/
│       ├── ButtonElement.m
│       ├── ButtonModule.m
│       ├── ButtonService.m
│       └── generated/
│           ├── ButtonModuleSpec.h
│           └── ButtonModuleSpec.m
├── harmony/
│   ├── Index.ets
│   ├── hvigorfile.ts
│   ├── oh-package.json5
│   ├── build-profile.json5
│   └── src/main/
│       ├── module.json5
│       └── ets/
│           ├── LynxLibraryProviderImpl.ets
│           ├── ButtonElement.ets
│           ├── ButtonModule.ets
│           ├── ButtonService.ets
│           └── generated/ButtonModuleSpec.ets
├── shared/
│   ├── CMakeLists.txt
│   ├── nativeModule/
│   └── elements/
├── lynxtron/
│   ├── CMakeLists.txt
│   ├── index.cjs
│   └── library_entry.cc
├── dist/
│   ├── darwin/
│   │   └── arm64/
│   │       └── lynx-button.node
│   └── win32/
│       └── x64/
│           └── lynx-button.node
└── example/
```

- `package.json` 让库可以通过 npm 安装，并通常提供 `codegen` 脚本。
- `lynx.lib.json` 是 Autolink 清单文件，用来声明按平台选择的文件或 Framework 源产物。
- `types/index.d.ts` 汇总导出原生模块类型声明；选中对应能力时，平台 Native Module 声明位于 `types/platform-native-module.d.ts`，N-API Native Module 声明位于 `types/napi-native-module.d.ts`。
- `src/index.ts` 导出应用代码需要 import 的 JavaScript API。
- `android/`、`ios/` 和 `harmony/` 放置原生实现以及生成的原生 spec。HarmonyOS 目录是一个完整的源码 HAR，包含模块级的 `hvigorfile.ts`。
- `shared/` 放置跨端原生代码，例如跨端自渲染元件实现，以及 `shared/nativeModule/` 下的 C++ N-API 回调桩代码。
- `lynxtron/` 和 `dist/` 放置 Lynxtron 加载入口和按宿主区分的输出。
- `example/` 是库作者用于本地验证的示例应用。

### 创建库

使用交互式命令创建库：

```bash
npm create lynx-library
```

在脚本或测试中，也可以用 flags 直接生成：

```bash
npm create lynx-library -- \
  --dir ./lynx-button \
  --features native-module,napi-native-module,element,service \
  --platforms android,ios,harmony,lynxtron \
  --package-name @example/lynx-button \
  --android-package com.example.button \
  --module-name ButtonModule \
  --element-name x-button \
  --service-name ButtonService
```

生成的库会包含：

- 带有 `"codegen": "lynx-autolink-codegen"` 的 `package.json`
- 用于 Android、iOS、HarmonyOS 和 Lynxtron Autolink 元数据的 `lynx.lib.json`
- `types/index.d.ts`、`types/platform-native-module.d.ts` 和 `types/napi-native-module.d.ts`，根据选择的模块能力生成对应类型声明
- JavaScript facade 入口 `src/index.ts`
- 原生源码目录 `android/` 和 `ios/`，以及完整的 `harmony/` 源码 HAR
- 生成跨端实现时使用的 `shared/` native source
- 生成 Lynxtron 产物时使用的 `lynxtron/` 加载入口
- `example/`、`tsconfig.json` 和 `README.md`

在库根目录运行 codegen：

```bash
npm run codegen
```

`lynx-autolink-codegen` 会读取 `lynx.lib.json`。对于原生模块，它会扫描 `types/` 下的 Native Module 声明文件，查找带有 `@lynxmodule` 的声明：

```ts
/** @lynxmodule */
export declare class ButtonModule {
  getLabel(id: string): string;
  setEnabled(id: string, enabled: boolean): void;
}
```

它会生成：

- JavaScript facade：`generated/<ModuleName>.ts`
- Android platform native module：`<ModuleName>Spec.java`
- iOS platform native module：`<ModuleName>Spec.h` 和 `<ModuleName>Spec.m`
- HarmonyOS platform native module：`<packageDir>/src/main/ets/generated` 下的 `<ModuleName>Spec.ets`
- N-API 原生模块：`shared/nativeModule/` 下的 C++ N-API 回调桩代码

HarmonyOS spec 当前支持 `void`、`string`、`number`、`boolean` 和带 `null` 的 nullable union。其他生成目标保留已有的数组、对象/maps/sets、promise，以及 `ArrayBuffer`、typed arrays、`BigInt`、`Date`、`Function`、`Symbol`、`Buffer`、`Value` 等 N-API wrapped value types 支持。

### 编写 Native API

在原生源码中使用平台对应的 Lynx 注解或注册方式，Autolink 就能发现库提供的能力。Android 和 iOS 原生模块通常继承 `lynx-autolink-codegen` 生成的 spec；元件和 Service 会通过原生标记被发现。HarmonyOS Library 则导出一个统一注册所有能力的 Provider。

```java
package com.example.button;

import com.example.button.generated.ButtonModuleSpec;
import com.lynx.jsbridge.LynxNativeModule;
import com.lynx.jsbridge.LynxMethod;
import com.lynx.tasm.behavior.LynxContext;
import java.util.HashMap;
import java.util.Map;

@LynxNativeModule(name = "ButtonModule")
public final class ButtonModule extends ButtonModuleSpec {
  private final Map<String, Boolean> enabledState = new HashMap<>();

  public ButtonModule(LynxContext context) {
    super(context);
  }

  @Override
  @LynxMethod
  public String getLabel(String id) {
    return "Button " + id;
  }

  @Override
  @LynxMethod
  public void setEnabled(String id, boolean enabled) {
    enabledState.put(id, enabled);
  }
}
```

```ts
import {
  Behavior,
  LynxLibraryProvider,
  LynxLibraryRegistry,
  LynxServiceType,
} from '@lynx/lynx';
import { ButtonElement } from './ButtonElement';
import { ButtonModule } from './ButtonModule';
import { ButtonService } from './ButtonService';

export class LynxLibraryProviderImpl implements LynxLibraryProvider {
  register(registry: LynxLibraryRegistry): void {
    registry.registerBehavior('x-button', new Behavior(ButtonElement));
    registry.registerModule('ButtonModule', { moduleClass: ButtonModule });
    registry.registerService(LynxServiceType.Extension, ButtonService.instance);
  }
}
```

### 构建跨端 N-API 原生模块

当同一个原生 API 可以在四个原生宿主上运行时，使用 N-API 原生模块。生成的平台工程会编译同一份 C++ 实现，Autolink 则负责各平台的构建、注册和加载壳。

#### 创建工程并声明 API

下面的命令会创建只包含共享 N-API 模块的包。如果这个库还需要元件、Service 或平台原生模块，可以在同一条命令里追加其他 feature：

```bash
npm create lynx-library -- \
  --dir ./lynx-storage \
  --features napi-native-module \
  --platforms android,ios,harmony,lynxtron \
  --package-name @example/lynx-storage \
  --module-name StorageModule
```

进入生成的 package 并安装依赖：

```bash
cd lynx-storage
npm install
```

在 package 根目录的 `types/napi-native-module.d.ts` 中声明 JavaScript 接口。不要和 `types/platform-native-module.d.ts` 混用；同时选择两个 feature 时会生成两个模块，并走各自独立的注册链路。

```ts
/** @lynxmodule */
export declare class StorageModule {
  getRuntime(): string;
}
```

修改声明后运行 codegen：

```bash
npm run codegen
```

Codegen 只会创建一次 `shared/nativeModule/StorageModule.cc`，后续运行会保留该文件；TypeScript facade、注册源码、iOS wrapper 和符号保留 header、Lynxtron 注册源码则会重新生成。新增、删除或重命名方法后，需要先重新运行 codegen，再自行同步这个被保留 C++ 文件中的 callback 和 export。重命名模块 class 时，需要先重命名或删除旧的 `<ModuleName>.cc`，并清理旧模块对应的生成文件，再重新运行 codegen；codegen 不会自动删除残留的模块文件。

#### 只实现一次模块

将业务逻辑和 Node-API callback 放在 `shared/nativeModule/<ModuleName>.cc` 中。这个保留的源码使用 `@lynx-js/weak-node-api` 提供的标准 header；具体使用普通符号还是 weak-suffixed 符号，由各平台构建配置决定。

下面的精简实现展示了用户维护代码和生成注册代码之间的边界：

```cpp
#if __has_include(<LynxWeakNodeAPI/headers/napi.h>)
#include <LynxWeakNodeAPI/headers/napi.h>
#else
#include "napi.h"
#endif

#if defined(USE_WEAK_SUFFIX_NAPI)
#include "weak_napi_defines.h"
#endif

namespace {

napi_value GetRuntime(napi_env env, napi_callback_info info) {
  (void)info;
  napi_value result = nullptr;
  napi_create_string_utf8(
      env, "shared-c++", NAPI_AUTO_LENGTH, &result);
  return result;
}

void BindStorageModule(napi_env env, napi_value exports) {
  napi_value get_runtime = nullptr;
  napi_create_function(
      env, "getRuntime", NAPI_AUTO_LENGTH, GetRuntime, nullptr, &get_runtime);
  napi_set_named_property(env, exports, "getRuntime", get_runtime);
}

}  // namespace

extern "C" napi_value LynxAutolinkCreateStorageModule(
    napi_env env, napi_value exports, const char* module_name, void* opaque) {
  (void)module_name;
  (void)opaque;
  BindStorageModule(env, exports);
  return exports;
}

#if defined(USE_WEAK_SUFFIX_NAPI)
#include "weak_napi_undefs.h"
#endif
```

不要在这个文件里放 `napi_module_register`、constructor 或平台 loader 代码。`shared/nativeModule/generated/<ModuleName>Registration.cc` 负责标准 Node-API 注册，并会被 codegen 覆盖；各平台入口只需要保留或调用这份生成注册代码。

#### 为每个平台声明 addon

`create-lynx-library` 会在 `lynx.lib.json` 中生成下面这些平台记录。在移动端，`nodeApiAddons` 的 `name` 必须与标记了 `@lynxmodule` 的 class 名称，以及生成的 TypeScript facade 加载的名称一致。

```json
{
  "platforms": {
    "android": {
      "packageName": "com.example.storage",
      "sourceDir": "android",
      "providerClassName": null,
      "nodeApiAddons": [
        {
          "name": "StorageModule",
          "libraryName": "StorageModule",
          "required": true
        }
      ]
    },
    "ios": {
      "sourceDir": "ios",
      "podspecPath": "ios/lynx-storage.podspec",
      "nodeApiAddons": [
        {
          "name": "StorageModule",
          "podName": "lynx-storage",
          "podspecPath": "ios/lynx-storage.podspec",
          "addonUseHeader": "addon_use.h"
        }
      ]
    },
    "harmony": {
      "packageDir": "harmony",
      "providerExportName": null,
      "nodeApiAddons": [
        {
          "name": "StorageModule",
          "libraryName": "StorageModule",
          "initializerExportName": "initializeNodeApiAddon",
          "required": true
        }
      ]
    },
    "lynxtron": {
      "targets": [
        {
          "os": "darwin",
          "arch": "arm64",
          "files": ["dist/darwin/arm64/lynx-storage.node"]
        }
      ]
    }
  }
}
```

- Android 从 package 的 CMake 工程构建 `lib<libraryName>.so`。生成的工程会链接 PrimJS 的 `libnapi_adapter.so` 和 `libnapi.so`；如果 package 发布的是预编译库，则可以改为声明 `jniLibsDir`。
- iOS 通过生成的 CocoaPods wrapper 编译共享实现。`addonUseHeader` 用于防止生成的注册符号被 linker 裁剪。
- HarmonyOS 构建源码 HAR。`initializerExportName` 指向一个幂等的 ArkTS export；Autolink 会在 AppStartup 阶段调用它，在 Lynx 创建 runtime 前加载 addon library。
- Lynxtron 选择匹配的 `targets` 记录、收集其中列出的 `.node` 产物，再加载 package 的 `./lynxtron` 入口。package 发布的每个 OS 和架构都需要构建并包含对应 target。

宿主应用仍然只需要完成[接入 Autolink](#接入-autolink) 中的一次性平台配置。不要在宿主中自行加载共享库、调用 `initializeNodeApiAddon()` 或引用 iOS 注册符号。原生注册本身不需要显式导入 `./lynxtron` 入口；如果业务代码需要使用该入口，仍然可以显式导入。

#### 保持 C++ 实现跨端共享

将可移植的 Node-API callback 和业务逻辑放在 `shared/nativeModule/` 下。平台目录只保留构建配置、生成 wrapper 和原生依赖打包：

| 平台      | 平台专属层                                                    | 共享输入                             |
| --------- | ------------------------------------------------------------- | ------------------------------------ |
| Android   | Gradle、CMake shared-library target、PrimJS 原生库            | C++ callback 和生成的注册代码        |
| iOS       | Podspec、生成 wrapper、`addon_use.h`                          | 同一份 C++ callback 和生成的注册代码 |
| HarmonyOS | 源码 HAR、CMake shared-library target、ArkTS initializer      | 同一份 C++ callback 和生成的注册代码 |
| Lynxtron  | CMake `.node` target、`./lynxtron` loader、打包 target 元数据 | 同一份 C++ callback 和生成的注册代码 |

共享文件里使用标准 Node-API 类型，不要直接使用 JNI、Objective-C、ArkTS 或 Node/V8 专属 API。如果某个原生依赖的平台接入方式不同，应通过平台 link library 或一层很小的 C++ 抽象把它提供给共享 CMake target，不要复制整套模块 callback。让生成的 CMake 控制 `USE_WEAK_SUFFIX_NAPI`，并确保 `weak_napi_defines.h` 和 `weak_napi_undefs.h` 成对包住实现。

从 package 根入口导入 `StorageModule`。首次访问时，生成的 facade 会通过 Lynx N-API loader 解析 addon，并同时暴露为 `NativeModules.StorageModule`。ReactLynx 组件模块可能在两个线程执行，但 N-API 模块只在后台 runtime 可用，因此调用前需要判断线程：

```ts
import { StorageModule } from '@example/lynx-storage';

function readRuntime() {
  if (__MAIN_THREAD__) {
    return;
  }

  const runtime = StorageModule.getRuntime();
  // 导入 package 后，下面的调用等价：
  const sameRuntime = NativeModules.StorageModule.getRuntime();
  // 在后台线程使用 runtime 和 sameRuntime。
}
```

如果没有这个判断，主线程执行阶段可能报出 `Native module "StorageModule" is unavailable`，即使同一个 package 已在后台 runtime 中正确注册。

### 发布库

像发布普通 npm 包一样发布库：选一个包名（通常是带 scope 的 `@example/lynx-button`），并在 `package.json` 中设置版本号。如果包声明了 Lynxtron targets，需要先生成源码，并在对应宿主上构建每个声明的操作系统和架构，再进行打包：

```bash
npm run codegen
npm run build:lynxtron
npm pack --dry-run
npm pack
```

`npm pack` 和 `npm publish` 不会编译原生产物。运行 `npm publish` 前，需要把所有 target 的输出收集到 `dist/`，确认 `package.json#files` 包含 `dist`、`lynxtron` 和 `lynx.lib.json`，并确认 tgz 中包含 `targets` 列出的每条路径。

应用团队只需把已发布的包加入依赖，然后执行应用自身标准的构建和打包命令。Lynxtron Autolink 会自动加载匹配的 target 并打包其运行时 payload，不需要任何逐库的应用配置。建议在库的 `peerDependencies` 中固定兼容的 Lynx SDK 版本范围，这样当库和宿主 SDK 出现版本错配时，应用团队能够第一时间收到清晰提示。

## Autolink 工作原理

Autolink 在构建期运行。它会扫描 `node_modules` 中每个 npm 包的 `lynx.lib.json` 清单，然后为当前平台生成或提供宿主接入数据。各平台的生成方式如下：

- **Android**：由 Gradle settings 插件和 build 插件配合完成 registry 生成。
- **iOS**：由 CocoaPods 插件完成，并产出 registry pod。
- **HarmonyOS**：在 Hvigor 配置阶段生成源码 Registry HAR 和 AppStartup task。
- **Lynxtron**：运行在宿主侧 Rspack 构建中，收集匹配到的原生包，并把加载代码注入宿主 bundle。已加载的库通过 Lynx 静态注册提供平台原生模块和元件；对于共享 N-API 模块，`./lynxtron` 入口加载已收集的 `.node` 产物时，会走生成的 Node-API 注册链路。

Android、iOS 和 HarmonyOS 都只会在初始化阶段加载一次生成的 registry，因此宿主代码中不需要任何逐库的接入逻辑。
