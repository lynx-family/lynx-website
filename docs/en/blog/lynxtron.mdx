Desktop apps need access to the system and a fast way to iterate on UI. **[Lynxtron](/lynxtron/)** keeps the familiar Node.js host and uses Lynx to render the app’s interface, so the base runtime ships without a browser engine.

<span id="light-weight-and-fast" />

- **Download size.** The [Lynxtron 0.0.28 runtime ZIP](https://github.com/lynx-family/lynxtron/releases/tag/v0.0.28) is **24 MB on macOS arm64** and **35 MB on Windows x64**. The [Electron 44.3.0 runtime ZIP](https://github.com/electron/electron/releases/tag/v44.3.0) is **130 MB** and **158 MB** on the same platforms.
- **Startup.** In a Windows production experiment, Lynxtron cut Douyin Desktop’s median time to first screen by **27%** versus the control group. Within the experiment group, P90 cold-start time to the first feed was **10.8 s** on the Lynxtron path versus **19.0 s** on the standard path (**43% lower**).

## An Electron-style architecture for developers and coding agents \{#multiplatform}

We wanted developers and coding agents to be able to start with a familiar Electron main script. The Node.js host still manages the app lifecycle, menus, and windows. What changes is what runs inside a window. In Electron, Chromium renders the page in a separate process. In Lynxtron, Lynx renders on the app’s main thread and runs UI logic on a background thread. [Explore the architecture.](/lynxtron/learn/what-is-lynxtron)

![Lynxtron runs the Node.js host and Lynx rendering on the main thread, with UI logic on a background thread.](https://lf-lynx.tiktok-cdns.com/obj/lynx-artifacts-oss-sg/lynx-website/assets/lynxtron/lynxtron-architecture-en.png)

For example, an Electron app opens its first window after `app.whenReady()`. The same pattern works here: create a `LynxWindow` and load a compiled Lynx bundle.

```ts
import { app, LynxWindow } from '@lynx-js/lynxtron';

app.whenReady().then(() => {
  const win = new LynxWindow({ width: 800, height: 600 });
  win.show();
  win.loadFile('main.lynx.bundle');
});
```

Electron developers can work on a web UI in the browser. Lynx for Web keeps that workflow for Lynx apps. Try editing a note in the preview below. The same UI saves through the same Notes API on both targets, using browser storage on the Web and a file on desktop. [Run Lynxtron in the browser.](/lynxtron/learn/running-on-web)

## Extend Lynx with the native code you already have \{#natively-extensible}

If your desktop app already draws a canvas with a native renderer, you can keep that renderer when you move the UI to Lynx. In Native Texture Canvas, the renderer draws into an external texture. Lynx displays that texture alongside ordinary UI controls, so the drawing code stays native. [Explore Lynx native libraries.](/lynxtron/Native-Libraries/Lynx-Native-Libraries)

Existing web pages can live inside a Lynx UI, too. We plan to support the [system WebView](https://github.com/lynx-family/lynxtron/issues/395) for apps that can use each platform’s web engine. Today you can bundle the [CEF WebView](/lynxtron/api/@lynx-js/cef-webview/index.mdx) to ship the same Chromium engine across platforms. In [Lynxtron 0.0.28](https://github.com/lynx-family/lynxtron/releases/tag/v0.0.28), the separate CEF download is **126 MB on macOS arm64** and **161 MB on Windows x64**.

For native modules, we followed Electron’s lead and chose [Node-API](/guide/use-native-modules.html?platform=node-api). Our goal is to let developers share a native module implementation across all Lynx native platforms. [Read the Node-API proposal.](https://github.com/lynx-family/lynx/discussions/845)
