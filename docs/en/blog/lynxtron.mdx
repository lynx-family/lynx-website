Electron lets front-end developers build desktop apps efficiently in JavaScript: Web technologies for the interface, Node.js for system capabilities. That efficiency rests on Chromium, and so does its cost — every app has to ship its own browser engine, which inflates the base download and runtime memory. To keep that efficiency at a lower cost, we built **[Lynxtron](/lynxtron/)**.

It uses Node.js as the host and Lynx to render the UI, so the base runtime ships without a browser engine. Developers keep using Electron-style main-process APIs to manage windows and the app lifecycle, and write Lynx components and styles the way they would write a web app. The same UI code also [runs in a browser](/lynxtron/learn/running-on-web), so there is no separate Web build to maintain.

<span id="light-weight-and-fast" />

- **Download size.** The Lynxtron 0.0.28 runtime ZIP is **24 MB on macOS arm64** and **35 MB on Windows x64**. Electron 44.3.0 is **130 MB** and **158 MB** on the same platforms. [Lynxtron release](https://github.com/lynx-family/lynxtron/releases/tag/v0.0.28) · [Electron release](https://github.com/electron/electron/releases/tag/v44.3.0)
- **Idle memory.** In a 700×520 hello-world idle benchmark, Lynxtron 0.0.28 uses less than Electron 44.3.0: on macOS (Apple M5 Max MacBook Pro) it is **52 MB** of memory Footprint in one process, versus **86 MB** across Electron’s four processes — roughly **40% less**; on Windows (Windows 11 25H2, Core Ultra 7 155H) it is **68.3 MB** of Working Set - Private in one process, versus **158.7 MB** across Electron’s four processes — roughly **57% less**.
- **Startup speed.** Douyin Desktop on Windows ships a Lynxtron-based startup entry alongside its existing Electron entry. Real-user data shows P50 time to first screen **27% shorter**; on cold start, P90 time to the first feed drops from **19.0 seconds** on Electron to **10.8 seconds**, a **43% reduction**.

## Familiar Electron APIs and Architecture \{#multiplatform}

### A Node.js host with Lynx rendering

A coding agent adapting an Electron app already has a starting point: its Node.js main script. Lynxtron carries over Electron’s main-process API: app lifecycle, menus, trays, and dialogs keep the same usage. The window layer is the most direct difference: `BrowserWindow` becomes `LynxWindow`, and window management methods such as creation, size, visibility, and full screen keep the naming and semantics of `BaseWindow`, but the window loads a Lynx bundle instead of HTML, and `webContents` is no longer available. Rendering changes with it: Electron renders the page in a separate Chromium process, while Lynxtron renders the interface on the main thread of the same process and runs business logic on a background thread. [Explore the architecture.](/lynxtron/learn/what-is-lynxtron)

![Lynxtron runs the Node.js host and Lynx rendering on the main thread, with UI logic on a background thread.](https://lf-lynx.tiktok-cdns.com/obj/lynx-artifacts-oss-sg/lynx-website/assets/lynxtron/lynxtron-architecture-en.png)

### Manage windows with APIs agents already know

For example, an Electron app opens its first window after `app.whenReady()`. The same pattern works here: create a [`LynxWindow`](/lynxtron/api/@lynx-js/lynxtron/Class.LynxWindow.mdx) and load a compiled Lynx bundle.

```ts
import { app, LynxWindow } from '@lynx-js/lynxtron';

app.whenReady().then(() => {
  const win = new LynxWindow({ width: 800, height: 600 });
  win.show();
  win.loadFile('main.lynx.bundle');
});
```

### Call Node.js objects directly from Lynx

Lynxtron’s [preload scripts](/lynxtron/learn/Communication-Between-Node-And-Lynx) work the same way as [Electron’s](https://www.electronjs.org/docs/latest/tutorial/tutorial-preload): gain Node.js access in an isolated context, then expose what the UI needs. What differs is what can pass between the system environment and the UI environment. Electron’s [`contextBridge`](https://www.electronjs.org/docs/latest/api/context-bridge) serializes, proxies, or copies values across contexts, so the page never receives the original objects from the preload context. Lynxtron’s [`contextBridge.exposeInLynxBTS()`](/lynxtron/api/@lynx-js/lynxtron/context-bridge/Interface.ContextBridge.mdx#exposeinlynxbts) exposes JS objects to Lynx BTS directly: the object can carry functions, and those functions can use closures from the preload context, take other functions as arguments, and return Promises.

Electron also offers `nodeIntegration`, which lets the page use Node.js directly, but it weakens isolation and is generally not recommended. Lynxtron doesn’t need that trade-off: the preload script uses Node.js in an isolated context, and the exposed objects stay directly callable.

The file explorer example below does exactly this: the preload script exposes file APIs, and the Lynx UI calls them through [`NativeModules.nodejs.exposed`](/lynxtron/api/@lynx-js/lynxtron/lynx/Interface.LynxtronNodejs.mdx#exposed).

### Embed native views in Lynxtron

Lynxtron can wrap a native view as a Lynx element and place it directly in the interface, so existing native capabilities carry over. With this capability you can embed a system WebView in the app; if the app needs to ship Chromium, use the [CEF WebView](/lynxtron/api/@lynx-js/cef-webview/index.mdx) we provide. Any other native view can be wrapped the same way — a rich text editor, a large data grid, a map control.

### Load Node-API modules on the UI side

Electron’s renderer runs in Chromium and can’t use [Node-API](/guide/use-native-modules.html?platform=node-api), so native modules live in the main process and the UI reaches them over IPC. Lynxtron’s preload script runs in the Node.js environment, so it can `require` native modules and hand the objects to the Lynx UI. The modules are the same npm Node-API packages Electron uses; only the rebuild tool changes, to [`@lynx-js/lynxtron-rebuild`](/lynxtron/api/@lynx-js/lynxtron-rebuild/). We’re also [bringing Node-API to all Lynx native platforms](https://github.com/lynx-family/lynx/discussions/845).
