Today, we're announcing [AnimaX](https://github.com/lynx-family/animax), a cross-platform animation framework compatible with Lottie. You can keep creating animations in After Effects, combining shapes, images, text, and transparent video for playback in Lynx and native apps.

AnimaX was built by engineers at ByteDance and has been rolling out across
ByteDance products such as TikTok and CapCut since 2023. Today it runs in dozens
of apps across Android, iOS, HarmonyOS, desktop, and Web, rendering animations
on the order of tens of billions of times every day. Those animations span a
wide range: lightweight, high-frequency motion such as splash screens, loading
states, and list effects, as well as visually intense, heavy-load experiences
such as shopping festivals, LIVE gifts, rewards and incentive features, and
global events.

For TikTok's 2024 Paris Olympics campaign, AnimaX delivered visually rich
effects to users around the world. In TikTok's incentive experiences, it has to
run just as smoothly on a large population of low- and mid-range devices. These
are the scenarios that keep pushing AnimaX on rendering consistency,
performance floors, and expressiveness.

Lottie established a workflow for bringing animations from After Effects into apps, allowing designers to bring their work directly into products. We want to build on that workflow, making room for richer visual effects while reducing the work needed to adapt animations across platforms.

Animations with complex effects, masks, and layer compositing require teams to balance visual fidelity, platform differences, and rendering cost. AnimaX addresses these three challenges with [mixed layers](#alpha-video) for complex effects, a [shared renderer](#consistent-rendering-across-platforms) to reduce platform differences, and [graphics work that runs off the main thread](#reduced-main-thread-work).

## Keep Your Lottie Workflow

Many teams already have a complete pipeline around After Effects, Lottie JSON,
preview tools, and release workflows. If stronger rendering required a new
format, both designers and developers would need to relearn the process, and
existing assets would be hard to reuse. AnimaX keeps parsing Lottie-compatible
artifacts so existing JSON files can enter the new runtime directly.

This lets teams start by using AnimaX as a more capable Lottie player, then
gradually introduce [Alpha Video](#alpha-video), [dynamic properties](#dynamic-properties), and mixed layers where they
make sense. Designers still organize motion in After Effects. Developers still
load animation assets, [control playback](/animax/lynx/basic-controls), and [listen to state changes](/animax/lynx/runtime-events). The main
difference is that the playback pipeline underneath is now a more unified C++
renderer.

In practice, [existing Lottie assets in a project can be handed to AnimaX for
playback](/animax/migrate-from-lottie#reuse-your-animation-assets) without asking designers to export them again from After Effects.

[AFX](/animax/afx) is the After Effects export plugin provided by AnimaX. It exports Lottie-compatible animations and can export selected layers as Alpha Video. You can keep using existing Lottie assets and [use AFX](/animax/afx#getting-started) when you want to add transparent video layers.

## A Shared Renderer for Consistency and Performance

AnimaX uses a C++ runtime and the [Skity](https://github.com/lynx-family/skity) rendering engine to provide a shared drawing implementation and move expensive graphics work off the main thread. These capabilities come from the player, so you can use them without recreating your animations.

### Consistent Rendering Across Platforms

The hardest part of cross-platform animation is often not whether an asset can
play, but whether it plays the same way everywhere.

In a traditional setup, Android, iOS, and Web often rely on separate rendering
implementations. An effect that works through Skia on Android may look different
when iOS draws it through Core Graphics or another stack. Even a blur on a shape
layer may be correct on one platform and missing on another. As support expands
to HarmonyOS, Desktop, or more embedded containers, those differences multiply.

AnimaX moves the core logic into C++ and uses
[Skity](https://github.com/lynx-family/skity) to unify drawing behavior.
Platform code only needs to provide the necessary window, texture, resource
loading, and event capabilities. Animation parsing, layer calculation, draw
order, and most rendering behavior are handled by the same engine. This does not
erase every platform difference, but it keeps those differences inside a much
smaller boundary instead of asking every platform to maintain a separate player.

With
[Skity](https://github.com/lynx-family/skity) as the self-rendering engine,
AnimaX can support more [drawing features and advanced motion](/animax/feature-support#effects) through one
graphics pipeline, reducing its dependence on the differences between native
platform renderers. AnimaX supports more After Effects features than Lottie
in several categories; see [Feature Support](/animax/feature-support) for
the full comparison.

### Reduced Main-Thread Work

Complex animation usually hurts page performance through continuous layer
calculation, mask processing, blending, and drawing. If all of that stays on the
UI thread, it competes with scrolling, layout, and gesture handling. The problem
is especially visible on lower-end devices.

AnimaX's self-rendering architecture allows expensive rendering work to run off
the UI thread. For animations with many mattes, masks, effects, and layer
compositing, this can significantly reduce main-thread pressure and move the
risk of jank out of the main interaction path.

The [AnimaX Lottie Benchmark](https://github.com/RickAi/animax-lottie-benchmark)
uses the rocket animation from the
[Callstack article](https://www.callstack.com/blog/lottie-vs-rive-optimizing-mobile-app-animation)
and plays the same vector asset on three platforms: a Pixel 4 on Android 10
held at 60 Hz, an iPhone 12 Mini on iOS 15.4, and Chrome with the hardware WebGL
backend, compared against lottie-web's SVG renderer. The method and full
reports are open source and reproducible.

Android shows the largest gap: AnimaX holds the main thread at 60 FPS while
Lottie reaches 37.5 FPS, and AnimaX does so with less process CPU, about 0.71
cores against 1.03. Moving rendering to the GPU thread leaves the main thread
more headroom. On iOS, both engines hold 60 FPS, which matches Lottie iOS's Core
Animation path handing part of the playback work to the system renderer. On the
Web, frame rates are effectively the same, and AnimaX's WebGL backend keeps
resources on the GPU side, so both the JS heap and Chrome's process RSS are
lower.

Memory needs to be read with each platform's accounting model in mind. On
Android, AnimaX has lower Native Heap and Java Heap deltas but a higher Graphics
delta; on iOS, its Phys Footprint is higher. This is the expected shape of a
self-rendering engine whose working set lives in graphics buffers, textures,
and renderer caches, which iOS counts directly toward the process footprint.

### In Production

A benchmark covers one animation on a few devices; production traffic is a
different kind of test. Across several product teams that migrated from Lottie,
the result has been consistent: AnimaX raises the floor of the experience
rather than the peak.

- **Incentive experiences**: frame rates in the middle percentiles improved by
  about half, with clear gains in the low percentiles as well, while CPU and
  memory stayed roughly flat.
- **E-commerce campaigns**: where Lottie ran at barely more than ten frames per
  second on low-percentile devices, AnimaX stayed close to the cap across
  percentiles, and animation assets loaded noticeably faster.
- **Large-scale events**: with frame rate capped at 30 FPS, AnimaX held the cap
  across all percentiles on both platforms, while Lottie stuttered visibly at
  the high percentiles.
- **Stability**: no significant difference from Lottie, with ANR and jank
  metrics slightly lower.

This matches the Android benchmark: moving rendering off the UI thread does not
make an already smooth device faster. It addresses the cases where the UI
thread is already saturated.

## Go Further with AnimaX

### Alpha Video

Pure vector layers cannot represent every After Effects effect. Real motion
often combines shape layers, images, text, blur, masks, lighting, and 3D-like
visuals. Forcing all of that into image sequences inside Lottie usually leads to
large files, unstable fidelity, and platform-specific rendering gaps.

AnimaX supports [Alpha Video](/animax/alpha-video) layers. For effects that are
too complex for vectors today, or simply better expressed as video, designers
can follow the [AFX export guide](/animax/afx) to [organize and export those
layers as transparent video](/animax/alpha-video#how-to-use). AnimaX then plays them together with Lottie
shape, image, and text layers. This keeps the expressive power of After
Effects without forcing every visual detail into pure vector data.

### Dynamic Properties

Once animation enters a product page, it is rarely just something that plays
once and ends. A page may need to [replace images](/animax/lynx/dynamic-properties#set-image-resources) based on user state, [switch
text](/animax/lynx/dynamic-properties#set-text-font-resources) for localization, update colors for themes, or [change a layer property](/animax/lynx/dynamic-properties#update-other-layer-properties) in
response to interaction.

AnimaX optimizes these runtime updates and provides direct APIs for replacing
images, fonts, text, and other resources. Product code can treat an animation as
a configurable runtime layer, rather than a closed video or a set of UI pieces
that cannot be reused. Designers can still build the motion in After Effects,
while developers inject real product data at runtime.

See [Dynamic Properties](/animax/lynx/dynamic-properties) for the Lynx component APIs
and native API entry points.

## Try AnimaX Today

AnimaX is available in the
[lynx-family/animax](https://github.com/lynx-family/animax) repository, with
native Android and iOS examples included. In Lynx apps, AnimaX animations can be
played directly through the
[`<animax-view>`](/api/elements/built-in/animax-view) element. The docs also
include examples you can preview and try.

For native apps, start with [Migrate from Lottie to AnimaX](/animax/migrate-from-lottie) if you are replacing an existing Lottie player, then follow the [Native Integration Guide](/animax/native/quick-start) to integrate AnimaX into iOS or Android. See the [Native API reference](/animax/native/api/animax-view) for [playback controls and lifecycle](/animax/native/playback), events, and status queries.

Start with the [AnimaX introduction](/animax/introduction) to understand the
runtime, then follow the [quick start](/animax/start/quick-start) to run a
minimal example. If your assets come from After Effects, continue with the
[AFX export guide](/animax/afx) to see how Alpha Video layers are produced
and played together with Lottie artifacts.

More platform support is also planned:

- HarmonyOS and Web support are expected to roll out in Q3 2026. In the same period, we will also package and release the LynxUI AnimaX component, allowing AnimaX to integrate into the LynxUI ecosystem through a more unified component model.
- Desktop support is planned to be open-sourced in Q4 2026.

AnimaX is licensed under Apache-2.0 and continues to evolve in the open. You are
welcome to file issues, discuss requirements, or contribute in the
[lynx-family/animax repository](https://github.com/lynx-family/animax).

AnimaX is not trying to replace the Lottie workflow designers already know. It
keeps that workflow and adds the rendering, composition, and runtime control
needed to deliver complex motion reliably across platforms. For teams shipping
animation-heavy product experiences, it offers a more controlled path forward.
