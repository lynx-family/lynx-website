When we open-sourced Lynx, we said that many production-proven capabilities—including a richer set of UI components—were [still on their way](/blog/lynx-unlock-native-for-more#this-is-not-the-end-but-a-new-beginning). From Lynx 3.6 to the current development version, we have kept moving that work forward: bringing more native elements into the open and using [lynx-ui](/blog/lynx-ui) to turn those foundations into components that frontend developers can use directly.

That path has three connected stages: first, bring native capabilities already proven in real products into open source; then organize those capabilities into a component language that frontend developers can use and extend; finally, let requirements, standards, implementations, and tests form a continuous loop in the open community.

> **Scope:** This article describes a direction, not a dated delivery checklist. Concrete designs will still take shape through RFCs, implementation work, and community discussion.

## XElement: Bringing Production Native Capabilities into the Open

In Lynx, [Elements](/guide/ui/elements-components) are the basic building blocks of an interface. `<view>`, `<text>`, and `<image>` provide the fundamentals. [XElement](/guide/ui/elements-components#xelement) extends Lynx with native capabilities such as scrolling, input, media, and overlays, absorbs differences in platform APIs, thread models, performance, and compatibility, then exposes them through the Element contract.

In Lynx 3.6, the open-source stack included a small set of extended native elements, primarily `<input>`, `<textarea>`, and `<overlay>`. Since then, we have gradually brought more capabilities already running in real applications into the open:

- Lynx 3.7 introduced the [`<svg>`](/api/elements/built-in/svg) element for cross-platform native vector rendering;
- Lynx 3.8 added interaction containers such as [`<refresh>`](/api/elements/built-in/refresh) and began opening up native Markdown rendering;
- In the current development version, capabilities such as `blur-view`, `markdown`, `scroll-coordinator`, `video`, `viewpager`, and `webview` are also entering the open stack across Android, iOS, and HarmonyOS.

Many are not new experiments, but implementations already proven in production. The goal is not to reinvent them in public, but to bring them into a public build, release, and maintenance lifecycle together with their semantics, compatibility boundaries, and migration paths. As XElement expands what Lynx can express natively, real products still need state, composition, defaults, and component APIs that can evolve over time. That is where lynx-ui enters the story.

## Why lynx-ui Emerged: Capabilities Still Need to Be Organized

The native layer is good at rendering performance, gesture latency, and platform adaptation. The frontend is good at state, composition, visual customization, and rapid iteration. Cross-platform UI should not choose between them. It should turn native capability into something the frontend can continuously organize and extend.

A native Element needs a complete **Capability Surface** to cover platforms, versions, and performance scenarios. If products inherit that API directly, they also inherit platform switches and compatibility branches. Lists are a representative example: `<list>` and `<scroll-view>` provide scrolling, reuse, caching, sticky positioning, and exposure, while products care about refresh, loading, empty state, and content composition. This is a **Leaky Abstraction**: adding every product shape expands the Element API; moving every difference into the frontend makes each DSL pay the same cost again.

lynx-ui formed at this boundary. It is not another set of native controls, nor does it merely rename Element properties. It is an officially maintained, unstyled, and composable component system:

- XElement preserves the expressive power required by native capabilities and owns their multi-platform implementations;
- Element turns those capabilities into public contracts that can be discussed and tested;
- lynx-ui converges platform switches, version strategies, and default behavior into component semantics, so the frontend deals with product intent instead of implementation detail.

This is also why lynx-ui uses a composable model built from [Primitives and Parts](/ui/styling-theming): components own state, behavior, and structure without fixing visual appearance, so design systems can build their own product language on top. The goal is native-grade interaction with Web-grade composition—not a thin wrapper around Elements.

### Let Capabilities Move Between Implementation and Composition

As part of XElement, the native `<overlay>` element solves an independent-layer rendering problem. It lets content escape the clipping and stacking constraints of the regular view tree and render in the appropriate native container. But `<overlay>` does not know what a dialog is, nor does it manage open and close state, enter and exit animation, anchor positioning, or drag-to-snap behavior.

lynx-ui first uses `OverlayView` to normalize how Overlay works across containers and platforms. From there:

- `Popover` composes anchor tracking, positioning, visibility state, and Presence;
- `Dialog` composes Trigger, Backdrop, Content, dismissal behavior, and enter and exit states;
- `Sheet` goes further by combining Overlay, Presence, main-thread gestures, and Motion to support dragging, resistance, and snap points.

> **Capability Flow: Platform capability → XElement implementation → Element contract → lynx-ui composition → Product experience**
>
> **Feedback Flow: Product requirements and tests → Component model → Element semantics → XElement implementation**

### Make Open Capabilities Truly Dependable

For an XElement to become dependable, it needs a clear Element API, stable cross-platform behavior, explicit compatibility and fallback strategies, and documentation, tests, and migration paths that evolve with each release. The corresponding lynx-ui component must also cover keyboard, focus, gesture, accessibility, performance, and edge states.

lynx-ui will also be a long-term **dogfooding** surface: Element contracts are composed in real components, engine capabilities are validated through component tests, and differences flow back into XElement. Success is not measured by code volume, but by whether developers know where a capability works, how it falls back, and what an upgrade will cost.

### Let One Capability Serve the Whole Ecosystem

Through RFCs and Discussions, the community can help define what an Element should promise, how components should compose, and what tests should verify. The Lynx team turns that consensus into multi-platform implementations and takes responsibility for releases and long-term maintenance.

When semantics and tests become public standards, reuse no longer stops at ReactLynx. Different DSLs do not need to share one lynx-ui codebase, but they can share three kinds of foundations:

- **Reusable lower-level implementations:** mechanisms such as gesture arbitration, animation drivers, overlays, focus, and keyboard handling that depend on native code or the main thread;
- **Shared behavioral contracts and tests:** even when state management and composition code differ, implementations can follow the same semantics and pass the same cross-platform assertions;
- **Thin, idiomatic wrappers:** each DSL can express component composition, context, and controlled state in the way that feels most natural to its users.

The goal is not to share one component codebase, but to share XElement implementations, Element contracts, and cross-platform tests. When a capability can fully follow Web semantics, we prefer familiar Web APIs. Otherwise, we define a consistent **Semantic Target** from native interaction patterns and user expectations, then document platform differences and fallback behavior.

The destination is not a catalog that grows only when the official team adds a component. The Lynx team maintains a high-quality core; the community defines requirements, standards, and tests; real use drives both native implementations and higher-level components forward. Discovery, distribution, and dependency infrastructure let those results move through the ecosystem.

## From Shared Infrastructure to Agent-ready UI

The vitality of the Web ecosystem comes not only from built-in controls, but from stable primitives, shared standards, and open tools. Lynx needs the same kind of foundation: not a compromise between the Web and native platforms, but native-grade interaction with Web-grade composition, distribution, and collaboration.

As the loop closes, a capability stops being a one-off implementation and becomes an asset shared by DSLs, design systems, and products. It can also support new ways of producing interfaces. AI does not remove the need to implement components, but it raises the value of stable semantics, composition rules, and validation. The direction is not to let an Agent write more TSX, but to let it express intent through a validated UI vocabulary and turn that expression into a trustworthy cross-platform experience.

> **Agent-ready UI = Constrained Expression × Trusted Semantics × Executable Evaluation**

This is the same public foundation with a new consumer: the Engine executes, XElement absorbs platform differences, Element exposes stable contracts, lynx-ui and other DSL libraries provide interaction vocabulary, and LUNA provides visual semantics. [OpenUI](https://lynxjs.org/next/react/genui/openui.html) already lets an Agent generate expressions within a controlled vocabulary and maps them into an interface through a trusted Renderer; [lynx-ui Skills](https://lynxjs.org/4.0/ui/introduction.html) are another starting point. Next, a Component Manifest can derive implementation, types, documentation, composition constraints, compatibility data, and tests from one source of truth while driving Skills, the OpenUI Catalog, and evaluation.

A component's core assets will then include not only source code, but also machine-readable contracts, usage boundaries, and executable tests. First-pass compilation, cross-platform execution, visual and interaction results, and required human edits can tell us whether this foundation is trustworthy.

Community contribution does not only mean submitting a new component. A reproducible platform difference, a behavioral test suite, an RFC, an XElement fix, or an implementation for another DSL can all make this foundation more dependable.

We especially want to answer three questions with the community:

1. What cross-platform semantics should an Element promise, and how should XElement validate them?
2. How should component APIs and composition models reflect and drive lower-level capabilities?
3. How should tests, tooling, and contribution infrastructure open up so these capabilities can be reused by more DSLs, community components, and new UI tools?

Join or start a conversation in [Lynx GitHub Discussions](https://github.com/lynx-family/lynx/discussions), talk with us on [Discord](https://discord.com/invite/mXk7jqdDXk), and follow the latest progress on [X](https://x.com/lynxjs_org). GitHub Discussions will be the primary home for proposals, standards discussions, and the decisions that follow.

In its next stage, Lynx needs to open more than a set of proven implementations. It needs to open the complete path from requirements and standards to native implementation and component composition. What we hope to build with the community is not simply more components, but a shared cross-platform UI foundation that any DSL, product, or tool can keep using, validating, and extending.
