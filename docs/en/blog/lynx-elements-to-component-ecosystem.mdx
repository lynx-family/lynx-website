When we open-sourced Lynx, we said that many production-proven capabilities—including a richer set of UI components—were [still on their way](/blog/lynx-unlock-native-for-more#this-is-not-the-end-but-a-new-beginning). From Lynx 3.6 to the current development version, we have kept moving that work forward: bringing more native elements into the open and using [lynx-ui](/blog/lynx-ui) to turn those foundations into components that frontend developers can use directly.

This progress is beginning to close the capability gap, but it is also changing the question itself. The community no longer asks only which Elements are available. It increasingly asks what cross-platform semantics they promise, how they become product-level experiences, whether different DSLs can reuse them, and how they remain dependable as the stack evolves.

The next stage is therefore not only about shipping more Elements or more components. It is about establishing a capability path that can keep operating in the open: native capabilities can enter, cross-platform semantics can be discussed, component models can be validated, and community feedback can drive the implementation forward again.

> **Scope:** This article describes a direction for the Lynx cross-platform UI ecosystem, not a dated delivery checklist. Some capabilities are already in progress; others still need concrete designs through RFCs, implementation work, and community discussion. It also does not attempt to define a universal governance or admission model for every community component.

## The Capability Boundary Is Open—and the Question Has Changed

In Lynx, [Elements](/guide/ui/elements-components) are the basic building blocks of an interface. `<view>`, `<text>`, and `<image>` provide the most fundamental structure and expression. Scrolling, input, media playback, and overlays require deeper cooperation with each platform's native UI system.

In Lynx 3.6, the open-source stack included a small set of extended native elements, primarily `<input>`, `<textarea>`, and `<overlay>`. Since then, we have gradually brought more capabilities already running in real applications into the open:

- Lynx 3.7 introduced the [`<svg>`](/api/elements/built-in/svg) element for cross-platform native vector rendering;
- Lynx 3.8 added interaction containers such as [`<refresh>`](/api/elements/built-in/refresh) and began opening up native Markdown rendering;
- In the current development version, capabilities such as `blur-view`, `markdown`, `scroll-coordinator`, `video`, `viewpager`, and `webview` are also entering the open stack across Android, iOS, and HarmonyOS.

Together, these capabilities cover input and keyboards, independent overlay layers, vector and blur effects, refresh and complex scrolling, rich text and media, and embedded content. Many are not new experiments; they have already been exercised in real products.

But code entering a repository does not mean that a capability has fully entered an ecosystem. Platform support, stability levels, known differences, changelogs, migration paths, and automated tests determine whether developers can depend on it. **Between open code and a dependable capability lies a public semantic and maintenance commitment.**

## A Component Ecosystem Is Not an Element Wrapper

Describing a component ecosystem as “a component wrapper around an Element” assumes a linear model: the native layer first defines a complete capability, then the frontend consumes it. Real cross-platform UI does not evolve along such a one-way path.

If every product interaction becomes another native property, the Element API surface expands without bound and lower-level implementations struggle to keep pace. If platform differences, performance switches, and compatibility strategies all move into the frontend, every DSL and product team pays the same engineering cost again.

Native ownership of performance does not mean native code should define every product behavior. Frontend ownership of composition does not mean the frontend should repeatedly solve every platform difference. The ecosystem problem is therefore not “native or frontend.” It is three related questions that cannot replace one another:

1. **Execution:** Where should performance-sensitive behavior run?
2. **Semantics:** What does a cross-platform capability promise?
3. **Composition:** How do these capabilities become reusable product experiences?

## XElement × lynx-ui: From a Linear Stack to a Feedback System

### Three Boundaries: Carrier, Contract, and Composition

When we look only at where code lives, XElement, Element, and lynx-ui can appear to form a static stack. From the perspective of ecosystem responsibility, they play three different roles:

- **XElement is the Capability Carrier:** it carries capabilities that do not belong directly in the Engine but still require native-platform or main-thread integration, including their concrete implementations across Android, iOS, and HarmonyOS;
- **Element is the Semantic Contract:** it defines APIs, core behavior, cross-platform semantics, compatibility status, and fallback expectations—the boundary that different implementations and DSLs can rely on together;
- **lynx-ui is the Composition Surface:** it organizes Elements, state, and interaction into headless components for ReactLynx developers, while exposing those abstractions to validation in real product scenarios.

> **Cross-platform UI = Capability Carrier × Semantic Contract × Composition Surface**

[XElement](/guide/ui/elements-components#xelement) and [lynx-ui](https://github.com/lynx-family/lynx-ui) are therefore not a one-way stack in which one disappears behind the other. XElement expands what Lynx can express natively. lynx-ui determines how those capabilities can be used in a stable and composable way. Performance, semantic, and compatibility issues revealed by real components then drive Elements and XElements forward again.

### Overlay: From Native Capability to Component Composition

Overlay shows how this technical feedback loop works.

As part of XElement, the native `<overlay>` element solves an independent-layer rendering problem. It lets content escape the clipping and stacking constraints of the regular view tree and render in the appropriate native container. But `<overlay>` does not know what a dialog is, nor does it manage open and close state, enter and exit animation, anchor positioning, or drag-to-snap behavior.

lynx-ui first uses `OverlayView` to normalize how Overlay works across containers and platforms. From there:

- `Popover` composes anchor tracking, positioning, visibility state, and Presence;
- `Dialog` composes Trigger, Backdrop, Content, dismissal behavior, and enter and exit states;
- `Sheet` goes further by combining Overlay, Presence, main-thread gestures, and Motion to support dragging, resistance, and snap points.

This example shows that XElements and components do not have a one-to-one relationship. A stable XElement can support several higher-level components. Those components then place more concrete demands on container selection, event pass-through, lifecycle, and animation coordination, helping `<overlay>` converge on clearer cross-platform semantics.

The path is no longer only “native capability → frontend wrapper.” It becomes a loop:

> **Native capability → Component composition → Product scenario → Semantic feedback → Native capability**

### video: From Open Implementation to Shared Standards

If Overlay explains how the technical system validates itself, `video` offers an early form of how an open ecosystem can evolve together.

The API, cross-platform semantics, and compatibility expectations of `video` will be discussed and defined by the Lynx team together with the community. The Lynx team will turn that shared understanding into concrete implementations across Android, iOS, and HarmonyOS, and take responsibility for testing, releases, and long-term maintenance.

This does not mean that the collaboration model is already final. `video` is still only a starting point, but it changes how a capability enters the open ecosystem: instead of opening code only after an implementation is complete, it brings requirements, standards, implementation, and validation into the same public loop.

> **The community helps shape the standard; the Lynx team implements and maintains it over the long term.**

### Across DSLs: What We Share Is Not One Component Codebase

lynx-ui currently targets ReactLynx. It is the official component implementation and proving ground in this capability path. But the Lynx Engine and XElement are not tied to one frontend framework. As more DSLs develop on Lynx, reuse should not mean running today's lynx-ui code unchanged everywhere. It should mean that each ecosystem does not begin by solving the same platform differences from scratch.

Different DSLs can share three kinds of foundations:

- **Reusable lower-level implementations:** mechanisms such as gesture arbitration, animation drivers, overlays, focus, and keyboard handling that depend on native code or the main thread;
- **Shared behavioral contracts and tests:** even when state management and composition code differ, implementations can follow the same semantics and pass the same cross-platform assertions;
- **Thin, idiomatic wrappers:** each DSL can express component composition, context, and controlled state in the way that feels most natural to its users.

The goal of multi-DSL reuse can therefore be expressed as another three-part model:

> **Share the Capability, follow the Contract together, and let each DSL own its Composition.**

### Consistency Is Not Identical Implementation

Cross-platform consistency does not require every platform to run identical code, nor should it erase interaction expectations that have already formed on each platform.

When a capability can fully follow Web semantics, we will prefer APIs familiar to Web developers. When the Web cannot accurately express native behavior, we will start from native interaction patterns and user expectations across platforms to define a consistent **Semantic Target**. Where complete unification is not practical, we favor progressive enhancement while documenting compatibility and fallback behavior clearly.

What must remain consistent is not the implementation detail, but the core behavior that developers and users can rely on: how state changes, when events fire, where a capability is available, and how it degrades when unsupported. Those commitments must be validated both by XElement implementations across platforms and by real component compositions in lynx-ui and other DSLs.

## Agent-ready UI Is Not About Letting AI Write More Components

AI is changing where the value of a component system lives. In the era of hand-written UI, components primarily encapsulated implementations and reduced repeated code. In the era of agent-generated UI, source code itself becomes cheaper. What remains scarce is a semantic space that is explicit, constrained, executable, and verifiable.

The direction is therefore not to let AI generate more TSX, nor merely to attach a Schema to existing components. A truly **Agent-ready UI** lets an Agent express intent in a controlled UI language, then relies on validated semantic layers to compile that intent into a trustworthy cross-platform experience.

> **Agent-ready UI = Constrained Expression × Trusted Semantics × Executable Evaluation**

In this pipeline, the role of each layer becomes more focused:

- **Lynx Engine is the Runtime**, responsible for executing UI expressions that have already been made valid;
- **XElement is the Capability ISA**, absorbing platform parameters, thread constraints, version branches, and compatibility differences behind a stable native capability instruction set;
- **lynx-ui is the Interaction Standard Library**, defining states, events, composition, Focus, Keyboard, Gesture, and A11y semantics that developers and Agents can understand together;
- **LUNA is a reference implementation of Visual Semantics**, allowing products to build their own visual systems through tokens, themes, and wrappers instead of fixing appearance inside interaction components;
- **Component Manifest, OpenUI, and Skills form the Agent Control Plane**, constraining what an Agent can express, how components can be composed, and which platform, performance, and safety requirements generated results must satisfy.

This means XElement should remain focused on hard capabilities that genuinely require native implementation rather than expanding toward a product component library. lynx-ui should remain headless and composable, providing validated interaction models instead of becoming a product black box with an ever-growing list of props.

> **XElement owns Capability, not Experience.**
>
> **lynx-ui owns Experience, not fixed Appearance.**

An Agent should not face an infinitely open code space. It should work with a validated UI vocabulary and grammar. [OpenUI](https://lynxjs.org/next/react/genui/openui.html) demonstrates this possibility: an Agent generates expressions within a controlled component vocabulary, then a trusted Renderer maps those expressions into a real interface. The existing [lynx-ui Skills](https://lynxjs.org/4.0/ui/introduction.html) are another starting point. Going further, component implementations, types, documentation, AI Schemas, Skills, compatibility data, and tests should derive from one **Component Manifest**, preventing several descriptions of the same component from drifting apart over time.

The complete asset represented by a component is therefore no longer just source code. It becomes:

> **Implementation + Semantic Contract + Safety Envelope + Evaluation Data**

The way we measure ecosystem progress changes with it. Component counts and downloads still matter, but first-pass compilation rates, cross-platform execution rates, visual and interaction pass rates, the amount of human modification required, and continued validity across version upgrades describe the trustworthiness of this infrastructure more directly.

## From Open Capabilities to a Shared Ecosystem

A component ecosystem is difficult to build from a dated checklist. We prefer to describe the work ahead in three horizons. Now asks whether a capability is usable. Next asks whether people and machines can understand and maintain it together. Exploring asks whether it can continue growing beyond a single framework and be composed safely by Agents.

![XElement and lynx-ui advance together through the Now, Next, and Exploring horizons, moving from a stable core toward shared standards, more DSLs, and a community ecosystem](/assets/blog/lynx-elements-to-component-ecosystem/component-ecosystem-horizons.en.svg)

### Now: Make Capabilities Usable, Legible, and Upgradable

- Bring more production-proven XElements into the open-source stack and continue aligning behavior across Android, iOS, and HarmonyOS;
- Maintain lynx-ui core components in parallel so new native capabilities gain component entry points that frontend developers can use directly;
- Improve documentation, runnable examples, interactive previews, and platform support information on both sides;
- Improve compatibility matrices, changelogs, and migration guides, while using real component scenarios to refine Element APIs and defaults;
- Prioritize complete keyboard, focus, gesture, accessibility, performance, and edge-state behavior for frequently used complex components instead of optimizing only for component count.

### Next: Make Capabilities Definable and Maintainable Together

- Define cross-platform Element semantics and compatibility baselines;
- Improve development, integration, testing, and release standards for XElement;
- Continue refining component APIs and composition models in lynx-ui;
- Open more cross-platform test infrastructure and contribution workflows, while gradually making performance, memory, and accessibility part of a verifiable quality baseline;
- Explore a unified Component Manifest so types, documentation, Skills, the OpenUI Catalog, composition constraints, tests, and version compatibility checks derive from one source of truth.

### Exploring: Let Capabilities Grow Across Framework Boundaries

- Explore discovery, distribution, and dependency resolution for XElements and frontend components;
- Continue moving shareable, framework-independent behavior lower in the stack;
- Let more DSLs reuse the same XElements, behavioral specifications, and test suites;
- Lower the barrier for the community to build native extensions, industry components, and design systems;
- Build AI evaluation across generation, compilation, cross-platform execution, interaction, and visual results, while exploring AI interaction primitives such as Streaming, Approval, Tool Call, Citation, Undo, Retry, and Partial Failure.

These horizons are not three stages of one-way delivery from the official team to the community. As the feedback among standards, implementations, components, and real needs becomes stronger, the community can participate earlier in capability evolution, while the Lynx team can take clearer responsibility for implementation and long-term maintenance.

## From Repeated Engineering Cost to Shared Infrastructure

The vitality of the Web ecosystem has never come only from how many controls browsers ship. It comes from stable primitives, shared standards, open tools, and the space for anyone to keep building. The Lynx component ecosystem needs that same foundation while preserving the distinct value of native rendering, cross-platform delivery, and low-latency interaction.

![Cross-industry needs, the XElement native extension ecosystem, lynx-ui and more DSLs, and community reuse form a cross-platform UI flywheel around shared Element semantics, behavior, compatibility, and tests](/assets/blog/lynx-elements-to-component-ecosystem/cross-platform-ui-commons.en.svg)

As this loop closes, a native capability or component no longer remains a one-off implementation owned by one platform, framework, or product team. It can be expressed through different DSLs, composed into different design systems, and preserve consistent user semantics across platforms. Cross-platform native UI can move from an engineering cost repeatedly paid by every team to shared infrastructure accumulated by the whole ecosystem.

The Lynx team will continue to take responsibility for implementing and maintaining core XElement and lynx-ui capabilities over the long term, while opening more specifications, tests, and tools. The community can participate earlier in discussions about requirements, APIs, cross-platform semantics, and testing standards, then build native extensions, industry components, and design systems on the shared foundation.

We especially want to answer three questions with the community:

1. What cross-platform semantics should an Element promise, and how should XElement validate them?
2. How should component APIs and composition models reflect and drive lower-level capabilities?
3. How should tests, tooling, and contribution infrastructure open up so these capabilities can be reused by more DSLs and community components?

Join or start a conversation in [Lynx GitHub Discussions](https://github.com/lynx-family/lynx/discussions), talk with us on [Discord](https://discord.com/invite/mXk7jqdDXk), and follow the latest progress on [X](https://x.com/lynxjs_org). GitHub Discussions will be the primary home for proposals, standards discussions, and the decisions that follow.

In its next stage, Lynx needs to open more than a set of proven implementations. It needs to open the complete evolution path from requirements and standards to native implementation and component composition. XElement lets native capabilities enter the open. Element turns cross-platform semantics into a public contract that can be discussed. lynx-ui brings those capabilities into real components and product scenarios. LUNA allows products to own visual semantics. OpenUI and Skills let Agents use those standards within controlled boundaries.

AI will make hand-written component source less scarce, while making stable semantics, composition rules, safety boundaries, and evaluation data significantly more valuable. Our goal is no longer only to provide more XElements or more components. It is to work with the community to define a public cross-platform UI language that Agents, developers, and the Runtime can all understand and trust.

When this system exists, an Agent no longer produces interface code that happens to run. It produces a UI expression that can be compiled, validated, executed across platforms, and evolved over time. That is the real meaning of Agent-ready UI.
