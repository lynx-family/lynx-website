**Lynx 4.2 is here!** Because Lynx 4.1 and 4.2 were released close together, we are not publishing a separate 4.1 release blog. This post covers the highlights of **both releases** since [Lynx 4.0](/blog/lynx-4-0).

This time, the focus is control: organize style precedence with CSS Cascade Layers, adapt styles to supported capabilities and changing color preferences, decide when ReactLynx hands over the first screen, and investigate memory across a page's lifetime. There are also improvements to images, text, scrolling, and host integration.

## CSS with More Predictable Behavior

### Organize Styles with Cascade Layers

As a design system grows, application overrides can turn into a contest of increasingly specific selectors. CSS `@layer` lets you decide the order of groups of styles first, rather than expressing every override through selector specificity.

For example, this card keeps the component's background but takes its padding from the utilities layer:

```css
@layer reset, base, components, utilities;

@layer components {
  .card {
    padding: 16px;
    background-color: #e8f4ff;
  }
}

@layer utilities {
  .compact {
    padding: 8px;
  }
}
```

```tsx
<view className="card compact">
  <text>A compact card with 8px padding</text>
</view>
```

With [cascade-layer ordering](https://github.com/lynx-family/lynx/pull/8209), a later layer wins over an earlier one for normal declarations; specificity and source order still matter within the same layer. Normal declarations outside layers take precedence over layered declarations. For `!important` declarations, the layer order is reversed. Named, anonymous, and nested layers are supported.

Cascade layers and the conditional rules below require compatible build tooling and CSS Rule encoding. Add this plugin to your existing build configuration, alongside the project's Lynx and ReactLynx plugins:

```js
import { pluginLynxConfig } from '@lynx-js/config-rsbuild-plugin';

pluginLynxConfig({
  enableCSSRule: true,
});
```

This is an opt-in encoding path, not a change automatically applied to every previously built template. See the [CSS Rule configuration example](/api/css/media-query#enable-css-rule-encoding).

### Apply Styles Conditionally

`@supports` adds declaration checks, engine-version range conditions, and combinations using `not`, `and`, and `or`. You can keep a fallback layout and enable an alternative when its CSS declaration is supported:

```css
.tiles {
  display: flex;
  flex-direction: column;
}

@supports (display: grid) {
  .tiles {
    display: grid;
    grid-template-columns: 1fr 1fr;
  }
}
```

On a supporting runtime, two children of `.tiles` use two grid columns instead of a vertical stack. A declaration check tests the engine's CSS parser; it does not detect whether a host has installed an optional native service. Unsupported function conditions and unknown condition forms conservatively evaluate to false.

Building on the [media queries introduced in 4.0](/blog/lynx-4-0#css-media-queries), hosts can also update the runtime's light/dark preference and trigger reevaluation of `prefers-color-scheme` without rebuilding the page. The existing media-query example shows the corresponding rules:

### Layout Defaults Closer to the Web

With `targetSdkVersion >= 4.1`, grid placement shorthands (`grid-column` and `grid-row`) and a `0%` basis when omitted from the `flex` shorthand are enabled by default. These capabilities were previously introduced behind configuration; this update changes their target-SDK defaults. Explicitly setting `enableGridPlacementShorthands` or `enableFlexBasisZeroPercent` to `false` still overrides the default.

When raising your target SDK, check layouts that depend on grid placement or the difference between a zero length and a percentage flex basis.

## Text and Scrolling

### Fine-Tune Text Decorations

On the **Android and iOS TextService** rendering path, three properties give decorated text more precise styling:

- `text-decoration-thickness` controls line thickness.
- `-x-text-decoration-width` controls dash length or the period of a wave.
- `-x-text-decoration-gap` controls the spacing between dashes or dots.

The existing text-decoration example provides a starting point:

```css
.annotation {
  text-decoration-line: underline;
  text-decoration-style: dashed;
  text-decoration-color: #1479ff;
  text-decoration-thickness: 2px;
  -x-text-decoration-width: 8px;
  -x-text-decoration-gap: 4px;
}
```

These extensions require TextService. Do not assume identical support on the native text-rendering path.

### Swipe across More List Items

A snapping list need not advance just one item per gesture. On Android and iOS, `item-snap` adds `maxSnapCount` to let a quick swipe move across several items. The default remains `1`, preserving the previous behavior.

Start with the existing horizontal snapping example:

Item-based snapping also comes to `<scroll-view>`, giving hosts another option for paginated scrolling.

## ReactLynx

### Choose When the First Screen Is Ready

[Instant First-Frame Rendering](/guide/interaction/ifr) lets the main thread render before the background runtime is ready. For pages whose critical data arrives in several batches, ReactLynx now lets the application explicitly decide when to hand the first-screen tree over to the background thread:

```js
import { pluginReactLynx } from '@lynx-js/react-rsbuild-plugin';

pluginReactLynx({
  firstScreenSyncTiming: 'manual',
});
```

Once the application's critical first-screen data is ready, call the [ready API](/api/react/Functions/markFirstScreenSyncReady):

```ts
import { markFirstScreenSyncReady } from '@lynx-js/react';

// Call from the application's first-screen data-ready path.
markFirstScreenSyncReady();
```

Before synchronization, the main thread can continue to handle host `updateData` calls synchronously. The handover happens only after **both** the ready signal and the current first-screen render have completed. The API works from either thread and repeated calls have no further effect.

:::warning Always send the ready signal

In manual mode, your data-ready path must call `markFirstScreenSyncReady()`, including any intended fallback for failed data requests. Otherwise background-thread hydration, and event handling that depends on it, remain unavailable. Do not wait for such an event handler to send the initial ready signal.

:::

This is a companion framework feature, available from `@lynx-js/react@0.123.0` and `@lynx-js/react-rsbuild-plugin@0.18.0`. ReactLynx package versions are independent of the engine SDK; upgrading Lynx alone does not update them.

### Load Bundles on Demand, with Source-Level Debugging

ReactLynx's lazy loading integrates with [`lynx.fetchBundle`](/react/code-splitting), while the corresponding SourceMap improvements preserve source-level debugging for lazy bundles. Configure `pluginReactLynx({ engineVersion: '3.9' })` or a later supported engine version to use this loading path; lower configurations retain the previous `QueryComponent` path.

## Lynx API

The host-facing updates are focused on integration and inspection:

- **SVG image-service hooks.** The image-service interfaces add [Android `fetchSVGImage`](https://github.com/lynx-family/lynx/pull/8104) and [iOS `loadSVGImageWithURL`](https://github.com/lynx-family/lynx/pull/8184) extension points. These are integration hooks for image-service implementers, not a bundled SVG decoder.

- **Logical element-tree queries.** Android, iOS, and HarmonyOS add LynxElement node queries and parent/child access; Android and iOS also expose associated platform views. The logical element tree is not the same as the native view hierarchy.
- **More native Autolink coverage.** Building on [Native Libraries and Autolink](/guide/autolink), Android and iOS add Node-API addon integration, while HarmonyOS adds global-library integration. Use matching SDK and platform-tooling versions.
- **HarmonyOS host APIs.** Native modules can declare synchronous-return methods with `static syncMethods`. `LynxContext.getPageDataByKeyAsync` reads page data asynchronously by key, and `LynxViewClient.onIntrinsicContentSizeChange` reports intrinsic content-size changes. Synchronous methods wait for the UI thread and should not perform expensive work.
- **`Promise.allSettled`.** Lynx Promise adds `allSettled` to wait for every asynchronous operation to finish and handle each fulfillment value or rejection reason without failing the whole group on the first rejection.

### TemplateBundle Preloading

Lynx 4.2 adds [`TemplateBundle.preload`](https://github.com/lynx-family/lynx/pull/9979) on Android, iOS, and HarmonyOS. It asynchronously loads LepusNG bytecode into pre-created main-thread runtimes, moving this preparation ahead of page use.

The order matters: disable context auto-refill, create all required contexts, then request preload. Once preload is accepted, do not create additional contexts. The completion callback runs on the preload worker thread; marshal any UI work to the appropriate thread. This prepares runtime state—it does not download all page resources.

Check whether the preload request was accepted. The success callback runs only after all pre-created runtimes finish loading; it is not called if validation or loading fails.

## DevTool

### Follow Memory across a Page's Lifetime

Trace expands its existing memory analysis with process physical-memory data and events for main-thread script (MTS) and background-thread script (BTS) VMs and runtime pools. It also accepts Trace configuration from DevTool, supports garbage-collection controls during recording, and can capture VM snapshots by URL. Available tracks and controls depend on the platform and Trace configuration.

For example, when investigating a page that appears to retain memory:

1. Record entry, several representative updates, and exit in one Trace.
2. Compare page lifetime and VM/runtime-pool events with the memory trend.
3. Capture snapshots around the suspicious interval to investigate retained objects.

A high point on a memory curve alone does not establish a leak; runtime pooling and normal object lifetimes also matter. See the [memory analysis guide](/guide/performance/analysis-performance/analysis-memory) for the existing workflow and the companion [Lynx Trace tools](https://github.com/lynx-family/lynx-trace).

Android also adds [`LynxView.takeBTSHeapSnapshot`](https://github.com/lynx-family/lynx/pull/8704), which writes a QuickJS background-script heap snapshot to a file and reports success or failure on a background thread. Supply an absolute output path with an existing parent directory; an existing file is replaced.

### Inspect Conditional Styles

With a matching DevTool version, the Styles panel adds `@media` inspection and `@supports` inspection and editing, making it easier to understand which conditional rules apply. Supported Android, iOS, and desktop screenshot requests can also select PNG; JPEG remains the default.

## Get Started with Lynx 4.2

Follow [Integrate with Existing Apps](/guide/start/integrate-with-existing-apps) for your platform and select matching Lynx, PrimJS, services, and tooling versions. The Lynx 4.2.0 release uses PrimJS 4.2.1; companion dependencies do not necessarily share the same version number.

Before upgrading an existing host, check these integration changes:

| Area                          | What to check                                                                                                                                                                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| iOS / AnimaX                  | Use the `XElement/AnimaX` element dependency. Update the dependency declaration if your integration still uses `Lynx/AnimaX`.                                                                                                                    |
| Android / LynxElement         | Replace `com.lynx.tasm.LynxElement` with `com.lynx.tasm.element.LynxElement`; migrate named callback implementations to `LynxElementCallback`.                                                                                                   |
| HarmonyOS / image redirection | Migrate `shouldRedirectUrlAsync` callbacks to `AsyncCallback<LynxRedirectCallbackResult>`. Return a string or a structured `LynxRedirectResult` with `url` and optional `fallbackUrls` / `fileCacheName`, rather than the previous array result. |
| Page target SDK / layout      | Recheck grid and flex layouts when raising `targetSdkVersion` to 4.1 or later.                                                                                                                                                                   |

For complete engine changes and patch availability, consult the [Lynx 4.2.0 release notes](https://github.com/lynx-family/lynx/releases/tag/4.2.0). Thank you to everyone contributing code, reporting issues, and sharing examples—we look forward to seeing what you build with Lynx 4.2!
