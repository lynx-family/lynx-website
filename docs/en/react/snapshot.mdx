# Snapshot Compilation Optimization

Snapshot is first and foremost a **compile-time optimization**. The ReactLynx compiler analyzes JSX ahead of time, turns predictable element structures into code that directly creates Lynx elements, and generates dedicated update logic for dynamic properties and children. At runtime, ReactLynx only needs to instantiate the compiled result and pass in dynamic values instead of interpreting the complete JSX structure again.

:::info

Snapshot is unrelated to snapshot testing or the `getSnapshotBeforeUpdate()` method on React class components. It is an internal ReactLynx implementation detail. Application code should continue to use regular JSX and should not create or manipulate Snapshots directly.

:::

## Why Snapshot

### Runtime Cost of Regular JSX

A regular JSX transform keeps element structure, static values, and dynamic expressions in the runtime output. Whenever the UI is created or updated, the runtime creates element descriptions, reconciles host elements level by level, and applies property and child changes to the UI.

The following component contains both a static structure and dynamic content:

```tsx
export function Greeting({ name, highlighted }) {
  return (
    <view className={highlighted ? 'card active' : 'card'}>
      <text>Hello, {name}</text>
    </view>
  );
}
```

With a regular JSX transform and no Snapshot extraction, the compiled result is semantically similar to the following code:

```js
export function Greeting({ name, highlighted }) {
  return _jsx('view', {
    className: highlighted ? 'card active' : 'card',
    children: _jsx('text', {
      children: ['Hello, ', name],
    }),
  });
}
```

This output retains the complete `view` and `text` element hierarchy. Every render creates this element description again, and the runtime reconciles the complete hierarchy. As a page grows, the cost of level-by-level reconciliation becomes more noticeable, while element descriptions and node state also consume more memory.

The ReactLynx compiler can complete work that does not depend on runtime data ahead of time:

- Determine the types, hierarchy, and insertion order of built-in elements.
- Extract fixed text, static properties, and CSS scope information.
- Locate dynamic properties, spread properties, and dynamic children.
- Generate a targeted update function for each dynamic part.

Together, these compiled results form a Snapshot definition.

### Compiling JSX into a Snapshot

For the `Greeting` component above, the ReactLynx compiler separates the following parts at build time:

- **Static structure**: `view`, `text`, and the fixed text `Hello, `.
- **Dynamic property**: the `className` determined by `highlighted`.
- **Dynamic child**: the text generated from `name`.

The compiler then combines the static creation logic, dynamic update functions, and slot locations into a reusable Snapshot definition and generates a Snapshot ID for it. At runtime, this definition is used to create Snapshot instances, with each instance providing only its own dynamic values and children.

More specifically, a Snapshot definition has four parts:

| Compiled result     | Purpose                                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| Static creator      | Directly creates predictable Lynx elements and establishes their parent-child relationships.              |
| Dynamic updaters    | Updates a property, event, or spread property by index without traversing the complete static structure.  |
| Dynamic child slots | Marks where dynamic subtrees such as components, conditional branches, text expressions, and lists go.    |
| Snapshot ID         | Identifies the compiled structure so that multiple component instances can reuse one Snapshot definition. |

Compiling this component with the current ReactLynx compiler produces code similar to the following:

```js
const __snapshot_a721c_e4779_1 = '__snapshot_a721c_e4779_1';

ReactLynx.snapshotCreatorMap[__snapshot_a721c_e4779_1] = (
  __snapshot_a721c_e4779_1,
) =>
  ReactLynx.createSnapshot(
    __snapshot_a721c_e4779_1,
    () => {
      const pageId = ReactLynx.__pageId;
      const view = __CreateView(pageId);
      const text = __CreateText(pageId);
      const rawText = __CreateRawText('Hello, ');
      const slot = __CreateWrapperElement(pageId);

      __AppendElement(view, text);
      __AppendElement(text, rawText);
      __AppendElement(text, slot);

      return [view, text, rawText, slot];
    },
    [
      function (ctx) {
        if (ctx.__elements) {
          __SetClasses(ctx.__elements[0], ctx.__values[0] || '');
        }
      },
    ],
    [[ReactLynx.__DynamicPartSlotV2, 3]],
  );

export function Greeting({ name, highlighted }) {
  return _jsx(__snapshot_a721c_e4779_1, {
    values: [highlighted ? 'card active' : 'card'],
    $0: name,
  });
}
```

:::warning

`createSnapshot`, `snapshotCreatorMap`, the global element operation functions, and generated Snapshot IDs are internal implementation details. Their names and parameters may change with the source code, compiler configuration, or ReactLynx version. Do not depend on or copy these outputs in application code.

:::

With this compilation optimization, a multi-level host structure that would otherwise participate in reconciliation level by level is compressed into a single Snapshot unit. The more complex the page and the more structure that can be determined statically, the more pronounced the reduction in reconciliation scale becomes. This compression applies to the runtime reconciliation hierarchy; Snapshot still creates the complete Lynx element tree on the main thread.

### How Snapshot Drives Rendering

A Snapshot definition is a reusable description generated by the compiler. A SnapshotInstance is one runtime instantiation of that definition. In ReactLynx's dual-thread architecture, the same logical Snapshot has a separate runtime object on each thread:

| Thread            | Runtime object               | Responsibility                                                                                                                                                                                                                           |
| ----------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Background thread | `BackgroundSnapshotInstance` | Acts as the host-layer node for Preact reconciliation; stores the Snapshot ID, dynamic values, and child relationships; compares dynamic values and records serializable patches for creation, insertion, removal, and property updates. |
| Main thread       | `SnapshotInstance`           | Uses the Snapshot definition to create and own real Lynx FiberElements during initial rendering or when applying subsequent patches; runs targeted update functions and inserts dynamic children into their slots.                       |

When the background thread commits an update, it sends the instance ID, operation type, and required dynamic data to the main thread. The main thread uses the instance ID to find the corresponding `SnapshotInstance` and apply the operation. The two objects therefore represent the same logical UI unit, but they are not the same JavaScript object and do not access each other through shared memory.

This division of work makes both reconciliation and element operations Snapshot-based. The compiled `_jsx(snapshotId, props)` no longer expands the complete host element hierarchy for the runtime. During React reconciliation on the background thread, the compiled structure corresponds to one `BackgroundSnapshotInstance`. The matching `SnapshotInstance` on the main thread executes the static creator and expands it into real FiberElements.

In the `Greeting` example, the main-thread `SnapshotInstance` contains the FiberElements for `view`, `text`, the fixed text, and the slot. In the background-thread reconciliation tree, however, the statically predictable `view → text → Hello, ` hierarchy does not need to be processed as individual host nodes. One `BackgroundSnapshotInstance` represents the hierarchy, and only the `name` associated with `$0` continues to participate in reconciliation as a dynamic child.

| Scenario                 | Processing host elements individually                                       | After compiling to Snapshot                                                                                                                    |
| ------------------------ | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Creating the UI          | Reconcile `view`, `text`, text, and their relationships level by level.     | Reconcile one `BackgroundSnapshotInstance`; its matching `SnapshotInstance` creates the FiberElements on the main thread.                      |
| `highlighted` changes    | Determine which element and property correspond to the dynamic value again. | Compare `values[0]` on the background thread, generate a patch, and directly update `className` on the root FiberElement.                      |
| `name` changes           | Process the host subtree containing both fixed and dynamic text.            | Keep the fixed text inside the main-thread instance; only the dynamic slot for `$0` participates in reconciliation and produces a child patch. |
| Rendering many instances | Carry and process the same host element structure for every instance.       | Represent each logical instance with a lightweight pair of runtime objects while sharing one Snapshot definition.                              |

The most direct change is that the runtime no longer needs to understand how to create and update this JSX structure. Instead, it executes compiler-prepared operations around Snapshot instances. The background thread folds the reconciliation hierarchy formed by multiple static host nodes into one `BackgroundSnapshotInstance`, while the corresponding main-thread `SnapshotInstance` materializes the compiled result as FiberElements. Reconciliation is therefore limited to Snapshot instances and their dynamic slots.

:::note

Snapshot reduces the reconciliation scale at the host-element level; it does not bypass React reconciliation. Components, conditional branches, lists, and dynamic children still participate in reconciliation normally. Snapshot only folds host element structures that the compiler can determine statically.

:::

## Writing Compiler-Friendly JSX

The compiler applies Snapshot optimization automatically; it does not need to be enabled manually. When writing JSX, keep host element types, hierarchy, and insertion order clearly visible in the source, and concentrate runtime data in property and child expressions. The compiler can then extract the former into a static skeleton and turn the latter into targeted update functions or dynamic slots.

### Dynamic Values Do Not Prevent Static Structure Extraction

In the following component, the `view → text` hierarchy remains unchanged. Only `className` and the text content are dynamic:

```tsx
function UserCard({ name, selected }) {
  return (
    <view className={selected ? 'user-card selected' : 'user-card'}>
      <text className="user-name">{name}</text>
    </view>
  );
}
```

The compiler can separate this JSX into:

- **Static structure**: `view`, `text`, and their parent-child relationship.
- **Static property**: `user-name` on the `text` element.
- **Dynamic positions**: `className` on the card and the text child generated from `name`.

There is no need to create different components for different combinations of `name` and `selected`. Keep the host structure stable and pass data through expressions.

### Keep Shared Structure Outside Conditional Branches

The following code duplicates the entire card structure in both branches:

```tsx
function ProductCard({ name, price, showPrice }) {
  if (showPrice) {
    return (
      <view className="product-card">
        <text className="product-name">{name}</text>
        <text className="product-price">{price}</text>
      </view>
    );
  }

  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
    </view>
  );
}
```

Keep one stable shell and make only the price region a dynamic slot:

```tsx
function ProductCard({ name, price, showPrice }) {
  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
      {showPrice && <text className="product-price">{price}</text>}
    </view>
  );
}
```

When `showPrice` changes, React only needs to reconcile the dynamic region for the price, while the card shell can be reused. If the two branches represent genuinely different interfaces, do not force them into one structure; clear branches are more important.

### Declare Host Element Types Explicitly

The Snapshot compiler analyzes JSX structures. When a string and `createElement()` determine the host element type at runtime, the compiler cannot determine that structure ahead of time:

```tsx
import { createElement } from '@lynx-js/react';

function DynamicNode({ type, value }) {
  return createElement(type, { className: 'content' }, value);
}
```

If the candidate structures are known during development, write explicit JSX branches:

```tsx
function Content({ variant, value }) {
  if (variant === 'label') {
    return <text className="content-label">{value}</text>;
  }

  return (
    <view className="content-panel">
      <text>{value}</text>
    </view>
  );
}
```

Runtime data still selects the branch, but the host structure of each branch is visible to the compiler, so each can produce its own Snapshot. Use dynamic creation only when the host type genuinely comes from runtime configuration.

### Prefer Explicit Properties for Fixed Property Sets

Snapshot supports spread attributes, but the compiler records the entire spread object as one dynamic property set. During an update, the runtime must compare the properties in that set before applying changes to the corresponding element:

```tsx
function UserCard({ id, name, selected }) {
  const cardProps = {
    id,
    className: selected ? 'user-card selected' : 'user-card',
  };

  return (
    <view {...cardProps}>
      <text>{name}</text>
    </view>
  );
}
```

When the property set is known during development, declaring properties explicitly is preferable:

```tsx
function UserCard({ id, name, selected }) {
  return (
    <view id={id} className={selected ? 'user-card selected' : 'user-card'}>
      <text>{name}</text>
    </view>
  );
}
```

The explicit form tells the compiler exactly which dynamic position corresponds to `id` and which corresponds to `className`, allowing it to generate targeted update logic for each property. It also avoids creating a `cardProps` object on every render. Spread remains appropriate when a component needs to forward unknown properties supplied by its caller; do not expand them one by one solely for Snapshot.
