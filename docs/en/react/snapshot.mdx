# Compiler-Informed Rendering

ReactLynx analyzes JSX at build time and extracts statically known host structures so that the runtime can focus on the parts that may change. In most applications, you can continue writing regular, idiomatic JSX.

The current compiler records the extracted structure and its dynamic positions in a compiled representation called a **Snapshot**. Conceptually, this can be loosely understood as a form of structural constant folding: host elements and values known at build time are folded into one reusable representation, while dynamic values and subtrees remain as its inputs.

```tsx
// Before folding
<view>
  <view className={cls}>
    <view style={{ backgroundColor: 'red' }} />
  </view>
  <text>{t}</text>
  <text>Hello World!</text>
  <Comp1 />
  {flag && <view className="optional" />}
</view>;

// After folding (conceptual output)
<__snapshot_0x1
  __0={cls}
  __1={t}
  __2={<Comp1 />}
  __3={flag && <__snapshot_0x2 />}
/>;
```

The exact generated names differ, but the shape illustrates the important boundary: the stable host hierarchy is part of the compiled representation, while `cls`, `t`, the component subtree, and the conditional subtree remain dynamic inputs.

:::info

Snapshot is unrelated to snapshot testing or the `getSnapshotBeforeUpdate()` method on React class components. It is the current internal compiled representation used by ReactLynx, not the optimization itself. You do not need to create or manipulate Snapshots directly.

:::

## Writing Compiler-Friendly JSX

Compiler-informed rendering is applied automatically. For most components:

- Prefer clear and idiomatic JSX.
- Let runtime data flow through properties and children as usual.
- Keep component semantics and readability ahead of compiler optimization.

Dynamic properties, text, and children do not prevent static extraction by themselves. When host element types, hierarchy, and insertion order are naturally visible in JSX, the compiler can extract the stable structure and record the expressions as dynamic positions. There is no need to split a component merely to make its properties or text values static.

The following sections explain additional patterns and the underlying mechanism. These patterns are not hard rules; use them only when they preserve the intended component structure.

## How Compiler-Informed Rendering Works

### Why Move Rendering Work to Build Time

A regular JSX transform keeps the element structure, static values, and dynamic expressions in the runtime output. On every render, `_jsx()` creates virtual nodes (VNodes) that describe the UI structure. The ReactLynx reconciler then compares these nodes level by level to decide which host elements to reuse, create, or update. This process is known as reconciliation.

The following component contains both a static structure and dynamic content:

```tsx
export function Greeting({ name, highlighted }) {
  return (
    <view className={highlighted ? 'card active' : 'card'}>
      <text>Hello, {name}</text>
    </view>
  );
}
```

With a regular JSX transform and no static extraction, the compiled result is semantically similar to the following code:

```js
export function Greeting({ name, highlighted }) {
  // view and text still correspond to separate host VNodes.
  return _jsx('view', {
    className: highlighted ? 'card active' : 'card',
    children: _jsx('text', {
      children: ['Hello, ', name],
    }),
  });
}
```

This output still represents the complete host hierarchy with separate `view` and `text` VNodes. Even if the reconciler ultimately reuses the corresponding host elements, every render creates these VNodes again and sends the complete `view → text` hierarchy through reconciliation. Only `className` and `name` can actually change; the element types, hierarchy, and parent-child relationships remain fixed.

These stable structures are exactly what the compiler can extract ahead of time.

### How JSX Lowers to the Snapshot Representation

With static extraction enabled, the call site for the same component is semantically similar to the following code:

```js
const __snapshot_xxx = '__snapshot_xxx';

export function Greeting({ name, highlighted }) {
  // The static host hierarchy is folded into one compiled representation.
  return _jsx(__snapshot_xxx, {
    values: [highlighted ? 'card active' : 'card'], // Dynamic property position 0
    $0: name, // Dynamic child slot 0
  });
}
```

The difference between the two outputs is that the regular output expands the complete host VNode hierarchy, while the compiled output only references a Snapshot ID and passes `className` and `name` into predefined dynamic positions.

The compiler can therefore determine built-in element types, hierarchy, and insertion order ahead of time; extract fixed text, static properties, and CSS scope information; and locate dynamic properties, spread properties, and dynamic children. For the `Greeting` component, these parts are:

- **Static structure**: `view`, `text`, and the fixed text `Hello, `.
- **Dynamic property**: the `className` determined by `highlighted`.
- **Dynamic child**: the text generated from `name`.

Finally, the compiler records the static creation logic, dynamic update functions, slot locations, and a Snapshot ID in the current Snapshot representation. The runtime uses this compiled definition to create instances and only supplies each instance's own dynamic values and children.

### What the Current Snapshot Representation Contains

The current Snapshot representation has four core parts:

| Compiled result     | Purpose                                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| Static creator      | Directly creates predictable Lynx elements and establishes their parent-child relationships.              |
| Dynamic updaters    | Updates a property, event, or spread property by index without traversing the complete static structure.  |
| Dynamic child slots | Marks where dynamic subtrees such as components, conditional branches, text expressions, and lists go.    |
| Snapshot ID         | Identifies the compiled structure so that multiple component instances can reuse one Snapshot definition. |

The Snapshot ID above refers to a compiled definition generated at build time. From a compiler perspective, lowering this representation into direct element operations can be understood as a form of partial evaluation: ReactLynx specializes the generic rendering process with the host structure known from JSX, leaving only dynamic values and subtrees to be processed at runtime.

The simplified example below preserves the static creator, dynamic updater, and slot information that illustrate the compiled structure, while omitting compiler metadata for CSS, entry points, and compatibility.

<details>
<summary>View a simplified Snapshot definition</summary>

```js
ReactLynx.snapshotCreatorMap[__snapshot_xxx] = (__snapshot_xxx) =>
  ReactLynx.createSnapshot(
    __snapshot_xxx,
    () => {
      // This part only depends on structure that is statically known in JSX.
      const pageId = ReactLynx.__pageId;
      const view = __CreateView(pageId);
      const text = __CreateText(pageId);
      const rawText = __CreateRawText('Hello, ');
      const slot = __CreateWrapperElement(pageId); // Reserve an insertion point for $0

      __AppendElement(view, text);
      __AppendElement(text, rawText);
      __AppendElement(text, slot);

      // Updaters and slot descriptors locate elements through these array indexes.
      return [view, text, rawText, slot];
    },
    [
      function (ctx) {
        if (ctx.__elements) {
          // values[0] only updates elements[0], the root view.
          __SetClasses(ctx.__elements[0], ctx.__values[0] || '');
        }
      },
    ],
    [[ReactLynx.__DynamicPartSlotV2, 3]], // $0 corresponds to elements[3]
  );
```

</details>

:::warning

The `$0` and `__DynamicPartSlotV2` representation shown here reflects `@lynx-js/react` 0.120.0 or later. `createSnapshot`, `snapshotCreatorMap`, the global element operation functions, and generated Snapshot IDs are internal implementation details. Their names and parameters may change with the source code, compiler configuration, or ReactLynx version. Do not depend on or copy these outputs in application code.

:::

### How the Compiled Output Enters the Runtime

The compiled Snapshot definition can be reused by multiple `Greeting` components, while every rendered `Greeting` creates a pair of corresponding runtime instances: the main-thread instance owns the Lynx elements it creates, and the background-thread instance stores the logical tree and dynamic data used for reconciliation. The runtime consumes the compiled output in two stages: the initial render and subsequent updates.

#### Initial render: Create an instance from the definition

The UI elements for the initial render are created directly on the main thread. The runtime first looks up the Snapshot definition from the VNode type, then creates a main-thread instance for this `Greeting`. The instance owns the Lynx elements returned by the static creator. Initial dynamic values are passed to their corresponding updaters, and dynamic children are inserted into the slots defined by the compiler.

The following pseudocode illustrates this process:

```js
function renderFirstScreen(vnode) {
  const definition = getSnapshotDefinition(vnode.type);
  const instance = createMainThreadSnapshotInstance(vnode.type);

  instance.__elements = definition.create(instance);
  instance.__values = vnode.props.values;
  definition.update[0](instance); // Write values[0] to className
  insertDynamicChild(instance, 0, vnode.props.$0);

  return instance;
}
```

In this example, `definition.create()` creates the `view`, `text`, and fixed text; `definition.update[0]()` writes `values[0]` to `className`; and `insertDynamicChild()` places the `name` from `$0` into the reserved slot. This still creates the complete Lynx element tree. The difference is that `definition.create()` expands the static hierarchy directly instead of sending every host VNode through reconciliation level by level.

The initial background-thread reconciliation also creates a logical instance tree that corresponds to the main-thread instance tree. During first-screen synchronization, hydration establishes the mapping between the instances on the two threads, allowing subsequent updates to locate the main-thread instance created for the first screen by `instanceId`.

#### Updates: Apply changes through the instance mapping

After the mapping is established, the background thread compares old and new dynamic data and generates updates. The main thread then finds the corresponding runtime instance and applies each update.

The following pseudocode continues with `Greeting`. `highlighted` corresponds to dynamic position `0`, so changing it produces a property update. `name` is in a dynamic child slot and continues to be reconciled by React:

```js
// Background thread: compare dynamic properties and reconcile dynamic children
function reconcileGreeting(previous, next, instanceId) {
  if (!isEqual(previous.values[0], next.values[0])) {
    emitAttributePatch({
      instanceId,
      dynamicPartIndex: 0,
      value: next.values[0],
    });
  }

  // $0 remains a React child.
  // Reconciliation produces tree operations such as insertions and removals.
  reconcileChildren(previous.$0, next.$0, {
    parentInstanceId: instanceId,
    slotIndex: 0,
  });
}

// Main thread: apply a property update using the instance and dynamic position
function applyAttributePatch(patch) {
  const instance = findSnapshotInstance(patch.instanceId);
  const index = patch.dynamicPartIndex;

  instance.__values[index] = patch.value;
  instance.definition.update[index](instance);
}
```

For the property path, `reconcileGreeting()` only describes which dynamic position changed on which instance. `applyAttributePatch()` then finds the main-thread instance and calls the update function generated by the compiler. Dynamic children do not pass through these property updaters; React reconciliation produces the corresponding tree operations instead. The implementation encodes these operations in a serialized Snapshot Patch.

## Additional Optimization Patterns

### Keep Shared Structure Visible When It Is Natural

The following code duplicates the entire card structure in both branches:

```tsx
function ProductCard({ name, price, showPrice }) {
  if (showPrice) {
    return (
      <view className="product-card">
        <text className="product-name">{name}</text>
        <text className="product-price">{price}</text>
      </view>
    );
  }

  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
    </view>
  );
}
```

When both branches naturally represent the same component structure, you can keep one stable shell and make only the price region a dynamic slot:

```tsx
function ProductCard({ name, price, showPrice }) {
  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
      {/* Only the price region changes structure with showPrice. */}
      {showPrice && <text className="product-price">{price}</text>}
    </view>
  );
}
```

The second form can make the shared shell more visible to the compiler and keep only the price region as a dynamic slot. Do not restructure conditional rendering solely for static extraction: different forms may affect component identity, state preservation, and readability.

### Declare Host Element Types Explicitly

The compiler can only analyze JSX structures that are visible in the source. If a string and `createElement()` determine a host element type at runtime, that part of the structure cannot be determined ahead of time and therefore cannot be statically extracted:

```tsx
import { createElement } from '@lynx-js/react';

function DynamicNode({ type, value }) {
  // type does not have a concrete value until runtime,
  // so the compiler cannot see the host type.
  return createElement(type, { className: 'content' }, value);
}
```

If the candidate structures are known during development, write explicit JSX branches:

```tsx
function Content({ variant, value }) {
  // Both candidate host types appear directly in JSX.
  if (variant === 'label') {
    return <text className="content-label">{value}</text>;
  }

  return (
    <view className="content-panel">
      <text>{value}</text>
    </view>
  );
}
```

Runtime data still selects the branch, but the host structure of each branch is visible to the compiler, so each can be statically extracted. Use dynamic creation only when the host type genuinely comes from runtime configuration.

### Explicit Properties Can Enable More Targeted Updates

Compiler-informed rendering also supports spread properties. The compiler knows which element receives the spread object, but because the set of properties is not known until runtime, it must record the entire object as one dynamic position. During an update, the runtime compares the properties in the old and new objects before applying changes to the target element:

```tsx
function UserCard({ id, name, selected }) {
  // A spread makes the entire property set one dynamic position.
  const cardProps = {
    id,
    className: selected ? 'user-card selected' : 'user-card',
  };

  return (
    <view {...cardProps}>
      <text>{name}</text>
    </view>
  );
}
```

When the property set is known during development, declaring properties explicitly can enable more targeted updates:

```tsx
function UserCard({ id, name, selected }) {
  // Each dynamic property gets its own position and updater.
  return (
    <view id={id} className={selected ? 'user-card selected' : 'user-card'}>
      <text>{name}</text>
    </view>
  );
}
```

The explicit form tells the compiler exactly which dynamic position corresponds to `id` and which corresponds to `className`, allowing it to generate targeted update logic for each property. It also avoids creating a `cardProps` object on every render. Spread remains appropriate when a component needs to forward unknown properties supplied by its caller; do not expand them one by one solely for static extraction.

When deciding whether JSX is suitable for static extraction, remember one principle: keep known host types, hierarchy, and order directly visible in the source, and let actual runtime data enter through properties or dynamic children. If a structure genuinely needs to be chosen at runtime, keeping it dynamic is more important than optimizing for the compiler.
