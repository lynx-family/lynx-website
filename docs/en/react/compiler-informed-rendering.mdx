# Compiler-Informed Rendering

ReactLynx analyzes JSX at build time and extracts stable host element structures ahead of time, allowing the runtime to focus on values and subtrees that may change.
We call this division of work between the compiler and runtime **compiler-informed rendering**.

This optimization is applied automatically. Most applications can continue writing clear, idiomatic JSX without changing their component design to accommodate the compiler.

Here, _host elements_ are [Lynx elements](/guide/ui/elements-components) such as `<view>` and `<text>` that ReactLynx renders through the Lynx Engine. User-defined components such as `<ProductCard>` are not host elements.

## What the Compiler Can Do Ahead of Time

Consider a regular component:

```tsx
export function Greeting({ name, highlighted }) {
  return (
    <view className={highlighted ? 'card active' : 'card'}>
      <text>Hello, {name}</text>
    </view>
  );
}
```

If JSX is transformed only as in a traditional, purely runtime Virtual DOM, without static extraction, the compiled result of `Greeting` is semantically similar to the following code:

```js
export function Greeting({ name, highlighted }) {
  return jsx('view', {
    className: highlighted ? 'card active' : 'card',
    children: jsx('text', {
      children: ['Hello, ', name],
    }),
  });
}
```

On every render, `jsx()` creates virtual nodes (VNodes) that describe the UI structure. ReactLynx then compares these nodes level by level to decide which host elements to reuse, create, or update. This process is known as [reconciliation](https://react.dev/learn/render-and-commit).

But in this example, the `view`, `text`, fixed text `Hello, `, and their parent-child relationships are static; only `className` and `name` can change. The compiler can generate the [Element PAPI](/api/engine/element-api) operations for creating the static structure ahead of time. The resulting static template definition can be reused across the initial renders of different instances and their subsequent re-renders; the runtime only needs to supply the dynamic data for each render. Conceptually, it looks like this:

```js
const GreetingTemplate = {
  // Create a template instance by directly executing compiled Element PAPI operations.
  create() {
    const pageId = ReactLynx.__pageId;
    const view = __CreateView(pageId);
    const text = __CreateText(pageId);
    const nameSlot = __CreateWrapperElement(pageId);

    __AppendElement(view, text);
    __AppendElement(text, __CreateRawText('Hello, '));
    __AppendElement(text, nameSlot);

    return { view, nameSlot };
  },

  // Update a known element directly without traversing the static structure.
  update(instance, { className }) {
    __SetClasses(instance.view, className);
  },
};

export function Greeting({ name, highlighted }) {
  return renderTemplate(GreetingTemplate, {
    className: highlighted ? 'card active' : 'card',
    nameSlot: name,
  });
}
```

These names and function shapes only explain the mechanism; they are not actual compiler output that applications can rely on. On the initial render, the compiled `create()` directly builds the known host structure. On subsequent renders, `update()` directly modifies a known element. The runtime does not need to repeatedly create and compare VNodes for this part of the structure, while children that cannot be determined ahead of time, such as `name`, are still handled through dynamic slots.

:::details Prior Art and the Current Implementation: Snapshot

This idea of using information known at build time to reduce runtime work is not unique to ReactLynx. [Vue's compiler-informed virtual DOM](https://vuejs.org/guide/extras/rendering-mechanism#compiler-informed-virtual-dom), [Owl's BlockDOM](https://odoo.github.io/owl/documentation/v2/miscellaneous/architecture.html#blockdom), and [Million.js](https://old.million.dev/blog/virtual-dom) all take a similar approach. From a broader computational perspective, it can also be understood as a form of [partial evaluation](https://en.wikipedia.org/wiki/Partial_evaluation): using host structures known from JSX to specialize the generic rendering process, leaving only the parts that cannot be determined ahead of time for runtime and producing an effect similar to “[partial prerendering](https://nextjs.org/docs/15/app/getting-started/partial-prerendering).”

In ReactLynx, this approach is currently implemented through an Intermediate Representation (IR) called a **Snapshot**. We are also exploring other representations with better performance. Snapshot follows the conceptual model above and can be summarized in four core parts:

| Compiled result     | Purpose                                                                                                  |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| Static creator      | Directly creates predictable Lynx elements and establishes their parent-child relationships.             |
| Dynamic updaters    | Updates a property, event, or spread property by index without traversing the complete static structure. |
| Dynamic child slots | Marks where dynamic subtrees such as components, conditional branches, text expressions, and lists go.   |
| Representation ID   | Identifies a reusable template so multiple template instances can share its static data.                 |

**Note:** The IR is an internal implementation detail. Do not depend on or copy these outputs in application code. Specific names, parameters, and data structures may change with the source code, compiler configuration, or ReactLynx version.

:::

## Writing Compiler-Friendly JSX

Dynamic properties, text, and children do not prevent compiler optimization by themselves. For most components, these three principles are enough:

- Keep component semantics clear and the code readable.
- Let runtime data flow through properties and children as usual.
- Let host types, hierarchy, and order that are already known during development appear naturally in JSX.

There is no need to split a component just to make a property or text value static, nor does the entire tree need to be static.
The compiler already separates stable structures from dynamic regions.

The following patterns are optional, not hard rules. Use them only when they also fit the component's intended semantics.

### Keep Shared Structure Visible When It Is Natural

The following code duplicates the entire card structure in both branches:

```tsx
function ProductCard({ name, price, showPrice }) {
  if (showPrice) {
    return (
      <view className="product-card">
        <text className="product-name">{name}</text>
        <text className="product-price">{price}</text>
      </view>
    );
  }

  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
    </view>
  );
}
```

When both branches naturally represent the same component structure, you can keep one stable shell and make the price region a dynamic child:

```tsx
function ProductCard({ name, price, showPrice }) {
  return (
    <view className="product-card">
      <text className="product-name">{name}</text>
      {showPrice && <text className="product-price">{price}</text>}
    </view>
  );
}
```

The second form makes the shared shell more directly visible to the compiler and leaves only the price region in a dynamic slot.
However, do not restructure conditional rendering solely for compiler optimization. Different forms may affect component identity, state preservation, and readability.

### Write Known Host Element Types Directly

The compiler can only analyze JSX structures visible in the source.
If a host type is not determined until runtime, that part of the structure must also be handled at runtime:

```tsx
import { createElement } from '@lynx-js/react';

function DynamicNode({ type, value }) {
  return createElement(type, { className: 'content' }, value);
}
```

If the candidate structures are already known during development, write them as explicit JSX branches:

```tsx
function Content({ variant, value }) {
  if (variant === 'label') {
    return <text className="content-label">{value}</text>;
  }

  return (
    <view className="content-panel">
      <text>{value}</text>
    </view>
  );
}
```

Runtime data still selects the branch, but the host structure of each branch is visible to the compiler, so each can be extracted separately.
Use dynamic creation only when the host type genuinely comes from runtime configuration.

### Declare Known Properties Explicitly

Compiler-informed rendering supports spread properties.
The compiler knows which element receives the spread object, but because the property set is not known until runtime, it must preserve the entire object as one dynamic position:

```tsx
function UserCard({ id, name, selected }) {
  const cardProps = {
    id,
    className: selected ? 'user-card selected' : 'user-card',
  };

  return (
    <view {...cardProps}>
      <text>{name}</text>
    </view>
  );
}
```

When the property set is known during development, declaring properties explicitly lets the compiler generate more targeted update logic:

```tsx
function UserCard({ id, name, selected }) {
  return (
    <view id={id} className={selected ? 'user-card selected' : 'user-card'}>
      <text>{name}</text>
    </view>
  );
}
```

The explicit form also avoids creating a `cardProps` object on every render.
Spread remains appropriate when a component needs to forward unknown properties from its caller; do not expand them one by one solely for compiler optimization.

In short, keep known host structures directly visible in the source and let actual runtime data enter through properties or dynamic children.
For structures that genuinely need to be determined at runtime, keeping the code natural and dynamic is more important.

## How the Compiler and Runtime Work Together

One characteristic of ReactLynx is that this compiled representation participates not only in update-time reconciliation, but also in Lynx's dual-thread [Instant First-Frame Rendering (IFR)](/guide/interaction/ifr) pipeline.

### One Template, Two Instances per Use

This section uses _template_ for the reusable compiled structure described above, which is a Snapshot in the current implementation. A _template instance_ is one use of that structure at runtime. Three roles work together:

| Role                          | Where it lives                          | How many                                                | What it holds                                                                                 |
| ----------------------------- | --------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Template                      | Compiled into the code for both threads | One per JSX structure, such as one for every `Greeting` | The static creator, dynamic updaters, slot positions, and template identity.                  |
| Main-thread template instance | Main thread                             | One per mounted use                                     | The Lynx elements built by the static creator.                                                |
| Background template instance  | Background thread                       | One per mounted use                                     | The latest dynamic values and dynamic children used for reconciliation, but no Lynx elements. |

For example, rendering `<Greeting name="Alice" />` and `<Greeting name="Bob" highlighted />` uses one `Greeting` template and two pairs of template instances. Both main-thread instances are built by the same static creator, so their element structures are identical. They differ only in the dynamic values each instance receives.

The two instances in a pair share an identity, which lets each thread refer to the same instance across the thread boundary. Static structure never crosses that boundary, because both threads already have the template. Only identities and dynamic data cross it:

- During the initial render, the main thread reports which template instances it created and which dynamic values it used.
- During updates, the background thread sends changed dynamic values and child changes for specific template instances.

The following sections follow this data flow through both stages.

### Initial Render: Create a Template Instance

The initial render takes three steps:

1. **The main thread renders the first frame.** It runs the components and creates a main-thread template instance for each use of a template. The static creator builds the Lynx elements, the dynamic updaters apply the initial dynamic values, and dynamic children are inserted into the slots reserved by the compiler. The first frame can be displayed at this point.
2. **The main thread describes what it created.** It sends the background thread a description of its template-instance tree: the template, identity, and dynamic values of each instance. The Lynx elements themselves stay on the main thread.
3. **The background thread hydrates.** It runs the same components again to build its own template-instance tree, pairs each background instance with the main-thread instance at the same position, and adopts that instance's identity. Where its dynamic values or children differ from the main-thread result, it sends only those differences back.

The following pseudocode illustrates this process:

```js
// Main thread: execute React and perform first-frame rendering to achieve IFR
const initialRender = mainThreadRoot.render(<App />);

// Background thread: execute React again and hydrate from the main-thread result
const backgroundRoot = hydrateRootFromMainThread(initialRender, <App />);
```

Here, `initialRender` abstracts the template-instance description from step 2. `hydrateRootFromMainThread()` abstracts step 3: the background render, instance pairing, and initial difference synchronization. It returns the long-lived background root responsible for reconciliation. These names illustrate the mechanism and are not current public ReactLynx APIs.

Here, we borrow the concept of SSR hydration to describe this process: the main thread runs the application first and creates the Host Tree required for the first frame, allowing content to be displayed without waiting for the background thread to become ready. The background thread then runs the application again and attaches its own template-instance tree to the existing Host Tree instead of recreating the entire tree.

ReactLynx takes advantage of the main thread's ability to create the Host Tree ahead of time, blocking the UI thread until the initial render completes so that the first displayed frame already contains content. This is [Instant First-frame Rendering (IFR)](/guide/spec.html#first-frame-rendering). After the initial synchronization, the background thread takes over subsequent reconciliation, while the main thread continues to own the Lynx elements and apply updates.

### Updates: Process Only Changes to Dynamic Positions

After hydration, every background template instance has a main-thread counterpart with the same identity, and the background thread drives all later updates:

1. A state or property change runs the affected components again on the background thread.
2. For each affected template instance, the background thread compares the new dynamic values with the ones it stored last time. React reconciles the dynamic children.
3. The background thread sends only the changes to the main thread, labeled with the template-instance identity and the dynamic position.
4. The main thread finds the template instance by that identity. It passes each changed value to the template's updater for that dynamic position and applies child changes to the reserved slots.

The static part of the structure is not created or compared again during this process.

The following pseudocode illustrates the same mechanism for any template. Changes to dynamic properties can be handled by targeted updaters generated by the compiler, while dynamic children remain reconciled by React:

```js
// Background thread
function reconcileTemplate(previous, next) {
  const propertyChanges = diffDynamicProperties(previous, next);
  const childChanges = reconcileDynamicChildren(previous, next);

  sendToMainThread({ propertyChanges, childChanges });
}

// Main thread
function applyTemplateChanges(Template, instance, changes) {
  if (hasChanges(changes.propertyChanges)) {
    Template.update(instance, changes.propertyChanges);
  }

  applyDynamicChildChanges(Template, instance, changes.childChanges);
}
```

For dynamic properties, the main thread directly calls the compiler-generated `Template.update()` without traversing the static host structure again. For dynamic children, React still performs reconciliation on the background thread, and the main thread applies the resulting child changes to the reserved slots.

## Back to Application Code

Compiler-informed rendering is not an API that developers need to invoke manually. It is a division of work that ReactLynx performs automatically between the compiler and runtime. Regular JSX continues to work even when a component contains dynamic properties, conditional branches, lists, and user-defined components; the compiler extracts stable structures wherever it can determine them.

In day-to-day development, prioritize components with clear semantics: let known host structures appear naturally in JSX, and let dynamic data flow through properties and children as usual. Consider additional adjustments only when performance analysis identifies the code as a bottleneck, and only when those adjustments preserve the component's semantics.

In other words, let the compiler find optimization opportunities in natural JSX instead of organizing application code around a particular internal IR.
