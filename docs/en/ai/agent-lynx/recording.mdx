# Recorder

[Recorder](/guide/devtool/recorder) captures Lynx page runtime state for deterministic replay. Its artifacts include template loading, runtime inputs, and environment data so a page can be reproduced outside its original app environment. It complements [performance tracing](tracing.mdx): traces describe execution and timing, while Recorder reconstructs the page and its runtime behavior.

The bundled `lynx-recorder` skill guides capture. `lynx-recorder-fixture` provides artifact inspection, decoding, and editing tools. An agent can complete a recording, then continue inspecting its contents when needed.

## From Page State to a Replay Artifact

This example continues with the [Tailwind CSS Settings page](https://github.com/lynx-family/lynx-examples/tree/3b019cec94b0e7b83e2239dd52839365fdd76522/examples/tailwindcss), opening it and switching to the Ocean theme. The app is already [connected](connections.mdx), `$CLIENT_ID` identifies it, and the bundle URL is reachable by the device.

The conversation emphasizes capture boundaries and artifact checks: **start Recorder before opening the page** so the replay includes `loadTemplate`. The theme change is the page state being reproduced in this example.

<AgentConversation {...recorderExample} locale="en">

The `savedFiles` returned by `recorder end` contains the actual output paths, which may include session suffixes or multiple files. `$FIXTURE_SKILL_DIR` is the directory returned by `skills get lynx-recorder-fixture`. The summary tool reads the saved filename instead of assuming that the `-o` argument is the final path.

## Recording and Artifact Capabilities

| Capability                   | What it supports                                                                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Start and finish capture     | `recorder start` and `recorder end` use the same client to capture and save page runtime data                                                    |
| Check capture completeness   | `recorder end` returns paths, action counts, `hasTemplate`, and diagnostics; without `loadTemplate`, record again starting before the page opens |
| Inspect an existing artifact | The fixture skill's `summary` and `decode` accept local files or URLs to inspect the Action List, calls, callbacks, and configuration            |
| Change replay inputs         | The fixture skill can edit mock responses, runtime operations, and environment settings, then `encode` a new replay file                         |
| Reproduce and share a page   | Host the artifact at a device-accessible URL and replay it in a Recorder-capable host; see the [Recorder replay guide](/guide/devtool/recorder)  |

The host must support Recorder. If starting returns `restartRequired: true`, restart the app, rediscover its client, and start again before opening the target page.

A `.json` extension does not always mean plain JSON: Recorder artifacts may contain `base64(zlib(JSON))`. The fixture tools handle that encoding. When editing, preserve action order, call/callback associations, and template contents. `healthy` and `hasTemplate` confirm artifact structure and required data; actual replay is performed by a Recorder-capable host.
