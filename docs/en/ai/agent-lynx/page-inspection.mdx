# Page Inspection and Interaction

Once the agent has found a page, give it a task to complete. It uses snapshots to understand the page, chooses an element to act on, and reads the resulting state to verify the outcome.

## Switch a Theme and Verify the Result

Continue the [connection guide](connections.mdx): the agent has loaded the `lynx-devtool` skill and found the Settings page. The conversation below uses the same client, `android-phone:8901`, and session, `1`, to switch its theme.

<AgentConversation locale="en" {...themeExample}>
  <p>
    Switched to <strong>Ocean</strong>. The page root's background color changed
    from <code>rgba(9, 9, 11, 1)</code> to <code>rgba(15, 23, 42, 1)</code>,
    matching the Ocean background color in this example.
  </p>
</AgentConversation>

The conversation uses the page structure to identify the target: the `Ocean` label is `@e16`, inside the `@e15` button container. After tapping it, the agent reads a new tree and compares the root's computed style. Its conclusion comes from the page state before and after the action.

An `@eN` ref identifies an element in the current page snapshot. The daemon retains these refs between calls. After navigation, reloads, or content changes, read a new snapshot and choose the target from that tree. This theme switch preserves the tree structure and its ref numbers; other changes can assign different numbers.

## Scroll to Inspect Offscreen Content

A full snapshot can include nodes marked `offscreen`, helping the agent discover content beyond the viewport. To inspect the bottom of Settings, it first finds the `scrollable` container, scrolls, and then reads the visible content.

<AgentConversation locale="en" {...scrollExample}>
  <p>
    The bottom of the page contains <strong>Danger Zone</strong>, with{' '}
    <strong>Delete Account</strong> and <strong>Cancel</strong> buttons and a
    description of irreversible actions. I only scrolled to inspect the content.
  </p>
</AgentConversation>

The visible snapshot after scrolling confirms that the bottom buttons have entered the viewport. Use `snapshot --visible-only` to inspect the current screen, or a full snapshot to discover content outside it.

## Give the Task a Completion Condition

On your own pages, describe input, waiting, and long-press tasks in the same way. Tell the agent what to change and what would confirm success so it can choose an action and check the result:

| Task             | What you can say                                                                | What the agent should check                                                                                         |
| ---------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Edit input       | “Replace the search field's contents with Lynx and confirm the displayed text.” | Find a field marked `editable`, replace its contents with `fill` or empty it with `clear`, then read the new state. |
| Wait for loading | “Wait until the page says ‘Loading complete’, then report the result.”          | Use `wait --text` for the page's completion signal, then inspect the corresponding content.                         |
| Inspect a menu   | “Long-press this message and check which actions are available.”                | Find the message, use `long-press`, and read the resulting menu from a new snapshot.                                |

Display Name and Email in the Settings example are text displays. For input tasks, use a page with actual editable fields; the snapshot's `editable` flag helps the agent identify them.

The next guide's [annotated screenshot](screenshots.mdx#annotated-and-fullscreen-screenshots) uses the same Settings example to connect visible boxes with element refs. If an action does not produce the expected change, continue with [logs and runtime debugging](debugging.mdx). See the [CLI reference](cli-reference.mdx#page-inspection-and-interaction-options) for parameters, snapshot refresh behavior, and wait units.
