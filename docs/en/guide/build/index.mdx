# Building and Shipping Bundles

How a Lynx app is built and shipped: which tool builds it, what it produces, and how to keep it running on the Lynx Engine you target.

- [Lynx Bundles and Compatibility](./lynx-bundle.mdx): what a build produces and which engines run it
- [Output Files](./output.mdx): where the files land
- [Rspeedy](./rspeedy.mdx): the earlier CLI around the same engine, and moving off it

## Which tool to build with {#tools}

A Lynx app is built by [Rsbuild](https://rsbuild.rs/). What makes the output a Lynx bundle instead of a web bundle is [**`pluginLynx`**](/api/packages/rsbuild-plugin), the Lynx build engine packaged as a set of Rsbuild plugins.

There are two ways to run that engine:

- **Rsbuild with `pluginLynx`** — the recommended setup. You own an ordinary `rsbuild.config.ts` and use the `rsbuild` CLI.
- **Rspeedy** — a wrapper around the same engine, with its own `rspeedy` CLI and `lynx.config.ts`.

```bash
# Rsbuild with pluginLynx (recommended)
npm create @lynx-js/lynx@latest -- --template rsbuild-react-ts

# Rspeedy
npm create @lynx-js/lynx@latest -- --template rspeedy-react-ts
```

Both produce the same `.lynx.bundle`, and the dev server, HMR, QR code and debug metadata behave identically, because all of that lives in `pluginLynx`. What differs is who owns the CLI and how much of the Rsbuild configuration surface you can reach.

### Rsbuild with pluginLynx

`pluginLynx` (from [`@lynx-js/rsbuild-plugin`](https://www.npmjs.com/package/@lynx-js/rsbuild-plugin)) is what turns an Rsbuild build into a Lynx build. It configures the dual-thread output and bundle filename, keeps the intermediate files under `dist/.lynx/<entry>/`, tunes minification and source maps for the Lynx runtime, resolves modules through Lynx's `exports` conditions, serves the bundle over your LAN during development, and registers the debug metadata used to [map production errors to source](/guide/devtool/map-errors-to-source.mdx).

You rarely apply it by hand: [`pluginReactLynx`](/api/packages/react-rsbuild-plugin/functions/pluginReactLynx) applies it for you when it is not already registered, which is why the ReactLynx template lists only `pluginReactLynx`.

```ts title="rsbuild.config.ts"
import { pluginReactLynx } from '@lynx-js/react-rsbuild-plugin';
import { defineConfig } from '@rsbuild/core';

export default defineConfig({
  source: {
    entry: {
      main: './src/index.tsx',
    },
  },
  plugins: [pluginReactLynx()],
});
```

Two things to know:

- **[`source.entry`](https://rsbuild.rs/config/source/entry) takes the object form**, like any other Rsbuild project.
- **Apply `pluginLynx` yourself when you need its options.** The automatic application uses default options, so configuring [`output.filename.bundle`](/api/build/output/filename/bundle) or [`performance.profile`](/api/build/performance/profile) means adding `pluginLynx({ ... })` to `plugins` explicitly. It is not applied twice.

The options `pluginLynx` adds, and the Rsbuild options whose defaults it changes for Lynx, are listed in the [build configuration reference](/api/build).

Types come from Rsbuild:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "types": ["@rsbuild/core/types"]
  }
}
```

### Rspeedy

Rspeedy wraps the same engine with its own `rspeedy` CLI and `lynx.config.ts`. See [Rspeedy](./rspeedy.mdx).

### Which one to use

Use **Rsbuild with `pluginLynx`** for new projects. It is what [`@lynx-js/create-lynx`](https://www.npmjs.com/package/@lynx-js/create-lynx) recommends, it keeps you on the config and CLI the Rstack ecosystem documents, and the whole Rsbuild configuration surface and plugin catalog stays available.

Rspeedy is still maintained. An existing project that depends on the `rspeedy` CLI or on `lynx.config.ts` need not rush to move, but do not start a new one on it.

Running `npm create @lynx-js/lynx@latest` without `--template` asks which build tool to use, and also offers Rslib for a component library.

To move an existing project, see [Migrating an Rspeedy project](./rspeedy.mdx#migrating-an-rspeedy-project).
