# Building a Lynx App

Lynx builds use [Rsbuild](https://rsbuild.rs/) with [`pluginLynx`]. Use Rsbuild's TypeScript, CSS, static asset and plugin capabilities, while `pluginLynx` compiles code for both threads and encodes the bundles your host loads.

## Get started with Rsbuild {#getting-started}

Create a project with the ReactLynx Rsbuild template:

```bash
npm create @lynx-js/lynx@latest -- --template rsbuild-react-ts
```

In the generated project directory, install dependencies and start the dev server:

```bash
npm install
npm run dev
```

Scan the QR code with [Lynx Explorer](/guide/start/quick-start.mdx) to run the app on a device. The dev server updates the app when you save your code.

The template's build configuration lives in `rsbuild.config.ts`. [`pluginReactLynx`](/api/packages/react-rsbuild-plugin/functions/pluginReactLynx) applies `pluginLynx` automatically, and [`pluginQRCode`](/api/packages/qrcode-rsbuild-plugin) provides the QR code:

```ts title="rsbuild.config.ts"
import { pluginQRCode } from '@lynx-js/qrcode-rsbuild-plugin';
import { pluginReactLynx } from '@lynx-js/react-rsbuild-plugin';
import { defineConfig } from '@rsbuild/core';

export default defineConfig({
  source: {
    entry: {
      main: './src/index.tsx',
    },
  },
  plugins: [pluginQRCode(), pluginReactLynx()],
});
```

When development is complete, use `rsbuild build` to generate production files and `rsbuild preview` to preview them locally.

### Configure your app

`rsbuild.config.ts` accepts the full [Rsbuild configuration](https://rsbuild.rs/config/). Configure the capabilities your project needs:

- <span id="typescript" />
  **[TypeScript](./typescript.md)**: build-time declarations and types for
  application data, elements and native modules.
- <span id="styling" />
  **[CSS](./styling.mdx)**: CSS Modules, global styles, pre-processors and
  PostCSS. For Tailwind, see the [Lynx preset
  setup](./styling.mdx#tailwind-css).
- <span id="static-assets" />
  **[Static assets](https://rsbuild.rs/guide/basic/static-assets)**: images,
  fonts, the `public/` directory, URL prefixes and inlining.
- <span id="module-resolution" />
  **[Module resolution](https://rsbuild.rs/config/resolve/alias)**: path aliases
  and dependency resolution. `pluginLynx` prefers dependencies' `lynx` export
  condition; see [`resolve.extensions`](/api/build/resolve/extensions) for file
  extensions.
- <span id="plugins" />
  **[Plugins](https://rsbuild.rs/plugins/list/)**: add Rsbuild plugins or extend
  the underlying build through `tools.rspack`.

The [`rsbuild.config.ts` reference](/api/build) describes Lynx-specific options and changed defaults. For example, to customize the bundle filename, explicitly add `pluginLynx({ output: { filename: { bundle: 'app.lynx.bundle' } } })` to `plugins`; it will not be applied twice.

### Optimize and debug

The build also provides ways to control loading, investigate performance and diagnose problems:

- **[Code splitting](/react/code-splitting.md)**: load some code on demand to reduce what the first screen needs.
- <span id="external-bundles" />
  **[External Bundle](./external-bundle.mdx)**: build common dependencies into a
  bundle shared by several apps.
- **[Build profiling](https://rsbuild.rs/guide/debug/build-profiling)**: use tools such as Rsdoctor to understand build time and dependencies.
- <span id="debugging-and-profiling" />
  **[Runtime
  profiling](/guide/performance/analysis-performance/analysis-framework.mdx) and
  [bundle size
  analysis](/guide/performance/analysis-performance/analysis-bundle-size.mdx)**:
  investigate runtime and loading costs.
- **[Production error mapping](/guide/devtool/map-errors-to-source.mdx) and [UI source maps](/guide/devtool/ui-source-map.mdx)**: use build-generated debugging information to connect errors and rendered nodes to source code.

:::info Still using Rspeedy?
Rspeedy is still maintained and uses the same build engine as `pluginLynx`. Existing projects can keep using it; Rsbuild is recommended for new projects. See the [Rspeedy migration guide](./rspeedy.mdx#migrating-an-rspeedy-project) for the differences and migration steps.
:::

## Understand the output {#bundles}

<span id="lynx-bundle" />A [***Lynx Bundle***][Lynx Bundle] is the deliverable
for a Lynx app: a binary file ending in `.lynx.bundle`. The host passes its URL
or contents to the [***Lynx Engine***][Lynx Engine], which loads it and renders
the page. A Lynx Bundle has much in common with a web app:

<span id="what-is-inside-a-bundle" />
<span id="dual-thread-builds" />

| Part    | Web app                                                                      | Lynx Bundle                                                                                                                                    |
| ------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Scripts | JavaScript files loaded at runtime                                           | Encoded into the bundle by default; **main-thread** code creates the **first screen**, while **background-thread** code runs application logic |
| Styles  | CSS files loaded at runtime                                                  | CSS parsed into structured data and encoded into the bundle                                                                                    |
| Assets  | Separate images, fonts and other files, with small assets optionally inlined | Also supports separate files and inlining small assets                                                                                         |
| Entry   | The browser loads HTML, then the scripts, styles and assets it references    | The host loads the bundle directly, including page configuration and other metadata                                                            |

### Output files {#output-files}

#### Standard Lynx Bundle output

Build output goes into `dist/` by default:

```txt
dist/
├── [name].lynx.bundle  # application bundle
├── lazy-bundle/       # bundles loaded on demand
├── static/            # static assets and split scripts
└── .lynx/[name]/      # intermediates for debugging
```

Scripts are encoded into the bundle by default; code splitting can also produce files in `static/js/`. Set the bundle filename with [`output.filename.bundle`](/api/build/output/filename/bundle), other filenames with [`output.filename`](https://rsbuild.rs/config/output/filename), and output directories with [`output.distPath`](/api/build/output/dist-path). See the APIs for [source maps](/api/build/output/source-map) and [license comments](/api/build/output/legal-comments) for those options.

#### Web output

The same source can also target the web: the `web` environment produces a `.web.bundle`, loaded by `<lynx-view url="...">`. The `[platform]` placeholder in the default filename is the environment name, so the two environments produce `main.lynx.bundle` and `main.web.bundle` respectively.

#### From intermediate files to binary

The build first produces the **main-thread** script `main-thread.js`, the **background-thread** script `background.js` and styles. The `tasm.json` file organizes these contents and page configuration for [`@lynx-js/tasm`](https://www.npmjs.com/package/@lynx-js/tasm) to encode into the `.lynx.bundle` binary.

These intermediate files live in `.lynx/[name]/` and are kept in development builds by default; use `DEBUG=lynx` to retain them in production builds. Inspect `tasm.json` to see what the bundle encodes; `debug-metadata.json` supports [Production Error Mapping](/guide/devtool/map-errors-to-source.mdx).

### An app can have multiple bundles

Besides the main bundle, an app can load other bundles on demand or share them:

- **Lazy bundles**: load components through dynamic `import()`, with output in `lazy-bundle/`, to reduce what the **first screen** needs. See [Code Splitting](/react/code-splitting.md).
- **External Bundle**: build common dependencies into a separate bundle shared by several apps. See [External Bundle](./external-bundle.mdx).

## Compatibility {#compatibility}

This article explains how to ensure version compatibility between [Bundle] and [Lynx Engine], and how to handle challenges that come with Lynx Engine version evolution.

### Build from Source

A simple way to ensure compatibility is to **always build the Bundle with the Host application from source**.

- Bundle can fully utilize all features of the current Lynx Engine version
- Compatibility can be fully verified during development, what you see is what you get

### Multi-version Compatibility

However, in a complex project, the relationship between Bundle and Lynx Engine is not one-to-one:

- A Bundle might run in applications with different Lynx Engine versions

- An application can run multiple Bundles maintained by different teams

In this case, you need to set the [`engineVersion`] to ensure compatibility.

:::info Engine Version
When the Bundle's [`engineVersion`] is greater than the Lynx Engine version, it will not be able to run.
:::

For example: a Bundle with [`engineVersion`] 3.3 can run on Lynx Engine 3.3 and later versions, but cannot run on 3.2.

When a Bundle needs to run on multiple Lynx Engine versions, its [`engineVersion`] must not exceed the oldest Lynx Engine version it targets.

When running multiple Bundles on a single Lynx Engine version, each Bundle can set different [`engineVersion`]s, but none can be greater than the Lynx Engine version.

#### Version Incompatibility Handling

If you try to run a Bundle on a lower version of the Lynx Engine, a Fatal level error with code [10204](/api/errors/error-code.mdx#10204-e_app_bundle_load_parse_failed) will occur, and the rendering process will stop. This mechanism prevents potential runtime issues caused by version incompatibility.

#### Configuring Engine Version

The [`engineVersion`] is a string containing two version numbers, and you can specify it in your configuration file:

```ts title="rsbuild.config.ts"
import { defineConfig } from '@rsbuild/core';
import { pluginReactLynx } from '@lynx-js/react-rsbuild-plugin';

export default defineConfig({
  plugins: [
    pluginReactLynx({
      engineVersion: '3.2',
    }),
  ],
});
```

### Upgrading Lynx Engine

As Lynx Engine evolves, new features are added and some features may be deprecated. Their compatibility is also managed by [`engineVersion`].

#### New Features

Some new features **_will not_** affect existing Bundles, but if [`engineVersion`] is lower than the version where they were introduced, runtime detection is needed, for example:

```js
// Detect if `lynx.newlyAddedMethod` can be called
if (lynx.newlyAddedMethod) {
  lynx.newlyAddedMethod();
}
```

While some new features cannot run on lower versions of the Lynx Engine at all, so they will only be enabled when [`engineVersion`] is greater than or equal to the corresponding version.

#### Deprecated Features

Some features may be deprecated during iteration, and their behavior may change when a higher [`engineVersion`] is set.

- If only the Lynx Engine version is upgraded without upgrading the Bundle's [`engineVersion`], there will be no compatibility issues
- If both Lynx Engine and Bundle's [`engineVersion`] are upgraded, you need to read the CHANGELOG to ensure there are no unexpected behavior changes
