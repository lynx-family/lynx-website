# Building a Lynx App

A build turns your application's code, styles and assets into a [_Lynx Bundle_][Lynx Bundle] that a host app can load. During development, the dev server and hot updates bring changes to your device. For production, the build generates the files you deploy and the debugging information you use to investigate performance and errors.

Lynx builds use [Rsbuild](https://rsbuild.rs/) with [`pluginLynx`]. TypeScript, CSS, static assets and plugins use Rsbuild's capabilities. `pluginLynx` handles the parts specific to Lynx: building code for two threads, encoding bundles and adapting the output to the target [_Lynx Engine_][Lynx Engine]. This chapter explains how these pieces fit together, with detailed usage in each topic's guide.

## Build tools and development {#getting-started}

Use Rsbuild with `pluginLynx` for new projects. [Quick Start](/guide/start/quick-start.mdx) walks through creating a project, starting the dev server and running the app on a device. ReactLynx projects use [`pluginReactLynx`](/api/packages/react-rsbuild-plugin/functions/pluginReactLynx), which applies `pluginLynx` automatically; [`pluginQRCode`](/api/packages/qrcode-rsbuild-plugin) provides a QR code to open the app.

Configure the project in `rsbuild.config.ts`. Use `rsbuild dev` during development, `rsbuild build` for production and `rsbuild preview` to preview the output. The full Rsbuild configuration is available; the [`rsbuild.config.ts` reference](/api/build) describes the options Lynx adds and the defaults it changes. To set Lynx-specific options, configure `pluginLynx` explicitly in `plugins`.

Existing Rspeedy projects use the same build engine. See [Rspeedy](./rspeedy.mdx) for the configuration differences, maintenance commands and migration steps.

## Code, styles and assets

Writing an application follows familiar Rsbuild patterns, while Lynx provides the runtime. The build processes your source and assets; Lynx determines which elements, CSS properties and runtime APIs are available.

### Styling {#styling}

The build supports CSS Modules, global CSS, Sass, Less and PostCSS. CSS is parsed and encoded into the bundle, while Lynx configuration controls behavior such as component scoping and inheritance. [Styling](./styling.mdx) explains how these approaches work together. [Tailwind CSS](./tailwind.mdx) also needs `@lynx-js/tailwind-preset` to adapt its utilities to the styles Lynx supports.

### TypeScript {#typescript}

Rsbuild handles general build needs such as `.ts`, `.tsx` and path aliases. Lynx adds types for its globals, elements and native modules, which you can extend to describe your application's data and host capabilities. See [TypeScript](./typescript.md).

### Static assets {#static-assets}

Reference images, fonts and other assets from code or CSS. The build emits them as separate files or inlines small files as data URIs; files in `public/` are copied directly to the output. [Rsbuild's static assets guide](https://rsbuild.rs/guide/basic/static-assets) covers paths, URL prefixes and inlining. See [`output.dataUriLimit`](/api/build/output/data-uri-limit) for Lynx's default inlining threshold.

### Module resolution {#module-resolution}

A dependency can provide both web and Lynx implementations. `pluginLynx` prefers the package's `lynx` export condition so the app uses the implementation intended for Lynx. Configure path aliases through `tsconfig.json` or Rsbuild's [`resolve.alias`](https://rsbuild.rs/config/resolve/alias); see [`resolve.extensions`](/api/build/resolve/extensions) for file extension resolution.

## Bundles and the runtime {#bundles}

Each application entry produces a `.lynx.bundle` containing main-thread code, background-thread code, styles and page configuration. The host hands it to the Lynx Engine, so a build must also account for the engine versions its hosts use. The bundle's [`engineVersion`] sets the minimum required engine version. [Lynx Bundles and Compatibility](./lynx-bundle.mdx) explains bundle contents, dual-thread builds and version compatibility.

### Output files {#output-files}

Production files go into `dist/` by default. Alongside application bundles, there may be lazy bundles and separate static assets. Development builds also keep intermediate scripts, styles and debug metadata so you can inspect the build. See [Output Files](./output.mdx) for directory layouts, filenames and output configuration.

### Sharing code between apps {#external-bundles}

Several applications can load common dependencies from an external bundle, reducing what each app packages itself. This addresses a different reuse need from [code splitting](/react/code-splitting.md) within an application. [External Bundle](./external-bundle.mdx) explains how to build the shared bundle and load it in the host app.

## Extending the build {#plugins}

Lynx builds can compose Rsbuild plugins for pre-processors, type checking and asset optimization. For lower-level extensions, add Rspack plugins through [`tools.rspack`](https://rsbuild.rs/config/tools/rspack). See [Rsbuild's plugin documentation](https://rsbuild.rs/plugins/list/) for general extensions. Lynx's own plugins are listed under "Plugins and tools" in the API reference, starting with the package that provides [`pluginLynx`].

## Debugging and profiling {#debugging-and-profiling}

During a build, [Rsdoctor and build profiling](https://rsbuild.rs/guide/debug/build-profiling) help you understand build time and dependencies. Once the app runs, [framework profiling](/guide/performance/analysis-performance/analysis-framework.mdx) and [bundle size analysis](/guide/performance/analysis-performance/analysis-bundle-size.mdx) help you investigate performance and size.

The build's debug metadata also [maps production errors back to source](/guide/devtool/map-errors-to-source.mdx), while the [UI source map](/guide/devtool/ui-source-map.mdx) maps rendered nodes to the JSX that created them. These capabilities connect build output to source code for development and production debugging.
