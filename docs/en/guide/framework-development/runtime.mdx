# Runtime Model

A Lynx framework runtime starts with its main-thread entry. The main thread responds to engine lifecycle events, owns Element nodes, and turns state changes into UI updates.
On top of this required path, a framework can handle lightweight interactions directly or introduce a background thread when needed for state management, update scheduling, asynchronous tasks, and business logic.

This guide first builds a minimal runtime that uses only the main thread, then adds a background thread step by step along the path of a user interaction:

<Mermaid>{`
flowchart LR
  Data["Host data"] --> Lifecycle["Main-thread lifecycle"]
  Lifecycle --> Element["Element PAPI"]
  Element --> UI["UI"]
  UI --> Event["User interaction"]
  Event --> MainUpdate["Main-thread update handling"]
  MainUpdate --> Element
  Event -. "Forward when needed" .-> Background["Background-thread tasks and state"]
  Background -. "Data or patch" .-> MainUpdate
`}</Mermaid>

## Start with the Main-Thread Entry

Whether or not you introduce a background thread, the framework must first establish a loop on the main thread: receive data, update the Element tree, and commit the UI. The first step is to integrate with the page lifecycle.

### Integrate with the Page Lifecycle

The framework listens for lifecycle events defined by the Lynx engine through `lynx.getEngine()`, then converts them into its own render, update, and destroy entry points:

| Event               | UI lifecycle stage | Framework responsibility                                                                                                                                   |
| ------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `__RenderPage`      | Render             | Process initial data, turn state into Element PAPI operations, and create the initial Element tree. The first render uses the SDK's default commit timing. |
| `__UpdatePage`      | Update             | Consume subsequent data from the host, determine state changes, update the Element tree, and call `__FlushElementTree()` to commit the UI.                 |
| `__DestroyLifetime` | Destroy            | Remove engine and node listeners and release local references. If a background thread is in use, forward the destroy event to it as well.                  |

Start by registering the three lifecycle callbacks:

```ts title="main-thread.ts"
// Register page render, update, and destroy callbacks.
const engine = lynx.getEngine();
engine.addEventListener('__RenderPage', onRenderPage);
engine.addEventListener('__UpdatePage', onUpdatePage);
engine.addEventListener('__DestroyLifetime', onDestroyLifetime);

function onRenderPage(event) {
  const [data] = event.data;
  renderPage(data);
}
function onUpdatePage(event) {
  const [data] = event.data;
  updatePage(data);
}
function onDestroyLifetime() {
  clearPage();
}
```

The framework can now receive page data, but it has not yet converted that data into UI. Next, use [Element PAPI](/api/engine/element-api) in `renderPage` and `updatePage`.

### Build and Update the Element Tree

`renderPage` creates an Element tree from the initial data, while `updatePage` updates existing nodes with subsequent data:

```ts title="main-thread.ts"
const page = __CreatePage('0', 0);
const pageId = __GetElementUniqueID(page);
let titleText;

function renderPage(data) {
  // Create the Element nodes needed for this render.
  const container = __CreateView(pageId);
  const title = __CreateText(pageId);
  titleText = __CreateRawText(data.title);

  // Compose the nodes and attach them to the Page.
  __AppendElement(title, titleText);
  __AppendElement(container, title);
  __AppendElement(page, container);
}

function updatePage(data) {
  if (data.title === undefined) return;

  // Update the retained node reference, then explicitly commit this UI change.
  __SetAttribute(titleText, 'text', data.title);
  __FlushElementTree();
}
```

The first render uses the SDK's default commit timing. For subsequent updates, call `__FlushElementTree()` after modifying Element nodes to commit that batch of changes to Lynx.
The framework should also retain the node references required by later updates and release them when the page is destroyed.

### Release Page Resources

`clearPage` removes listeners registered during the page lifecycle and releases node references, Element mappings, and state:

```ts title="main-thread.ts"
function clearPage() {
  engine.removeEventListener('__RenderPage', onRenderPage);
  engine.removeEventListener('__UpdatePage', onUpdatePage);
  engine.removeEventListener('__DestroyLifetime', onDestroyLifetime);
  titleText = null;
}
```

The minimal main-thread path is now complete: host data enters through lifecycle callbacks, the framework converts it into Element PAPI operations, and the UI is rendered and updated.

## Handle Lightweight Interactions on the Main Thread

Next, add an interaction to the page. Register node events directly on the main thread with `__AddEventListener()`. When state management and update computation are lightweight, no background thread is required:

```ts title="main-thread.ts"
// Maintain state inside the framework and trigger an update when it changes.
function useState(initialValue) {
  let value = initialValue;
  const setValue = function (nextValue) {
    value = nextValue;
    updatePage({ title: value });
  };
  return [value, setValue] as const;
}

function renderPage(data) {
  const [title, setTitle] = useState(data.title);

  const titleElement = __CreateText(pageId);
  titleText = __CreateRawText(title);

  // The event callback requests an update through the framework's state setter.
  __AddEventListener(
    titleElement,
    'tap',
    function () {
      setTitle('Hello Lynx');
    },
    {},
  );
  __AppendElement(titleElement, titleText);
  __AppendElement(page, titleElement);
}
```

The framework should retain the node, handler, and event options, then call `__RemoveEventListener()` with the same arguments in `clearPage`.
For lightweight interactions such as counters and visibility toggles that do not depend on asynchronous tasks or complex scheduling, the framework can complete the entire “update state → modify Element nodes → commit UI” loop on the main thread.
When interactions begin to involve asynchronous tasks, complex scheduling, or heavier computation, move the work that can run independently of the UI to a background thread.

## Introduce a Background Thread When Needed

The background thread is an optional extension of the main-thread model. It neither owns Element nodes nor replaces the main thread. Instead, it computes new state or data patches and hands them to the main thread for UI updates.

### Establish Paired Communication Channels

The main thread and background thread exchange events through paired endpoints returned by `lynx.getJSContext()` and `lynx.getCoreContext()`.
An event dispatched from one endpoint is received by its paired endpoint on the other thread:

| Direction                       | Sender                                           | Receiver                                         |
| ------------------------------- | ------------------------------------------------ | ------------------------------------------------ |
| Main thread → background thread | `lynx.getJSContext()` on the main thread         | `lynx.getCoreContext()` on the background thread |
| Background thread → main thread | `lynx.getCoreContext()` on the background thread | `lynx.getJSContext()` on the main thread         |

Cache and reuse these endpoints for cross-thread communication. Send events with `dispatchEvent()` and receive them with `addEventListener()`.
During teardown, remove listeners using the same endpoint, event name, and function reference.
Keep event payloads small and serializable: pass only primitive values, arrays, and plain objects.

After establishing the communication channel, the framework must define an update protocol: the main thread sends a task, the background thread updates state and generates a patch, and the main thread applies the patch.

### Connect a Cross-Thread Update

The following example connects the two threads, in setup order, for a single tap-driven update:

<Mermaid>{`
sequenceDiagram
  participant Main as Main thread
  participant Background as Background thread
  Main->>Background: SetTitle { id, value }
  Background->>Background: Update state and generate a patch
  Background->>Main: Patch [...]
  Main->>Main: Element PAPI + flush
`}</Mermaid>

In the lightweight example above, `setTitle()` updates the UI directly on the main thread. After introducing a background thread, the state change passes through the following steps.

#### 1. Prepare the State Update on the Background Thread

```ts title="background.ts"
const [, setTitle] = useState('Hello World');

function useState(initialValue) {
  let value = initialValue;
  const setValue = function (id, nextValue) {
    value = nextValue;
    // Work that the framework must implement.
    handleUpdate(id, value);
  };
  return [value, setValue] as const;
}
```

A real framework can continue with scheduling, diffing, and batched updates inside `setValue`. Once this state update entry is ready, the main thread only needs to send the user's update intent.

#### 2. Send an Update Task from the Main Thread

```ts title="main-thread.ts"
const elementMap = new Map();
const backgroundThread = lynx.getJSContext();
function setTitle(element, title) {
  const elementId = __GetElementUniqueID(element);
  elementMap.set(elementId, element);
  backgroundThread.dispatchEvent({
    type: 'SetTitle',
    data: { id: elementId, value: title },
  });
}

function renderPage(data) {
  const titleElement = __CreateText(pageId);
  const titleText = __CreateRawText(data.title);
  __AddEventListener(
    titleElement,
    'tap',
    function () {
      setTitle(titleText, 'Hello Lynx');
    },
    {},
  );
  __AppendElement(titleElement, titleText);
  __AppendElement(page, titleElement);
}
```

The main thread sends only the serializable Element identifier and new value. It does not pass the Element node itself to the background thread.

#### 3. Receive the Task on the Background Thread

```ts title="background.ts"
const mainThread = lynx.getCoreContext();
mainThread.addEventListener('SetTitle', onSetTitle);

function onSetTitle(event) {
  const { id, value } = event.data;
  setTitle(id, value);
}
```

After receiving the task, the background thread runs framework logic through the state update entry. Next, organize the result as a patch that the main thread can consume.

#### 4. Generate and Return a Patch

```ts title="background.ts"
function handleUpdate(id, title) {
  // A real framework can perform diffing and batched updates here.
  const patch = [['__SetAttribute', id, 'text', title]];
  mainThread.dispatchEvent({
    type: 'Patch',
    data: patch,
  });
}
```

The patch contains only serializable operation names, Element identifiers, and new values. Finally, the main thread converts these descriptions into actual Element PAPI calls.

#### 5. Apply the Patch and Commit the UI

```ts title="main-thread.ts"
backgroundThread.addEventListener('Patch', onPatch);

function onPatch(event) {
  const patch = event.data;
  if (!Array.isArray(patch)) return;

  let didUpdate = false;
  for (const item of patch) {
    const [action, id, key, value] = item;
    const element = elementMap.get(id);
    if (!element) continue;
    switch (action) {
      case '__SetAttribute':
        __SetAttribute(element, key, value);
        didUpdate = true;
        break;
      default:
        break;
    }
  }

  if (didUpdate) __FlushElementTree();
}
```

This completes the loop for a single interaction: the main thread sends a task, the background thread updates state and returns a patch, and the main thread commits the UI.
When the page is destroyed, the main thread should also forward the destroy event, and both threads should remove communication listeners, node event listeners, and local state.
