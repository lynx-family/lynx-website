# Runtime Model

A Lynx framework runtime starts with its main-thread entry. The main thread responds to engine lifecycle events, owns Element nodes, and turns state changes into UI updates.
On top of this required path, a framework can handle lightweight interactions directly or introduce a background thread when needed for state management, update scheduling, asynchronous tasks, and business logic.

This guide first builds a minimal runtime that uses only the main thread, then adds a background thread step by step along the path of a user interaction:

<Mermaid>{`
flowchart LR
  Data["Host data"] --> Lifecycle["Main-thread lifecycle"]
  Lifecycle --> Element["Element PAPI"]
  Element --> UI["UI"]
  UI --> Event["User interaction"]
  Event --> MainUpdate["Main-thread update handling"]
  MainUpdate --> Element
  Event -. "Forward when needed" .-> Background["Background-thread tasks and state"]
  Background -. "Data or patch" .-> MainUpdate
`}</Mermaid>

## Start with the Main-Thread Entry

Whether or not you introduce a background thread, the framework must first establish a loop on the main thread: receive data, update the Element tree, and commit the UI. The first step is to integrate with the page lifecycle.

### Integrate with the Page Lifecycle

The framework listens for lifecycle events defined by the Lynx engine through `lynx.getEngine()`, then converts them into its own render, update, and destroy entry points:

| Event               | UI lifecycle stage | Framework responsibility                                                                                                                                   |
| ------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `__RenderPage`      | Render             | Process initial data, turn state into Element PAPI operations, and create the initial Element tree. The first render uses the SDK's default commit timing. |
| `__UpdatePage`      | Update             | Consume subsequent data from the host, determine state changes, update the Element tree, and call `__FlushElementTree()` to commit the UI.                 |
| `__DestroyLifetime` | Destroy            | Remove engine and node listeners and release local references. If a background thread is in use, forward the destroy event to it as well.                  |

## Introduce a Background Thread When Needed

The background thread is an optional extension of the main-thread model. It neither owns Element nodes nor replaces the main thread. Instead, it computes new state or data patches and hands them to the main thread for UI updates.

### Establish Paired Communication Channels

The main thread and background thread exchange events through paired endpoints returned by `lynx.getJSContext()` and `lynx.getCoreContext()`.
An event dispatched from one endpoint is received by its paired endpoint on the other thread:

| Direction                       | Sender                                           | Receiver                                         |
| ------------------------------- | ------------------------------------------------ | ------------------------------------------------ |
| Main thread → background thread | `lynx.getJSContext()` on the main thread         | `lynx.getCoreContext()` on the background thread |
| Background thread → main thread | `lynx.getCoreContext()` on the background thread | `lynx.getJSContext()` on the main thread         |

Cache and reuse these endpoints for cross-thread communication. Send events with `dispatchEvent()` and receive them with `addEventListener()`.
During teardown, remove listeners using the same endpoint, event name, and function reference.
Keep event payloads small and serializable: pass only primitive values, arrays, and plain objects.

After establishing the communication channel, the framework must define an update protocol: the main thread sends a task, the background thread updates state and generates a patch, and the main thread applies the patch.

### Connect a Cross-Thread Update

The following example connects the two threads, in setup order, for a single tap-driven update:

  Background->>Background: Update state and generate a patch

When the page is destroyed, the main thread should also forward the destroy event, and both threads should remove communication listeners, node event listeners, and local state.
