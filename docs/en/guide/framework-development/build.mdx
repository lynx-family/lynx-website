# Bundle Build

The previous guide established the boundary between the main thread, which drives the UI, and the optional background thread, which can take on additional logic.
This guide focuses on how to identify, assemble, and encode those assets so that a page can be delivered as a `.lynx.bundle` that the host app can load.

## Start with Two Entry Files

Begin with the simplest structure: **two entry files**. Suppose your framework generates the following files for a page:

```text
src/counter/
├── main-thread.ts   Runs on the main thread and draws the UI with Element PAPI
├── background.ts    Runs on the background thread and manages state and async logic
└── style.css        Styles
```

These are two **different files**, each compiled by the toolchain as an entry. This step is no different from a typical frontend build: two entries produce two JavaScript assets.
The next step is specific to Lynx artifact encoding: **how do you encode the main-thread, background-thread, and style assets as a single `.lynx.bundle`?**

<Mermaid>{`
flowchart LR
  MT["main-thread.ts"] --> MainJs[".rspeedy/counter/main-thread.js"]
  BG["background.ts"] --> BgJs[".rspeedy/counter/background.js"]
  CSS["style.css"] --> CSSRule["CSS rules"]
  MainJs --> Encode["Encoding input<br/>(tasm.json)"]
  BgJs --> Encode
  CSSRule --> Encode
  Encode --> Bundle["counter.bundle"]
`}</Mermaid>

A Bundle is not a simple concatenation of two JavaScript assets and CSS. It is a binary format encoded according to the Lynx template protocol.
Main-thread scripts, background-thread scripts, and styles are written into sections with distinct responsibilities.
The build tool must therefore identify and mark the thread role of each asset, assemble the assets into structured data according to the encoder's input contract, and finally generate the Bundle.

## Group and Wrap Thread Assets

Main-thread and background-thread assets are both JavaScript files, so their thread role cannot be determined from the file type alone.
The build tool must attach role metadata to each asset so that code for the two threads can be separated during assembly and encoding.

An Rspeedy plugin accesses the assets generated by the current build through `compilation`. Each asset includes its filename, its `source` content, and `info` metadata.
For more information about plugin hooks and build artifact processing, see [Rspeedy plugins](/rspeedy/plugin).

In your build plugin, identify the asset generated from the main-thread entry, retrieve it by filename with `compilation.getAsset()`, and write `lynx:main-thread` to its `info` with `updateAsset()`.

```ts title="thread-assets.ts"
function markMainThreadAsset(compilation, filename) {
  const asset = compilation.getAsset(filename);
  if (!asset) return;

  compilation.updateAsset(filename, asset.source, {
    ...asset.info,
    'lynx:main-thread': true,
  });
}
```

Assets marked with `lynx:main-thread` are assigned to the main-thread section. Other JavaScript assets are assigned to the background-thread section.
This is the default grouping rule used by the built-in Rspeedy plugins. The [ReactLynx build plugin](https://github.com/lynx-family/lynx-stack/blob/main/packages/webpack/react-webpack-plugin/src/ReactWebpackPlugin.ts), for example, follows this approach.

If your framework organizes its own entries and does not add this marker, you can instead set the contents of the main-thread and background-thread sections directly before encoding through the [`beforeEncode` hook](#encode-as-a-bundle), described later in this guide.

Background-thread JavaScript assets must also be wrapped with the [`RuntimeWrapperWebpackPlugin`](https://github.com/lynx-family/lynx-stack/blob/main/packages/webpack/runtime-wrapper-webpack-plugin/src/RuntimeWrapperWebpackPlugin.ts) provided by [`@lynx-js/runtime-wrapper-webpack-plugin`](https://www.npmjs.com/package/@lynx-js/runtime-wrapper-webpack-plugin):

```ts title="background-assets.ts"
import { RuntimeWrapperWebpackPlugin } from '@lynx-js/runtime-wrapper-webpack-plugin';

function wrapBackgroundAssets(chain: RspackChain) {
  chain.plugin('myLynx:runtime-wrapper').use(RuntimeWrapperWebpackPlugin, [
    {
      // Wrap only background-thread JavaScript assets.
      test: /^\.rspeedy\/.+\/background\.js$/,
    },
  ]);
}
```

The `test` pattern should match background-thread artifacts precisely so that main-thread assets are not wrapped.
The plugin wraps the code in a function. The host loads background scripts according to this convention and injects objects such as `console`, `setTimeout`, `NativeModules`, and `lynx` as module-level variables.
Main-thread code uses a different loading path and does not need this wrapper.

At this point, the main-thread asset has its thread-role marker, the background-thread asset has its runtime wrapper, and both thread assets are ready.

## Encoding Input: `tasm.json`

Next, the build tool collects the thread assets and associated styles for each logical entry, then assembles the structured input required by the encoder:

| Field             | Content                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------- |
| `lepusCode`       | **Main-thread** code: `{ root, chunks, filename }`.                                               |
| `manifest`        | **Background-thread** code: `{ filename: fileContent }`.                                          |
| `css`             | Style rule mappings and content.                                                                  |
| `compilerOptions` | Compiler switches such as `targetSdkVersion` and `enableCSSSelector`.                             |
| `sourceContent`   | `{ dsl, appType, config }`, where `config` is the page configuration.                             |
| `customSections`  | Extension data such as lazy-loaded components and bytecode. Leave it empty when it is not needed. |

:::info The field names can be misleading
`lepusCode` contains **main-thread** code, while `manifest` contains **background-thread** code. These legacy field names do not reveal that relationship. Swapping the contents does not produce an error; it produces a Bundle that cannot run.
:::

In development builds, this object is written directly to `.rspeedy/<entry-name>/tasm.json`:

```bash
# Production builds do not emit tasm.json by default. Enable it with DEBUG.
DEBUG=rspeedy:template rspeedy build
```

This file is not an intermediate build cache. It is the exact input received by the encoder, serialized with `JSON.stringify`.
When an artifact does not work as expected, inspect this file first. You can immediately see whether main-thread code is in `lepusCode`, background-thread code is in `manifest`, and styles are present.

## Encode as a Bundle

The final step uses [`@lynx-js/tasm`](https://www.npmjs.com/package/@lynx-js/tasm), the actual encoder. It writes the structured data above into a Lynx template binary and also produces debugging information and style diagnostics.

Within the build pipeline, two plugins from [`@lynx-js/template-webpack-plugin`](https://www.npmjs.com/package/@lynx-js/template-webpack-plugin) work together to complete this process. **They must be used together**: with only the first plugin, nothing performs the encoding; with only the second, there is no encoding input. Neither configuration produces a valid Bundle.

| Plugin               | Responsibility                                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `LynxTemplatePlugin` | Collects and groups assets by entry, assembles the object described above, and exposes the `beforeEncode` hook for adjusting the encoding input. |
| `LynxEncodePlugin`   | Receives encoding requests and invokes `@lynx-js/tasm` in a worker to perform the encoding.                                                      |

<Mermaid>{`
flowchart LR
  Assets["Grouped assets"] --> Template["LynxTemplatePlugin<br/>Assemble encodeOptions"]
  Template --> Json[".rspeedy/counter/tasm.json<br/>(written in dev / DEBUG)"]:::flow-label
  Template --> EncodePlugin["LynxEncodePlugin"]
  EncodePlugin --> Tasm["@lynx-js/tasm"]
  Tasm --> Bundle["counter.bundle"]
`}</Mermaid>

The following example shows how a framework build plugin registers `LynxTemplatePlugin` and `LynxEncodePlugin`:

```ts title="framework/plugin-lynx-bundle.ts"
import {
  LynxEncodePlugin,
  LynxTemplatePlugin,
} from '@lynx-js/template-webpack-plugin';

export const pluginFrameworkBundle: RsbuildPlugin = {
  name: 'myLynx',
  setup(api) {
    api.modifyBundlerChain((chain) => {
      chain.plugin(`${PLUGIN_NAME}:template`).use(LynxTemplatePlugin, [
        {
          ...LynxTemplatePlugin.defaultOptions,
          // The two thread entry names registered earlier.
          chunks: ['app__background', 'app__main-thread'],
          filename: '[name].lynx.bundle',
          intermediate: '.rspeedy/app',
          targetSdkVersion: '3.5',
        },
      ]);
      chain.plugin(LynxEncodePlugin.name).use(LynxEncodePlugin, []);
    });
  },
};
```

Up to this point, the main-thread and background-thread entries have remained **two separate files**. That is enough to understand the artifact structure, but most frameworks do not organize their source this way.

## When Both Threads Share the Same Source

In ReactLynx, for example, developers write a single component file that must be compiled for **both** threads:

- The main-thread artifact retains the rendering logic and removes event handling and Effects.
- The background-thread artifact does the opposite: it retains complete event handling and Effects, and carries the framework's state updates, scheduling, and diffing.

Both entries now point to the same file, so the file path alone cannot determine which transformation pipeline to use.
Assign a different [`layer`](https://rspack.rs/config/entry#entrydescriptionlayer) to each entry to distinguish the two compilation contexts.

```ts
chain.entry('counter__main-thread').add({
  import: ['./src/counter/index.tsx'],
  layer: 'framework:main-thread',
});
chain.entry('counter__background').add({
  import: ['./src/counter/index.tsx'],
  layer: 'framework:background',
});
```

A `layer` is a build-time compilation context; it does not create another runtime thread.
It propagates through the module graph. Loader rules match the layer of the importing module through [`rules[].issuerLayer`](https://rspack.rs/config/module-rules#rulesissuerlayer), then select the corresponding transformation pipeline.

This allows the same file to pass through entirely different compilation pipelines in the two layers.
ReactLynx uses this approach. For a concrete implementation, see the [entry handling in `@lynx-js/react-rsbuild-plugin`](https://github.com/lynx-family/lynx-stack/blob/main/packages/rspeedy/plugin-react/src/entry.ts).

Both configuration options come from Rspack and are not specific to Lynx. Note that `layer` solves only the **compilation** problem.
Asset grouping, `tasm.json` assembly, and encoding remain exactly the same as before. Regardless of how the source is organized, the final contract still identifies which code belongs to the main thread and which belongs to the background thread.
